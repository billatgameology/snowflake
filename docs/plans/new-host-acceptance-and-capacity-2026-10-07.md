## Done when

This operational task has no charter milestone. Glass/camera acceptance uses the existing plan's
done-when without softening it: exact registered replay/media, matching authored camera witnesses,
glass readability at start/middle/final/oblique views, seeks/reverse/play/pause/manual override,
reduced motion, responsive containment, zero legacy-mesh requests and the five failure lanes.
The named product checks, app build and real-browser/visual review pass, or a concrete failed
criterion and remaining recovery dependency is recorded without claiming acceptance.

NAS recovery records bind the needed assets to existing owner/record digests and describe current
backup availability and unresolved custody without exposing private filenames or credentials.
No source pruning is implied by restore success. A full roughly 215 GB restore is optional pending
the maker's scope answer; useful bounded checks and required comparison recovery proceed meanwhile.

Worker capacity records exact workload/source/runtime, actual concurrency, elapsed throughput,
memory headroom and a finite measured recommendation. Its registered short-row ladder is committed
before launch. A representative strict core pause/resume witness preserves the same scientific state
and matches uninterrupted continuation; it must not imply an accepted production resume protocol.
The discovery runner remains restricted to short independently terminal stages until it can resume.

## Approach

Use one common task checkout. Root owns product acceptance and progress; the NAS lane reads only
known catalogue/owner/receipt locators and recovers a bounded registered subset; the capacity lane
registers its finite protocol here before execution and uses existing ordinary solvers. Independent
read-only preparation can run in parallel. Benchmark timing runs sequentially after other heavy
work settles so concurrent build/restore/render load is not silently counted as host capacity.

Keep every historical comparison record/capture unchanged and create a separately named current
browser record. Supersede only the stale product capture contract needed to test the implemented
glass/camera behavior. The retired legacy publisher remains disabled; no NAS publication is inferred
from local acceptance. Store working logs/captures in `out/new-host-readiness-2026-10-07/` and record
their disposition. Durable small operational summaries belong in the tracked plan/results, while
large generated assets retain their existing governed owner and recovery method.

Known lessons and checks: the old bold-ice/stationary-camera capture cannot accept the new glass
candidate; uniform tests or screenshots alone prove no scientific gate; exact source/media hashes
and executable browser assertions must agree. A hash alone is not backup, and same-NAS custody
is one failure domain. Each benchmark row terminates independently; logs are not resume state.
Relevant controls are the existing scene-motion/comparison tests, NAS catalogue/restore verifiers,
strict ordinary LK checkpoint/resume contracts and Rules 6/14/15.
