Chapter 16

Where the numbers came from

The model needs hundreds of numbers before it can grow anything. Where did each one actually come from — and what happens to the ones nobody has ever measured?

~15 min read 5 interactive figures Part VI · What we tried to build

By the end you will be able to

  • Sort a mixed pile of model inputs into measured, fitted, diagram‑informed and numerical.
  • Explain why a missing number has to stay missing rather than be estimated.
  • Tell an independent check apart from a self‑consistency check — and say why only the first one is worth much.
  • Say why a rule about naming can be a scientific safeguard, when the worst failure mode is a believable wrong answer.

Four kinds of number

Chapter 15 gave you two labels for a number on screen: what it is, and what it has earned. This chapter gives you four for a number going in. The two jobs are different. Chapter 15 governed what the program is allowed to say about a quantity it has computed. This one governs where a quantity came from before any of it ran.

Here is the awkward fact that makes this necessary. Open the file that carries the model’s physical inputs and you will find, in one table: the number of water molecules in a cubic metre of ice, which is instrument data; a curve somebody fitted through a scatter of measurements; a curve somebody drew specifically so that the model would agree with the Nakaya diagram; and the rule for joining up dots on a graph, which is not physics at all. Printed as digits they look identical. They are not the same kind of thing.

So the project’s charter gives every solver input a provenance class, and the class travels with the number permanently — into the parameter file, into the code, into the test that checks the code, into the report at the end. The four classes are quoted here exactly as docs/libbrecht-parameters.md states them, in the section headed “Provenance classes (decision 0005; charter §2.7) — every entry carries one”.

SDAK, in the P3 line, is structure-dependent attachment kinetics — Part One’s chapter 13 left it as the open frontier: the proposal that a very narrow facet is much easier to start a new layer on than a wide one. It comes back at the end of this chapter, and it is the reason chapter 17 exists.

Read the P2 line again, because it contains a sentence doing real work: extrapolating a fit outside its range silently manufactures a fake result. That is not a style preference. Later in this chapter you will make a working copy of the model do exactly that, on purpose, and watch what it produces.

Key idea

A model input is not a number. It is a number plus a claim about where it came from, and it is the second half that decides what the model’s output may be used for.

Follow one number back to its page

A class letter is cheap. What stops it being decoration is a rule at the top of the parameter file, which reads, verbatim:

No number enters this file without a citation — paper, section or figure or table, and page. A parameter with no provenance is indistinguishable from a parameter someone tuned until the picture looked right, and that is the exact failure this project exists to avoid.

That last clause is the whole argument. Handed a simulation and told it produces snow crystals, you cannot tell from the output whether its constants were measured in a cold chamber or nudged until the pictures looked convincing. Both make pretty crystals; only one is evidence. A citation is not politeness towards the original author. It is the only thing that makes the difference visible from outside.

Below, every quantity is a real entry from that file. Pick one and the panel unrolls its chain. One of them is going to surprise you.

The surprise, if you found it, is σ0 — the nucleation parameter, which chapter 11 introduced as the reason a flat facet is reluctant to grow. It is one of the two most important numbers in the whole model. And it was read off a graph.

Not out of carelessness. Out of necessity. The parameter file states the situation plainly: “Neither the paper nor the monograph prints the fit formulas or a numeric table — the curves exist only as plots. Documented gap.” The values in the model are therefore digitizations of monograph Figure 4.5 (printed p. 144 / pdf 145), taken from a 300 dpi render of the plot, with a declared uncertainty of ±25% relative on σ0 and ±0.03 absolute on A. Class P2, and the file adds: “The figure is the authority; anyone can re-read it from research/1910.06389v2.pdf.”

How we know

The parameter file describes exactly how it read the plot: a 300 dpi page render, log–log axes, and “gridline‑anchored abscissae only” — meaning the horizontal positions were taken at printed gridlines rather than estimated between them. (A log–log plot is one where both axes are stretched so each step along them is a multiplication rather than an addition — 1, 10, 100 evenly spaced instead of 1, 2, 3. It is the shape that turns curves spanning many powers of ten into something you can actually read.) It also records what the source itself says about those curves: they are “little more than parameterized fits to experimental data” (monograph printed p. 145 / pdf 146). Even the original is a fit, not a measurement.

Declaring this costs the project something. “Read off a graph, ±25%” is a worse-sounding provenance than most published parameter tables admit to. It is also the truth, and the alternative — printing 0.032 with no note attached — would make an estimate look like a measurement.

The citation rule is enforced by more than good intentions. That parameter file is now hash-frozen — chapter 15’s fingerprint, pointed this time at a table of physical constants instead of a run manifest. (Line endings are normalised before the fingerprint is taken, which is why the file can say the fingerprint “survives this repository’s CRLF checkout conversion and can be verified on any platform”: Windows and Linux write the invisible end-of-line character differently, and without that step the same file would fingerprint differently on the two machines the project wants to compare.) This file’s fingerprint is registered in runner/src/phase6-protocol.ts and checked by a test, so “an edit here fails the suite rather than silently changing the physics under a completed sweep.” (The suite is the set of automatic checks that runs over the whole repository; one of them failing stops the change.) Corrections are still allowed, at a price the file prints: any change “invalidates every Phase 6 sweep result produced under the current protocol; the sweep re-runs in full.” The price is the point — “it is what stops a parameter from being adjusted after a disagreeing result is seen.” The sweep that freeze protects has since run — that is chapter 28 — and Phase 6 around it has not finished.

Read it off the graph yourself

“Read off a graph” probably sounds sloppy. Before you decide, try it.

Below is a blurred curve, deliberately degraded to feel like a printed plot at the wrong zoom level. Your job is the one the project did: read nine values off it, at nine fixed temperatures. The quantity is Aprism — a multiplier between 0 and 1 that caps how sticky a prism facet can ever be, no matter how much vapour is available. It sits in front of the exponential in the attachment rule, which you will see in full under “A factor of a hundred, hiding in an exponent”. Set the slider (or click the plot), record, repeat. Then press Compare.

One difference from the project’s own reading, and it matters three paragraphs from now. The project read monograph Figure 4.5. The curve below is not that plot — it is a closed-form equation for the same quantity, printed in a later Libbrecht paper that nobody on the project had seen. You are digitizing the source the project was afterwards checked against.

Now the part that matters, and it is not about who scored better.

The nine anchors in the model were digitized on 2026‑07‑15. Nobody on the project had the paper that prints the closed form. It turned up much later, and at the worst possible moment: the rule file records that three uncited Libbrecht papers printing closed forms for figure-digitized curves “surfaced the day after the table’s hash-freeze, converting a free upgrade into an ADR-plus-re-freeze decision.”

An ADR — an Architecture Decision Record — is one of the numbered decision records chapters 14 and 15 have both been quoting: one permanent, public file per decision, filed under docs/decisions/, setting out the context, the decision, its consequences, and the alternatives rejected. They are numbered in the order they were written, and a later mistake is repaired by adding a new record rather than rewriting the old one — a decision that has been overtaken keeps its number and gains a line saying which number replaced it — so the sequence doubles as the project’s history. That is the definition; the rest of Part Two uses the abbreviation and points back here.

So: a correction that would have been free the day before now costs a written decision and a re-freeze. That is why AGENTS.md now carries a Rule 12 reading “Check source currency before any freeze” — a rule written by getting it wrong first.

When the comparison was finally run, the digitized anchors reproduced the printed equation to 8.4% at worst and under 2% typically. The findings ledger — docs/findings-ledger.md, entry A2 — states why that is worth more than it sounds:

An extraction that agrees with sources it had no access to is independently confirmed, not merely self-consistent.

That sentence is the distinction this chapter most wants you to keep. Self-consistent means your two methods agree with each other — which they will, if they share an assumption or a spreadsheet. Independently confirmed means your method agrees with something it could not have peeked at.

Now be exact about what was independent here, because it is not the two curves. Figure 4.5 is Libbrecht’s and Eq. (5) is Libbrecht’s, and both render the same broad-facet model: research/libbrecht-figure-findings.md §2 introduces the equation as “the broad-facet model in full”, and the figure’s own caption calls its curves the “best-estimate CAK model functions”. One author, one model. The agreement therefore says nothing at all about whether he is right about ice. What was independent is the reading: the digitizer could not have peeked at Eq. (5), because nobody on the project had seen it, so agreement with it cannot have been engineered. The same file calls it exactly that — “an independent check on the digitization method”. That is the entire strength of the check, and it would have been destroyed had the papers arrived first.

Careful

So the strongest sentence this check licenses is a sentence about pixels: they were turned into numbers faithfully. It licenses nothing about ice. Those are different claims, and the difference is exactly the type × evidence split from chapter 15: the model was given a faithfully transcribed fit, which is not the same as being given a correct description of nature.

A temperature the table cannot answer

Class P2 comes with an obligation attached: record the functional form and its stated domain of validity. The digitized curve exists between (Tm − T) of 1 and 50 °C — that is, from −1 °C to −50 °C. Outside that window there is no curve, because there is nothing on the plot to read.

Most code, asked for a value outside its data, quietly continues the line and hands back a number. This code does not. Here is that guard, from core/src/libbrecht.ts, with its message tidied so that it reads as one sentence:

throw new Error(
  `(Tm - T) = ${x} C is outside the digitized domain [1, 50]
  — extrapolation is banned (libbrecht-parameters.md)`
);

where
throw
the program stops here. It does not return a value, it does not warn and continue, and no crystal is produced.
(Tm − T)
how far below freezing the run asked for, in °C — the horizontal axis of the digitized figure.
${x}
not a symbol from the physics, and not a printing error: it is a slot the program fills in with the actual number that was asked for, so that the message names the offending value instead of complaining in general. Ask for 55 °C below freezing and the message comes out saying 55 — which is what you are about to see happen in the panel below.
[1, 50]
the only interval the printed plot actually covers. In the file itself these two bounds are not typed as digits either — they are filled in the same way, read out of the anchor list, so that the message can never disagree with the data.

core/src/libbrecht.ts, interpIndex; pinned by core/test/libbrecht.test.ts — “throws outside the digitized domain instead of extrapolating”

Try to break it. The dial below drives a working copy of that interpolation code, running in your browser — same anchors, same joining rule, same error text. One thing differs, and it is the whole point of the demo: the repository’s own version has no off switch. The guard above is unconditional, and there is no flag, setting or argument anywhere in the project that turns it off. The copy adds a switch so that you can see what the alternative would look like.

So: the dial runs past both ends of the digitized window. Inside, you get numbers and a run. Outside, you get the message above and nothing else — unless you switch the safeguard off, in which case the copy will happily extrapolate and hand you a confident, entirely manufactured answer.

Notice what the naive answer looks like. It is not obviously wrong. It has the right number of digits, it sits on a smooth continuation of a real curve, and it would flow into the solver and produce a perfectly presentable crystal. That is the danger: an extrapolated parameter does not announce itself downstream.

The ban costs the project a result it would have liked. The Nakaya diagram runs all the way to 0 °C. The parameter file therefore records a hard consequence: “the warmest temperature Phase 6 may sweep is −1 °C, and the coldest is −50 °C. Any comparison against the diagram’s 0 to −1 °C strip is outside the digitized domain and is not made.” The model declines to sit an exam question it cannot honestly answer.

The inside of that window is where class P4 earns its keep. The file registers the exact rule for joining up the nine dots: log–log linear for σ0, plain linear for Aprism (which dips and touches 1, so a log scheme would be wrong for it), and extrapolation banned.

How we know

The justification for that scheme was wrong once, and the file says so in its own margin. It used to claim the curves are “near-straight on the log–log plot above (Tm−T) ≈ 3”. They are not. Measure the steepness in small pieces along the curve and it keeps changing — 0.22 at one end to 1.62 at the other on basal, 2.26 to 1.76 on prism — and forcing one straight line through everything from (Tm−T) = 3 outwards leaves a leftover error of 21% (basal) and 23.8% (prism). The replacement justification is measured rather than asserted: drop each interior anchor, rebuild it from its two neighbours, and see how far off you land. The worst case sits comfortably inside the ±25% band the anchors already carry — the interpolation entry in the tracer above carries the two figures — and runner/test/phase6-protocol.test.ts recomputes them from the live solver every time the suite runs, “so this justification cannot drift away from the code it describes.”

The cell that stays empty

That guard refuses to invent a number past the edge of a plot. Here is the same refusal one step earlier: what do you do about a number that nobody has published at all?

The model needs D, the diffusivity of water vapour in air — how fast vapour spreads out. Part One’s whole story about the runaway bump depends on it. The sources give a value at one atmosphere (≈ 2 × 10−5 m2/s, monograph Appendix A) and they give how it changes with pressure (D ∼ P−1, printed p. 65 / pdf 66). How it changes with temperature — which is the axis this entire project is built to sweep — is not printed anywhere in either source.

There is a standard-looking formula in the wider atmospheric literature. It would have been easy to type it in. The section of the parameter table that covers D instead reads, in full:

Notice the second row before you get to the last one. The same book prints D twice, and the two printings differ by a factor of two — 2 × 10−5 in the appendix, 10−5 in the main text. The parameter file does not quietly pick a winner and move on. It records both, names which one the solver adopted, and calls the discrepancy what it is: “the source’s own factor-2 looseness”. That is the state of the published record on a quantity Part One’s entire diffusion story runs through — which makes the empty cell underneath it more striking, not less.

The rule that produced that empty cell is the second half of the file’s opening rule, and it is worth reading slowly: “No number is guessed, interpolated, or recalled from memory. If a value is not in the source, the cell stays empty and the gap is stated. An empty cell is a research task; a wrong cell is a physics bug that will be discovered three phases later, if ever.”

What happened next is the part worth copying. Rather than fill the gap, the project went looking for what the source’s own numbers implied. The monograph prints a working table (Table 2.1) that includes a length called X0, from which D can be back-computed. Doing that at two very different temperatures gives D ≈ 2.02 × 10−5 m2/s at both −15 °C and −40 °C. In other words, the monograph’s own working table treats D as temperature-independent at one atmosphere. So the solver does the same, and says so — and the file adds a standing instruction: “anyone tempted to import a T^1.94-style law from other literature must cite it and log the change here.”

Still unsettled

This is a gap, not a solution. The file says where it bites and where it does not: “This matters most for Phase 6 temperature sweeps; at fixed T … it does not bite at all.” A sweep across temperature is precisely the thing the project is building towards, so this empty cell is a live weakness sitting in plain sight rather than a closed question.

A factor of a hundred, hiding in an exponent

A missing number at least announces itself: the cell is empty, and you can see that it is. Here is the opposite case — a number that is present, and correct, and in the wrong unit. It is the single easiest way to destroy this model while every number on screen still looks reasonable.

alphaHK = A · exp(−σ0 / σsurf)

where
alphaHK
the attachment coefficient — Part One’s “stickiness”. The fraction of vapour molecules that arrive at the surface and actually stay. Between 0 and 1.
A
a prefactor for that facet, read off the same figure; between 0 and 1.
σ0
the nucleation parameter — how much spare vapour a flat facet needs before a new layer can get started.
σsurf
the supersaturation right at the crystal surface, as the solver computes it there and then.

Libbrecht, arXiv:1910.09067 Eq. 3, p. 4 — as recorded in docs/libbrecht-parameters.md §1

Both σ0 and σsurf are ratios. You may write a ratio as a fraction (0.032) or as a percentage (3.2%). Libbrecht’s plots and text mostly use percent. The code uses fractions. And the two quantities sit on top of each other inside an exponential, so getting one of them in the wrong unit does not shift an answer by a bit — it multiplies the exponent by a hundred.

Put numbers on it. At −15 °C the model’s prism σ0 is 0.032. With σsurf = 0.01, the exponential is exp(−3.2) ≈ 0.041 — about four arriving molecules in a hundred stick, which is slow but real. Read “3.2 percent” as if it were the fraction 3.2, and you get exp(−320), which is about 1 × 10−139. The prism facet simply stops existing as a growing surface. Neither 3.2 nor 0.032 looks wrong on its own. The parameter file calls this out in its canonical-units section as “the single easiest way to destroy the model while every individual number ‘looks right.’”

So the file adopts one canonical unit — every supersaturation is a dimensionless fraction — and then does something slightly obsessive: every entry records the raw cited value in its raw units and the converted fraction, side by side. The conversion happens once, in public, at the point of extraction, where a reader with the paper open can check it.

That is the theory. In practice somebody still has to copy several hundred numbers out of a book without slipping. Try being that somebody.

The lesson is not “look harder”. It is that careful reading is a poor instrument and a written check is a good one, and that the check keeps working after the person who wrote it has stopped paying attention.

Checks of exactly this shape are real, and two of them are recorded in docs/findings-ledger.md as entry A4, the “transcription-fidelity floor”. The first: the monograph’s Table 2.1 — which is an embedded image in the PDF, so it cannot be copied and must be typed — was verified cell by cell against the page render. The second is better. The table’s water-saturation column was checked against Murphy & Koop (2005), a completely separate published formula that the solver does not use anywhere. The test that pins it records the outcome in its own comment: “Measured worst deviation is 1.78%, at the -1 C anchor; every anchor from -5 C to -40 C agrees to within 0.5%.”

Careful

None of this is the model reproducing nature, and the ledger refuses to let it be read that way. Entry A4 ends: “Not lab-data reproduction — recorded here as the fidelity baseline the A-class entries stand on.” Copying a table correctly is the floor, not the achievement. It is worth stating only because every later claim would be worthless without it.

The word you are not allowed to type

There is one more way for a number to go wrong, and it is the strangest safeguard in the project.

This solver has two ancestors. From Libbrecht it takes the attachment coefficient — the stickiness alphaHK in the equation above, dimensionless, between 0 and 1. From Gravner and Griffeath it takes an attachment threshold — a completely unrelated quantity, a cutoff on how much vapour must be sitting next to a site before it freezes, indexed by how many neighbours it has. The two have nothing to do with each other. They are measured in different things. They mean different things.

By convention, both are written α.

Chapter 15 showed one collision of this kind in the display layer, where two different quantities were both about to be drawn as blue cells. This one is worse, because it is not in the display layer. It is in the arithmetic.

The two quantities appear in the same update step of the same solver. The project’s rule file states the consequence in a sentence that could stand as the thesis of this whole section:

A model that conflates them will produce plausible-looking crystals for the wrong reasons — which is the worst available outcome for a project whose stated identity is epistemic honesty.

Read that carefully. The bad outcome is not a crash. A crash is a gift; you notice it. The bad outcome is a beautiful crystal that means nothing, because two different quantities got swapped somewhere inside a loop and the picture came out pretty anyway.

So the bare word is banned from the entire repository. Not discouraged — banned, and checked by a program. Every use has to say which one it is:

alphaHK, alphaHKBasal, alphaHKPrismalpha, αHertz–Knudsen attachment coefficient

The reason it is a scanner rather than a note in a style guide is given in one line, and it is the most transferable idea in this chapter: “Vigilance does not survive a model handoff; a failing build does.” A failing build is what happens when one of those automatic checks says no: the change is stopped, loudly, in front of whoever made it. Whoever picks this project up next — a different person, a different model, six months later — inherits none of today’s carefulness. They inherit the tests.

But be precise about how far the program reaches, because the rule itself is. The scanner reads identifiers — the names in the code. In a code file it reads every line, comments included, which is why the scanner’s own English comments have to carry waivers to describe the thing they ban. In a documentation file it reads only what sits inside inline code marks. Ordinary prose in a document it does not judge. Rule 7 says so in its closing line: “Reviewers enforce the qualified-prose rule because the scanner mechanically covers identifier cases only.” So half of Rule 7 is a failing build, and the other half is still a reviewer paying attention — which is exactly the vigilance the rule’s own best line says does not survive a handoff. The honest version is the more interesting one: the file names which half is which, rather than letting you assume the machine has both.

The editor below holds one real line from core/src/libbrecht.ts, with one change: in the repository that line is a return — the line that hands the answer straight back to whoever asked. Here it parks the answer in a name first, so that there is a name for you to rename. Type into it. Try the presets. Then turn the scanner off and see what you get.

Notice the escape hatch. A line carrying rule7-waive: plus a written reason is skipped — because the rule that bans the word has to be able to quote the word, and tests need fixtures that fail on purpose. The waiver is not a loophole so much as a confession: it demands a reason in writing, and it shows up in every future reading of that line.

The discipline reaches into prose too. Transcribing the monograph’s spherical-growth equations, the project hit a quantity the book writes as a bare Greek letter, and recorded in the parameter file: “Its diffusive counterpart, Eq. 3.18, is the ratio X_0/R, and is written out here rather than given a name, because a name built on the bare stem is what Rule 7 bans.” A quantity was left deliberately un-named. That is what enforcement looks like when it is real: inconvenient.

What a stamp buys, and what it does not

Provenance does not make a number correct. Nothing in this chapter has made a single value more accurate than it was. A ±25% digitization is still ±25% after you write “±25%” beside it.

What it buys is that the number’s status is legible — to a reviewer, to a future maintainer, and to you, reading a result twelve chapters from now. The comparison in chapter 28 has run; Phase 6 around it has not finished. When the argument about that verdict starts — why did it come out this way? — the argument is only possible if the inputs are already sorted. Was it the code? The numbers? Or the theory? You cannot even ask that question of a parameter table where measurements and guesses are printed in the same typeface.

Still unsettled — and who checked all this

Almost everything in this chapter has been checked, and almost none of it by a human expert. The project’s own process file states the position without softening it: “All reviews to date, internal and external-facing, are LLM reviews; for publication that is a disclosed limitation, not a substitute.” The same file requires that at least one human domain scientist read any manuscript before submission. That reading has not happened. The same limit applies to this page, which was checked by two reviewers, both of them language models. Carefully checked, and not yet expert-checked, are different things — which is, in the end, the argument of this whole chapter applied to the chapter itself.

And there is one class we have named but not spent. P3 — “Nakaya-informed SDAK hypotheses”. The parameter file explains the label by quoting the source’s own words about how those curves were chosen (monograph printed p. 152 / pdf 153):

I have chosen different values of Tonset for the basal and prism facets to impose agreement with the known ice-growth behaviors from the Nakaya diagram

Sit with that. Some of this model’s available inputs were set, by their original author, openly and for a stated reason, so that a model using them would agree with the Nakaya diagram. Available, and not used: nothing in the solver implements them. The parameter file records that “SDAK appears in no source file — so every run to date is a no-SDAK run.” They were extracted, classified, cited, and then deliberately left unwired, which is what makes chapter 28’s comparison a real test rather than a rehearsal.

Every number in the model now carries a stamp, and one of those stamps says that the value was chosen to make the model agree with the very diagram the project intends to test it against. Why leaving those values unwired was forced, what it cost, and why the parameter file keeps “two separate branches… never merged” is chapter 17 — which asks the uncomfortable question underneath all of it: what would it even mean for this model to be wrong?
