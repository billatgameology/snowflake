Chapter 26

Fast Without Being Wrong

The preview design budget keeps about eight million cells on the graphics card, split across bounded submissions. The card also does its arithmetic with about nine fewer digits than the careful version. So how do you know the fast answer is the same answer?

~18 min read 2 diagrams 5 interactives

By the end you will be able to

  • Explain why a graphics card's speed is a consequence of sameness, not of magic.
  • State a bounded-difference claim instead of an equality claim, and say why the weaker claim is worth more.
  • Describe the ordering that stops a project fooling itself: measure, publish the bound, then look at the answer.
  • Say what the word “faster” is a claim about — and why this project measured its own situation and retracted its own plan.

Chapter 25 left the hardest oracle problem of the lot still open: a program checked against another program — a fast engine on the graphics card, working in about seven decimal digits instead of sixteen, which must nonetheless be shown to agree with the slow, readable one. How wide should that envelope be, and who decides, and when? The short answers are the spine of this chapter: the envelope is measured, and its fingerprint published, before anybody is allowed to look at the fast code — and for the yes-or-no quantities there is no envelope at all. But the reason a graphics card forces that discipline rather than merely rewarding it starts with what the machine is, so that is where we start.

Why sameness is the whole trick

Why is a graphics card the right shape of machine for a snowflake? Not because it is “a faster computer.” A processor is a small number of very clever workers, each able to do a different job. A graphics card is thousands of simple workers who must all do the identical job at the same instant, each on a different piece of data. For most problems that restriction is crippling. For this one it costs nothing, because every cell in the lattice wants exactly the same instruction: look at your neighbours, and average.

Here is that instruction as it actually ships, from the in-plane diffusion pass in solver-gpu/src/diffusion-shaders.ts, line 186:

auxiliaryA[index] = (((own + low) + middle) + high) / 7.0;

where
own
the vapour value this cell currently holds
low, middle, high
the three opposing-neighbour pairs — east+west, north-east+south-west, south-east+north-west — placed in ascending order, so the seven values are always accumulated smallest-first
/ 7.0
the cell plus its six in-plane neighbours — seven values, one average
index
this worker's own cell, and no other

solver-gpu/src/diffusion-shaders.ts:186 · the pairing and the sort at lines 153–185

Notice what no cell needs: it never asks what any other cell has decided, only what that cell currently holds. That is the whole reason the work can be split a million ways at once.

The sorting deserves a second look, because it is the one thing in that line that is not obvious — and two sections from here summation order comes back as one of the reasons two correct programs disagree. Adding the same seven numbers in a different order gives a different 32-bit answer, so the shader fixes the order by value rather than leaving it to whatever the compiler felt like. The project has a whole decision record for the identical technique applied to a different reduction, the surface operator — ADR 0023, “Sum the opposing-vapor operands in ascending order”, which the repository version-numbers as surface policy v6, chapter 20's subject. Hold that label apart from the other v6 in this chapter: the Phase 5 protocol version is also numbered v6, and it means something entirely unrelated. The shadow program implements the same sort a second time, independently, as sortedTriple() (runner/src/phase5-shadow.ts, lines 108–121). It is also the one place in this pass where the workers do not literally do the identical thing: the branch ladder means neighbouring cells can take different routes through the sort. They still all run the same program, which is what the hardware demands. They just do not all take the same turning. One caution about that decision record, collected in full at the end of this chapter: the sort you have just read does ship, in this diffusion pass — but ADR 0023's fix to the surface operator was never ported to the graphics card, and that omission bounds what the closing conformance claim is allowed to say.

A compute shader — here written in WGSL, the shading language WebGPU uses — is a short program describing what one worker does. You then ask the card to run that same program hundreds of thousands of times, handing each copy a different ID number. The copy turns its ID into a cell index, reads that cell, writes that cell's answer, and stops. There is no loop over the grid anywhere in the shader. The loop is the launch.

Workers are launched in fixed-size squads — GPU_WORKGROUP_SIZE = 256 (solver-gpu/src/submission.ts, line 1) — and the number of cells is almost never an exact multiple of 256. So the last squad is partly empty, and its surplus workers are real workers who would happily write past the end of the array. Every shader therefore opens with a surplus-worker guard. The shared one reads (solver-gpu/src/shaders.ts, lines 4–9):

let index = uniforms.baseCell + invocation.x;
if (index >= uniforms.cellCount) {
  return;
}

where
invocation.x
this worker's ID number, handed out by the hardware
baseCell
where this chunk of work starts — large grids are cut into chunks, for a reason we get to below
cellCount
how many cells actually exist
return
“you are surplus. Do nothing.”

solver-gpu/src/shaders.ts:4–9, the shared GRID_ENTRY_GUARD

The production diffusion and surface shaders write the same idea in a slightly different, overflow-safe form — uniforms.baseCell >= uniforms.cellCount || invocation.x >= uniforms.cellCount - uniforms.baseCell — which subtracts rather than adds, so it cannot itself overflow while testing for overflow (solver-gpu/src/diffusion-shaders.ts, line 193, and twelve other places across diffusion-shaders.ts, gg-surface-shaders.ts and lk-shaders.ts). Same refusal, spelled two ways: if you are surplus, do nothing.

One more piece of plumbing decides the speed. On a graphics card, where your numbers sit often matters more than how much arithmetic you do. When 256 neighbouring workers read 256 neighbouring numbers, the hardware fetches them in one gulp; when they read numbers scattered far apart, it makes 256 separate trips. So each physical quantity gets its own flat array — all the vapour values together, all the occupancy flags together — rather than one array of little bundles. That is exactly how the buffers are declared: one named, four-byte-per-cell array per quantity, occupancy, wall, noise and the rest listed one to a line (solver-gpu/src/layout.ts, lines 13–54). Sameness again, one level down: not just the same instruction, but the same instruction reaching for numbers that happen to sit side by side.

Key idea

The graphics card's speed is a consequence of sameness. Anything that forces the workers to do different things runs badly — which is why several passes in this solver are deliberately launched with a squad size of one, the boundary-list rebuild among them (@compute @workgroup_size(1), solver-gpu/src/gg-surface-shaders.ts:288). Rebuilding the list of boundary cells has an order, and order is exactly what a thousand simultaneous workers destroy.

The bug your eye cannot see

A three-dimensional grid lives in memory as one long line of numbers, so you need a rule turning a coordinate into a position. In TypeScript it is one line (solver-gpu/src/layout.ts, line 112):

return k * layout.plane + j * layout.dims.nx + i;

where
i, j, k
the three grid coordinates of a cell
nx
how many cells fit along the first axis
plane
nx × ny — how many cells are in one horizontal layer

solver-gpu/src/layout.ts:112 · the same arithmetic, run backwards, at solver-gpu/src/shaders.ts:20–23

That rule is written twice: once in TypeScript for the host, once in WGSL for the shader. Two copies of one rule is a standing invitation to a bug — and it is the nastiest kind of bug in this project, because a swapped axis still runs. Nothing crashes. The pictures still look like ice. They are just a different crystal. The charter says so in the passage explaining why the language is strictly typed: “the solver is index arithmetic over flat typed arrays, and a swapped coordinate is a silent physics bug” (project charter.md, §3.1).

Two things defend against it, and it is worth being exact about which does what. First, the host refuses to build a layout whose cell-count arithmetic disagrees with the shared core package: throw new Error("GPU grid cell-count calculation disagrees with core") (layout.ts, lines 87–89). That catches a wrong size. It cannot catch a wrong filing order. Swapping two axes leaves nx × ny × nz completely unchanged — the fixture below, 17×19×11, has 3,553 cells either way — so this check passes cheerfully on the mutated mapping.

Catching the swap takes a second, harder check. The graphics card computes a fingerprint of every cell's three coordinates using its own index arithmetic; the host recomputes the same 3,553 values independently, from the TypeScript rule, and compares them one by one. And because a check nobody has watched fail is not yet a check, the project registered a negative control against it: a mutation written specifically to break this one thing.

The registered axis-swap control, transcribed from runner/src/phase5-protocol.ts, lines 897–901.

The 187 cells that do still agree are the ones where j happens to equal k: 11 values of k times 17 values of i. You can count them in the third panel above. (docs/plans/phase-5-gpu-port.md:573–575.)

Two arithmetics, one oracle

Now the harder problem. Computers store fractions in a fixed number of bits. The careful reference solver on the processor uses 64-bit floating point — about 15 or 16 significant decimal digits. The graphics card uses 32-bit — about 7. Every arithmetic result on the card is rounded to the nearest representable 32-bit value — with one exception we come back to. Do that a few hundred million times and the two machines' answers drift apart. Not because either is broken. Because they are different arithmetics.

So the slow solver is never thrown away. The charter fixes this before any shader exists: the processor solver “is the ground truth and the debugging environment. It is never deleted”, and four lines later, “Never port ahead of the oracle.” (project charter.md, §3.1.) The oracle of chapters 18 and 25 — whatever tells you the right answer — is here neither a person nor a paper: it is a slow, readable program you are allowed to step through line by line.

The instinct at this point is: fine — so check that the fast one gives the same answer. That is exactly the check that cannot be done, and the project says so out loud, in writing, before the first line of shader code:

“Float32 GPU vs float64 oracle and any future cross-engine or cross-backend comparison use stated tolerances, never bitwise equality; FMA contraction and driver shader compilers differ legitimately.”

project charter.md, §3.1, “Determinism scope”

And again in the phase plan, line 103: “An f32 result is compared by frozen tolerance, never described as bitwise-equivalent to float64.” Two correct implementations of one formula can differ in their last digits for at least five legitimate reasons: different storage widths; the hardware's fused multiply–add, which computes a×b + c with one rounding instead of two; different driver shader compilers reordering the arithmetic; different implementations of functions like exp(); and the order in which thousands of threads' partial sums are combined — which a reduction tree fixes in advance, precisely so that it is not left to whoever happens to finish first.

What replaces equality is a bounded difference, and the bound is a published number. Three statistics are computed for every compared field, and all three must pass — not the friendliest one: the worst single cell, the typical error across the whole field, and the error as a proportion of the value. Whole scalars — totals, ledgers — get a mixed bound instead:

|gpu − cpu| ≤ 1×10−4 + 2×10−4 · |cpu|

where
gpu
the value the float32 graphics-card run produced
cpu
the value the float64 oracle produced
1e−4
an absolute allowance, so a quantity near zero is not required to agree to a fraction of nothing
2e−4 · |cpu|
a proportional part, so a million-scale ledger is not required to agree to within 1e−4 — which would be a nonsense requirement

runner/src/phase5-protocol.ts:491–499 (PHASE5_SCALAR_TOLERANCES) · docs/plans/phase-5-gpu-port.md:373–376

Careful

Rounding error is not a bug. It is the arithmetic working as specified. The interesting question is never “is there error” but “is the error bounded, measured, and smaller than the thing I want to conclude.” A claim you can state precisely and check is worth more than a stronger claim you cannot.

Measuring the error before writing the fast code

Where do those tolerance numbers come from? The obvious and worthless answer is: run the fast code, see how far off it is, and set the bound just above that. Any bound chosen that way is guaranteed to pass, and therefore measures nothing.

What this project did instead was write a shadow. A shadow run is a deliberately slow, independent program simulating what the fast code will do to the numbers — written before the fast code exists, so it cannot be tuned to flatter it. Its own source file opens by refusing to be mistaken for the thing it models:

“Phase 5 WP0 CPU-side binary32 shadow. This is not a GPU implementation and must never be presented as one. It supplies pre-WGSL error measurements from (a) an independent operation-rounded diffusion kernel, (b) binary32 storage at each public SurfaceOperator boundary, and (c) scalar attachment-kinetics sweeps. Frozen tolerances add explicit safety factors over these measurements before any production shader exists.”

runner/src/phase5-shadow.ts:1–5

Concretely, it redoes the diffusion arithmetic in the order the shader will, rounding to 32 bits after every single operation — the file's own words: “Every arithmetic result that would inhabit a WGSL f32 value is explicitly rounded with Math.fround. The kernel is intentionally independent of GGSolver's mutable implementation” (lines 123–127). Then the ordering is stated as a rule. One piece of vocabulary first: an ADR is an architecture decision record, a numbered, permanent, public note saying what was changed and why.

“Tolerance values come from an operation-count error analysis plus a CPU-side float32 shadow probe, not from relaxing thresholds until a WGSL result passes. The probe and threshold rationale are committed before implementation results are inspected. Any later tolerance relaxation requires an ADR, invalidates comparison evidence, and reruns the Windows lane.”

docs/plans/phase-5-gpu-port.md:78–81

The frozen numbers then sit deliberately above what the shadow measured, because the shadow cannot see everything the real hardware does — fused multiply–adds, the reduction trees, the driver's own compiler. That gap is the safety factor, and it is published:

Once measured, the numbers were frozen and hashed. The tolerance manifest carries the SHA-256 d38ec0f7…, printed in full at runner/src/phase5-protocol.ts, lines 20–21. A hash is a short fingerprint of a file: change one digit of one tolerance and the fingerprint changes, so a quiet edit stops being quiet.

The bar that would not move

Then the real hardware answered back. One 64-pass diffusion fixture, run on the actual D3D12 driver — Direct3D 12, the way Windows talks to graphics hardware — came out at a root-mean-square error of 2.0899141975678157e-7 — narrowly above the independently frozen 2e-7 bound. Narrowly. Four and a half percent over.

The easy fix was sitting right there. Nudge the bound to 2.1e-7 and everything passes. What happened instead is recorded in the plan's Tried and rejected section, which is where this project lists the roads it did not take. The bullet's heading is about a different road — “Force every WGSL intermediate through the operation-rounded shadow sequence” — but it is where the decision about the bound is written down:

“Rejected after the real D3D12 64-pass noisy/drifting fixture produced RMS error 2.0899141975678157e-7, narrowly above the independently frozen 2e-7 bound. The tolerance was not relaxed. Explicit WGSL fused multiply-adds instead reduced error against the unchanged float64 oracle to 1.8798277887340792e-7…”

docs/plans/phase-5-gpu-port.md:1535–1540

A fused multiply–add computes a×b + c with a single rounding at the end instead of two, so it is more accurate — and “more accurate” means “different.” Writing it explicitly, as at solver-gpu/src/diffusion-shaders.ts line 215 (auxiliaryA[index] = fma(3.0 / 14.0, verticalPair, centerTerm);), moved the code under a line that never moved.

Freeze the number, then write code up to it. That sequence turns up again in a place with nothing to do with rounding, which is how you can tell it is a habit rather than a one-off. Every buffer entry on the card is exactly four bytes, and the per-cell totals are declared as data and checked: GPU_GG_BYTES_PER_CELL = 48, GPU_LK_BYTES_PER_CELL = 64, GPU_CELL_BYTES_CEILING = 64 (solver-gpu/src/layout.ts, lines 56–58). If a layout ever disagrees with its declared size, construction throws GPU <operator> schema has unexpected bytes/cell (same file, lines 177–179). And that ceiling was written down at the phase's planning stage — “WP0 reserves a conservative planning ceiling of 64 GPU bytes per cell… It is an allocation guard, not a promised WP1 layout” (docs/plans/phase-5-gpu-port.md:262) — before the layout existed, rather than measured afterwards from whatever the code happened to use. When a later decision gave the attachment-kinetics solver one extra buffer, its allocation rose from 60 to 64 bytes per cell: up to the already-frozen ceiling, not through it (docs/decisions/0021-bound-phase5-float32-two-cycles.md:74–75). Same shape as the tolerance. The number was fixed first, and the code came up to the line instead of pushing it — and what that extra buffer is actually for is a substantive piece of this chapter's own subject, told later on.

A tolerance may never vote on a yes-or-no

Some quantities in this model are continuous — how much vapour sits in a cell. Some are discrete — does this cell freeze, yes or no. Continuous quantities can be compared with a tolerance. Discrete ones cannot, because “approximately frozen” is not a state. So the harness proves, before comparing anything at all, that every blocking freeze decision sat comfortably far from its threshold, such that a 32-bit wobble could not possibly have flipped it:

“Blocking attachment decisions must be exact. Before comparison the CPU harness proves every G-G boundary-mass decision is at least 4e-4 from its threshold and every LK fill decision is at least 4e-4 from saturation. If a blocking fixture violates its margin, the fixture is invalid and the gate fails by configuration; the tolerance is never used to vote an occupancy bit.”

docs/plans/phase-5-gpu-port.md:298–302

That 4e-4 is not a free parameter either. In code it is written as 8 * PHASE5_FIELD_TOLERANCES.ggBoundaryMass.maxAbs (runner/src/phase5-protocol.ts, lines 526–529), so it is eight times the field tolerance by construction, and moves if that ever moves.

Read the rule again and notice the failure mode. It is not “the two engines disagreed.” It is “this run is not admissible as evidence, and we knew that before we looked at the answer.” That is a stranger and much better rule, and it is worth feeling with your hands.

The project does still run cases that sit on the seam — four of them, deliberately. They are labelled stress diagnostics, and the plan is explicit about their standing: “They report sensitivity and may disagree; they cannot excuse a blocking-fixture mismatch” (lines 295–296). Measuring how twitchy something is near a boundary is useful. Using that twitchiness as an excuse is not.

Two seconds, and what Windows does after them

About eight million cells is the blocking preview budget, not one simultaneous update. Windows watches the graphics card; if one piece of GPU work runs for roughly two seconds without finishing, it assumes the driver has hung, resets it, and kills whatever was running — including your browser tab. The charter turns that into an architectural rule: “Every pass is bounded (Windows' GPU watchdog resets dispatches that run ≈2 s), so bake-quality work is chunked across many dispatches by design” (§3.1).

So the ceiling is written into the code, well below where the operating system would intervene: 16,384 squads of 256 workers, or 4,194,304 cells in one dispatch (solver-gpu/src/submission.ts, lines 1–4). The blocking column preview budget is 160×160×320 = 8,192,000 cells (runner/src/phase5-protocol.ts, line 115), so it needs at least two ranges. The plate preview budget is 400×400×50 = 8,000,000 cells. These are morphology-shaped Phase 5 design and gate budgets, not a claim that either whole field is processed in one dispatch.

The larger numbers are targets with a different status. Detailed mode is about 30 million cells; the two bake shapes are 133,120,000 cells for a plate and 131,072,000 for a column — roughly 130 million. Detailed and bake are capability-reported design budgets, not Phase 5 acceptance criteria. Under the canonical device request, one bake field would exceed the requested storage binding limit, so bake is currently reported unsupported rather than partially allocated or silently shrunk. The adapter's aggregate 10 GB memory does not turn that target into an executed capability claim (docs/plans/phase-5-gpu-port.md, “Resolution and memory budgets” and “Out of scope”).

And then — this is the part that matters — every submitted piece is timed, and the project's own bound is far tighter than the watchdog's. Two rows below quote a p99: the number that 99 of every 100 samples come in under.

The gate's own checklist

Chapter 25 has already told the sabotage half of this story — the sixteen registered mutations, and why the ownership rule had to retreat from “fails exactly its owner” to “the observed failing set contains its owner.” What belongs here is the other half: the sixteen criteria those mutations are aimed at, because read as a list they are this chapter in checklist form. They run P5-WINDOWS-PROVENANCE through P5-PUBLICATION (runner/src/phase5-protocol.ts, lines 854–871), and they cover, one criterion apiece, the things the six sections above have been about: the recorded machine, the layout indexing, the frozen field and scalar tolerances, the exactness of the discrete decisions, the bounded dispatch, the audited readbacks.

One of them bears directly on the rule two sections back. If a tolerance may never vote on a yes-or-no, something has to stop the harness quietly deciding that a blown tolerance was close enough — so there is a mutation pointed at exactly that temptation: NC-TOLERANCE-BYPASS, which “report[s] pass while one blocking raw field, scalar, decision, or invariant comparison exceeds its frozen tolerance” (runner/src/phase5-protocol.ts, lines 952–957). That is the saboteur aimed at the tolerance machinery this chapter spent three sections building — and, as it happens, the one chapter 25 singled out, for the unrelated reason that it is the mutation two criteria legitimately notice.

On the canonical run, all sixteen criteria passed and “All sixteen negative controls were rejected with their registered owner in the observed failing set” (docs/plans/phase-5-gpu-port.md:1455–1456).

Still unsettled

Every review round in this project — including the three rounds that closed this phase, and including the two-reviewer process that checked this page — has been a review by a language model. The project is worked on “by multiple different LLMs across sessions, with no shared memory between them” (AGENTS.md, line 3), and its Rule 10 requires every review to record the reviewing model, what it independently re-executed, and what it did not check, “stated as a limit of the evidence rather than left implicit.” Reviews by a different model than the one that wrote the code have caught real seams. They are still not the same thing as review by a human domain scientist, and no human domain scientist has read this work. The project treats that as a disclosed limitation rather than a substitute, and so should you.

Winning the gate, losing the job

The phase closed. Exit code 0, sixteen criteria out of sixteen, three review rounds ending at zero blockers. Everything in this chapter worked.

And then the next phase — the one that finally points the model at nature — registered in writing that its big parameter sweep would run on the graphics card. The reasoning was that the processor runs were expensive, so the card must be necessary. Nobody had measured the card.

Somebody measured the card. Here is the correction, in the plan's own voice:

“From the cost figures alone this plan asserted the GPU was a prerequisite. A GPU calibration probe then measured the opposite: at 28³ to the same target the GPU took 32.9 s against the CPU oracle's ≈5 s, roughly 6× slower, because the CPU warm-starts and converges many steps in a single sweep while the GPU always submits a 16-sweep segment with a full queue sync. No size was measured at which the GPU wins. The original sentence was an extrapolation from one engine's cost with no measurement of the other, and that is exactly the reasoning this project is supposed to refuse.”

docs/plans/phase-6-nakaya-validation.md:296–302

Two words in there need unpacking. The bare word steps means interface steps — the plan spells it out where it repeats the finding later, “converges many interface steps in a single relaxation sweep” (same file, line 856) — and an interface step is one advance of the crystal's surface: work out the vapour field, move the ice a little, repeat. And warm-starting means beginning each of those from the answer you had last time rather than from scratch — which is most of why the processor gets there in five seconds. The card cannot do either cheaply. It commits to a fixed block of sweeps and then waits for the whole queue to drain before anyone is allowed to look.

Worse followed, and it turns on the distinction chapter 22 exists to teach. A fixed-supersaturation run counts as converged only when two independent things hold. The iterate residual — how much the field changed during a sweep — must be under relaxTol. And the divergence identity — |injection + drift − exchange| / |exchange|, the numerical bookkeeping check that the signed shell-clamp update, directly metered smoother drift and signed surface-boundary replacement balance during the final elliptic sweep — must be under divTol. It is not a physical uptake or deposited-ice identity; relaxation sweeps advance no physical time. The residual and divergence identity are two separate controls, registered on the fixture itself on consecutive lines: relaxTol: 1e-9 and divTol: 1e-7 (runner/src/phase5-protocol.ts, lines 345–346; the same pair is registered again for the Phase 6 runs at runner/src/phase6-crossplatform.ts, lines 82–83). Now look at the two numbers, because they are the wrong way round for the obvious story. The divergence bound is a hundred times looser — and it is still the one the card cannot reach. If the second check were merely a stricter version of the first, the looser number would be the easy one. It is not. It is a different question. Chapter 22 is the story of why (docs/decisions/0006-audited-surface-operator-numerics.md, Decision 1).

divTol = 1e-7 is relative — the imbalance as a proportion of the signed numerical surface-boundary exchange, not Hertz–Knudsen demand or uptake (docs/plans/phase-6-nakaya-validation.md:305 and 314–321) — and it is the one float32 cannot satisfy. In float32, the smallest gap between two representable numbers near 1.0 is 2−23 — about 1.19×10−7 (FLOAT32_EPSILON, runner/src/phase5-protocol.ts, lines 501–502). The requirement sits below a single rounding step of the arithmetic being asked to satisfy it. So the probe walked into a state with no way out: at 20³, 24³ and 28³ the relaxation residual was exactly 0 — a bit-stationary fixed point, where more sweeps provably cannot change anything — while the divergence residual sat at 1.0–1.6e-7 and the run was refused (lines 304–312). The plan's own correction note draws the conclusion, of that residual: “which is why the observed residuals cluster at 1.0–1.6e-7 and why no amount of extra sweeping helps. It is unreachable by construction, not by misfortune” (lines 314–324).

Two answers, already on the books

The bit-stationary trap above was not this project's first meeting with this shape of problem. Two decisions from earlier in Phase 5 — both dated 2026-07-24, both written before the Phase 6 sweep ever ran — had already drawn the line for the two different ways a float32 engine can fail to satisfy a criterion the float64 oracle satisfies exactly. They answer two different questions, because relaxTol and divTol fail in two different ways, and each got its own ADR rather than one shared, vaguer fix.

The first question is about the drift term itself — the same drift named in the divergence numerator above, injection + drift − exchange. It carries its own independent bound, separate from divTol, and that bound has to hold at whatever magnitude the field legitimately reaches — including a subnormal one, since the CPU oracle accepts finite supersaturation all the way down to one. Written as a pure fraction of the field's own size, the pre-shader expression was 64 * activeCellCount * 2−23 * maxAbsSweepInput (docs/decisions/0020-floor-phase5-float32-smoother-drift.md:13). Independent WP4 review found that it underflows conceptually on legal input, before any production shader existed to hit it: “For maxAbsSweepInput = 2−149, even 1,000 cells produce a bound below one minimum binary32 ULP” (same file, lines 19–20) — 2−149 being the smallest positive value float32 can represent at all, one step above zero. A purely relative bound shrinks exactly as fast as its own input; push the input small enough and the bound shrinks past the arithmetic's own floor, so a genuinely fine one-ULP drift could then read as a violation, or the bound itself could round to zero on the shader. Decision 0020's fix floors the expression instead of loosening it:

perCellRoundoffScale = max(2−23 * maxAbsSweepInput, 2−149)

smootherDriftAbsLimit = 64 * activeCellCount * perCellRoundoffScale

where
2−149
the smallest positive subnormal float32 value — the floor beneath which the relative term is not allowed to fall
exact zero field
special-cased to a zero bound and zero drift (same decision, point 2)

docs/decisions/0020-floor-phase5-float32-smoother-drift.md:39–40

The bound is still computed in host float64 from an independently reduced float32 maxAbsSweepInput, so the GPU shader itself never evaluates the product that could underflow (same file, lines 44–46). And the ADR says outright why the input domain could not simply be narrowed instead, which was the tempting alternative: “This is the same numerical-domain defect closed for the CPU float64 oracle by decision 0014… silently narrowing the GPU input domain would make the port less general than its oracle” (lines 23–25). Same habit as the tolerance-and-buffer pattern already seen twice in this chapter: the floor was derived and pinned by an adversarial subnormal test (line 47) before any production LK shader existed to need it.

The second question is about relaxTol, and it is stranger, because it is not about how small a bound can safely go. Decision 0020 assumes the arithmetic can still, in principle, get closer to a fixed point; it only needed a bound that would not underflow first. Decision 0021 is for when the arithmetic provably cannot get closer at all. A pre-WGSL feasibility probe had appeared to clear relaxTol for good: converge the float64 CPU oracle at each interface step, then round that already-converged field down to float32. That probe never carried an evolving float32 field from one interface step to the next — and the production D3D12 run did. In the frozen cold/noise/timeline fixture, by interface step 3, two interior cells stopped approaching anything at all:

“index 4419: 0.0018111496465280652 ↔ 0.001811149762943387
index 4743: 0.0017357079777866602 ↔ 0.0017357078613713384”

docs/decisions/0021-bound-phase5-float32-two-cycles.md:23–24

Each side of each pair sits exactly one float32 ULP — one unit in the last place, the smallest possible gap between two representable float32 values — from the other, and the orbit does not decay: “after 4,096 sweeps the active field repeats bit-for-bit every two sweeps” (same file, line 30). The reduced relative residual sits at 5.82076573607537e-8 and stays there — roughly 58× relaxTol's frozen 1e-9 — even though, this time, the other check is clean: “the divergence residual is exactly zero, shell injection and surface exchange are strictly positive, and the signed smoother drift is within its independent bound” (lines 27–29). It is the mirror of the bit-stationary case above: there, relaxTol was trivially satisfied and divTol failed; here, divTol is satisfied and relaxTol is the one that cannot be reached — both for the same underlying reason, that float32 ran out of representable room before the CPU's own criterion did.

Decision 0021 does not lower relaxTol. It opens a second, narrowly-shaped door, and every one of five predicates has to hold on the same sweep before it does: “at least two sweeps have executed under the current topology, tick, temperature, and far-field controls; every active unattached destination value bit-equals its value two sweeps earlier; every active unattached destination value is at most one ordered finite-f32 ULP from the immediately preceding value; both orbit phases pass the unchanged Dirichlet divergence criterion when fixed-sigma Dirichlet is applicable; reflecting mode makes no divergence claim; and both orbit phases pass the unchanged independently checked smoother-drift bound” (docs/decisions/0021-bound-phase5-float32-two-cycles.md:54–61) — that last clause is decision 0020's own bound, doing double duty as one of 0021's gates. Clear all five and the run is reported as bounded-two-cycle rather than fixed-point, with its true nonzero residual still printed: “it is never rewritten to zero or called a fixed point” (lines 63–64). And there is no slack in the substitute criterion either: “Exact period two is mandatory; no decimal residual threshold, longer period, multi-ULP cycle, or generic stagnation test is accepted” (lines 72–73). The one float32 buffer this needs, to remember the state from two sweeps back, is the buffer this chapter already mentioned: the reason LK's allocation rose from 60 to 64 bytes per cell (lines 74–75) was never just bookkeeping. It exists to hold the other half of the orbit.

The plan retracted its own registered claim in the same document that made it, and recorded two lessons rather than burying them: “an engine certified on one workload does not transfer to a different workload of different duration, and a plan sentence asserting one engine's necessity from the other engine's cost alone is not evidence” (lines 863–866). There is a third, quieter fact in the same passage: the sweep is made of independent runs, which are “embarrassingly parallel across 16 CPU cores while the Phase 5 protocol permits one process per physical adapter” (docs/plans/phase-6-nakaya-validation.md:866–868; the one-process rule is gpuProcessesPerPhysicalAdapter: 1, runner/src/phase5-protocol.ts, line 536). So the processor wins on throughput sixteen ways — “by arrangement rather than by clock.”

Key idea

“Faster” is never a property of a machine. It is a claim about a machine, a workload, a duration and a precision — and it is only true where somebody measured it. This project had certified the graphics-card path for four interface steps at 24×24×18. The sweep needed far more than four — the probe was already refusing at steps 11 to 47 (docs/plans/phase-6-nakaya-validation.md:309). That is a different claim, and it turned out to be a false one.

What exit 0 lets anyone say

The phase's canonical result is a single command exiting 0 — 0 being the code a program returns when it has nothing to complain about — at a named clean commit c436df57… (printed in full at docs/plans/phase-5-gpu-port.md:1449), under protocol version phase5-gpu-conformance-windows-v6 (runner/src/phase5-protocol.ts, line 15). That is the protocol v6 flagged in the first section, not the surface policy that carries the same number: what its v6 revision changed was “only the negative-control ownership rule” chapter 25 described (same file, lines 2–4). Alongside it: zero device losses, zero uncaptured GPU errors, zero hidden retries, zero stale generations, and zero full-field display-frame reads across 2,715 audited readbacks (docs/plans/phase-5-gpu-port.md:1453–1455). Those middle words carry weight. Copying a whole field back out of the card is allowed — for a checkpoint, for a test, for the published gate artifacts. What is forbidden is doing it in order to draw a picture: the app “may not copy a full field to JavaScript every display frame” (docs/plans/phase-5-gpu-port.md:113–115). All 2,715 readbacks were audited against that rule, and none of them broke it.

Read carefully what that entitles anybody to say. On one recorded Windows / Chromium / D3D12 machine, a float32 implementation of the same model reproduced the float64 implementation's results, within tolerances published before the shader existed, with the discrete decisions matching exactly and every safeguard demonstrably able to fail.

The words the same model now carry an asterisk, and it was pinned on after this phase closed. Phase 5 certified the graphics-card path under one named surface policy: aggregate-hv-g1h1-v5 — the gather-order summation of chapter 20 — which the plan writes into its scope (docs/plans/phase-5-gpu-port.md:50, and again at line 947: WP4 “implements only the forward aggregate-hv-g1h1-v5 policy”). Surface policy v6, ADR 0023's ascending-order fix, arrived later and was ported to the processor lane only. On the card, the opposing-vapour sum still accumulates in gather order (opposingSupersaturation, solver-gpu/src/lk-shaders.ts:640), and the entry points refuse any other policy by name: “GPU LK supports only aggregate-hv-g1h1-v5: the WGSL boundary kernel still sums the Eq. 5.35 opposing operands in gather order” (solver-gpu/src/lk-solver.ts:1512–1515). In ADR 0023's own words the shader defect is “registered, not repaired”.

That does not retract anything above it, and it is worth being exact about why not. Both engines were on the same policy when the gate ran: the plan names aggregate-hv-g1h1-v5 as Phase 5's solver truth, for the oracle as much as the shader, so the float32 run was compared against a float64 program computing the identical arithmetic — which is exactly the comparison the whole chapter has been about. And the sorted pass at the top of this chapter is the in-plane diffusion smoother, a different reduction that carried the pairing-and-sorting rule from the beginning and was never the defective one. The defect ADR 0023 found was in the surface operator, and it was found a phase later.

What it does mean is that the certificate names a policy as well as a machine, and that the card ended up excluded from the sweep for two independent reasons rather than one. “Winning the gate, losing the job” gave the first: at sweep durations the card is slower, and at the frozen divergence tolerance it cannot finish at all. ADR 0023 gives the second — the unported operator is “a second declared difference beside f32 arithmetic and the relaxed divergence tolerance: the GPU lane can corroborate a trend, and cannot be compared value-for-value against a v6 sweep.” A certificate that is honest about its own scope is what makes a sentence like that writable at all. An engine certified without one would simply have been assumed to transfer.

It does not say the model matches nature. The plan puts that boundary in its own scope section: “This is a numerical-portability and interactive-performance phase. It does not validate the physical model…” (lines 22–23). The charter states it as a standing rule: “‘The model was given real physics’ and ‘the model was shown to reproduce reality’ are different claims; only Phase 6 can promote the first to the second” (project charter.md, §3.3, “Standing guardrails”). It does not say the code runs correctly on a Mac: when the Mac was unreachable, “every Metal capability remained unobserved rather than guessed” and decision 0018 moved that work off this gate (docs/plans/phase-5-gpu-port.md:245–247), which the charter turns into a flat rule — “Untested backends carry no Phase 5 claim” (project charter.md, §3.1, line 223). And it does not even say the fast path is fit for a workload longer than the one it was certified on; the previous section is what that turned out to cost.

Phase 6 — the one that points the model at the Nakaya diagram — is in progress as this is written. Phase 7, the product, has not started. Nothing in this chapter is a result about snow.

How we know

So why spend a whole phase on it? Because of what it buys next. When the validation sweep returned its score, the obvious question followed at once: was that the physics, or was it the code? Chapter 28 has the number, and the several reasons it is not yet gate evidence. Every safeguard in this chapter — the frozen tolerances, the decision margins, the sixteen registered criteria, the bounded dispatch, the recorded provenance — exists to make those two answers separable. This phase did not make the sweep faster. It made the sweep's failures readable.

Which leaves one question standing. If you already suspect the answer might be disappointing, what stops you from quietly adjusting the exam after you have seen the marks? Chapter 27 is about writing the marking scheme down, publishing its fingerprint, and then — deliberately — waiting.
