Chapter 15

Two Labels on Every Number

How can a program honestly print −15 °C on screen and still refuse to say that this is what snowflakes do at −15 °C?

~16 min read 6 original interactives 0 borrowed figures

By the end you will be able to

  • Take any number a program shows you and say what it is, separately from what it has earned.
  • Explain why a single confidence score cannot answer three questions at once — and show that it cannot, rather than assert it.
  • Find the verb doing the smuggling in a sentence like “our physics-based simulator shows that…”
  • Argue that a blank space with a stated reason is a stronger interface than a plausible number.

The application at the centre of this project has a temperature control. You set it to −15 °C and a crystal grows. Nothing about that is dishonest: temperature is a real input to the equations the solver runs, in real degrees, and chapter 21 is about the machinery that made it one — its section “Where temperature stops being a label” is exactly that story. But there is a second sentence lurking right behind the first, and it is a completely different claim — that the crystal which comes out at −15 °C is what nature actually grows at −15 °C.

Every honest thing this project can say, and every dishonest thing it could have said, lives in the gap between those two sentences. This chapter is about the vocabulary built to keep them apart, and about the code that enforces the vocabulary when a person forgets. It is a short chapter with a lot of machinery in it, because the words are only worth anything if something checks them.

The ladder that broke

The project’s charter — the design document the rest of Part Two keeps quoting, written first and amended ever since — originally had a simpler idea. Every quantity on screen would carry a confidence level: a number from 1 to 4. Low numbers meant “don’t trust this much”; high numbers meant “this one is solid.” It is the design almost everybody reaches for first, and it lasted until somebody tried to use it on real readouts.

On 2026-07-14 it was thrown out. The reason is recorded in one sentence in the charter and again in the decision record that removed it. The four levels “conflated provenance, validation, and units (temperature input is not computed state; units do not imply validation)” (docs/decisions/0005-validation-scope-surface-operator-numerics.md:157–158). Three unrelated questions were wearing one hat:

  • Where did this number come from? Did you type it, did the solver compute it, or did somebody make it up?
  • Has anyone checked it against nature?
  • Does it carry a physical unit?

A single rung cannot answer all three, and you can prove that to yourself in about a minute. The demo below has five readouts from the real application, named as the application names them, with <live> wherever a live number would sit — a chapter about unearned digits has no business inventing any. One mentions d: a made-up bookkeeping quantity that the project’s older, simpler surface rule tracks instead of real supersaturation, and a section further down is about why the two must never be confused. Assign each readout a level from 1 to 4 so that the ladder means something. Three lamps score you, one for each of the three questions the old design was trying to answer at once.

The best any assignment can do is one lamp out of three, and one of the three can never be lit at all. That last failure is the interesting one. There are five genuinely different origins in that list and only four rungs, so two readouts must share a level — at which point the level has stopped saying where anything came from.

This is not a hypothetical. The fifth origin is ticks/s, the solver’s speed. It is a real measurement in real units, and it is not a statement about snowflakes at all; it is a statement about the computer. The shipped application prints the live rate followed by ticks/s (instrument performance, not a model quantity) (app/src/main.ts:599). A ladder has no rung for “this is not the kind of thing you are asking about.” Two independent labels do.

Key idea

A confidence score is a compression. If the things you compressed are independent, the score is not a summary — it is a place for one of them to hide.

Two axes, not one score

What replaced the ladder is deliberately less convenient. The charter’s rule is that “every quantity shown to the user carries two independent labels, and the UI never silently upgrades either” (project charter.md:78). The two labels are:

Type — “what the quantity is: input (the temperature slider), computed state (a vapor field value), derived metric (a hollowness index), or phenomenological parameter (a G–G threshold, a noise amplitude)” (project charter.md:81). “Phenomenological” is the honest word for a knob that changes the picture and means nothing physically — you tune it, and there is no quantity in nature it corresponds to.

Evidence — “what it has earned: unvalidated; qualitatively supported; or quantitatively validated over a named domain. Only Phase 6 can grant the third, and only where the comparison actually holds” (project charter.md:82). Phase 6 is the validation phase — the one that runs the model against measurements it could disagree with. It is in flight as this is written: a first sweep has run, was invalidated by a later decision record, and re-runs. Chapter 28 is where its result lives.

The whole force of the design is in the word independent. Knowing what a number is tells you nothing about whether anyone checked it. A temperature you typed in has never been checked against anything, and it is still a perfectly honest number. A dimensionless supersaturation computed by real physics has also never been checked, and it is also a perfectly honest number — it just must not be described as a result about the world.

Six readouts follow, all copied out of the running application. Give each one a Type and an Evidence. There is a trap in here, and it is worth naming in advance so you can watch yourself fall into it anyway: carrying a real physical unit is not evidence of anything.

Notice where everything landed. All four rows filled; two of the three columns stayed completely empty. Nothing this project displays sits in quantitatively validated, and the reason is not modesty — it is that the column has a precondition attached to it and the precondition has not been met. The application’s status panel ends, on every one of its three code paths, with the same line: all model quantities: Evidence = unvalidated (§1.5) (app/src/main.ts:573, :633, :678). The control pane it sits next to is titled GGThreshold dev instrument (model, unvalidated) (:1284) — GGThreshold being the name of that older, simpler surface rule.

The two sentences that must never merge

Here are the two sentences, in the charter’s own words, as a standing rule that binds every part of the project:

How we know

“No UI label ever claims more physical confidence than Phase 6 has earned. ‘The model was given real physics’ and ‘the model was shown to reproduce reality’ are different claims; only Phase 6 can promote the first to the second.” — project charter.md:340, one of the ten standing guardrails at :335–344.

The first sentence is about what went in: measured equations, a real temperature entering real mathematics. The second is about what came out: a comparison with the world that the model could have lost. Only a test can turn the first into the second, and only for the exact comparison that was tested.

Watch how easily they weld together. “Our physics-based simulator shows that at −15 °C snowflakes grow as plates.” The verb doing the smuggling is shows, and the adjective helping it is physics-based: the sentence uses a fact about the inputs to license a claim about the output. The honest rewrite splits it in two. The solver is given measured attachment kinetics and a real temperature. At −15 °C in the model, a plate grows. Whether that matches nature is a separate question, and this sentence does not answer it.

So what would it take to promote a label? Not an opinion. The demo below is the upgrade button, and it refuses.

Two things in that refusal are worth pulling out. First, an upgrade needs a named domain, not a general endorsement: a report about growth rates says nothing about pressure dependence, so five of the six rows stay grey even after it loads. Second, some rows can never be upgraded by a Nakaya comparison at all, no matter how well it goes, because some of the model’s inputs were chosen to make it agree with that diagram in the first place. That is the subject of chapter 17; here it is enough to see the refusal has more than one reason in it.

The most convincing fake available

Now the part that is genuinely counter-intuitive. If your model has not been checked, which readout should it print when you hover over a patch of the crystal’s surface?

The charter’s own worked example, verbatim from project charter.md:87.
ReadoutStatusWhat a reader concludes
attachment rate: 91% banned …that somebody measured this.
high relative attachment tendency allowed …that the model has an opinion.

The instinct is that the first one is more scientific, because it is more specific. The charter says the opposite, and says why in a clause worth memorising: “a fake physics readout is worse than none — and a real-looking number resting on an untested model is the most convincing fake of all” (project charter.md:87). Precision is not a property of a number. It is a claim about how well the quantity is known, and every digit you print is another unit of that claim. Print digits you have not earned and you have lied in a format that is very hard to argue with.

uclaimed = ½ × 10−n

where
uclaimed
the uncertainty a reader is entitled to assume when you print a number — half a unit in the last place you printed
n
the number of decimal places actually printed

Standard reading convention, not a project result. It applies to a bare numeral; a number printed with its own ± band states its uncertainty outright instead. The band it is compared against below is the real one: docs/libbrecht-parameters.md:246.

The demo below uses a genuine number from the project’s frozen parameter table: σ0 for the basal facet at −2 °C, recorded as 0.0035 (docs/libbrecht-parameters.md:255). That value was read off a plot, because neither of the source documents prints the formula or a table — a gap the project wrote down rather than papered over. Its stated uncertainty is “±25% relative on σ0 (log-scale reading)” (docs/libbrecht-parameters.md:246). Where that number came from, and why reading it off a graph is legitimate when you say so, is chapter 16’s subject. Here we only care what happens when you print it.

Careful

“Vague wording means the authors are hedging.” Sometimes. But a vague phrase over an untested model is a correctly sized claim, and a four-decimal number over the same model is an oversized one. The register the writing is in should match the evidence, not the confidence of the writer.

What the interface refuses to say

Disclaimers are cheap. The convincing evidence that a labelling rule is real is what the program declines to print — because a blank space is the single hardest thing to ship and the single easiest thing to fill with something plausible.

The application can run its solver on the CPU or on the graphics card. Two of its readouts, the aspect ratio and the symmetry error, are full-field metrics: computing them means looking at every cell in the grid. The GPU deliberately keeps the field on the GPU, so those numbers are not available without dragging millions of cells back across the link between the graphics card and the rest of the computer, every frame. The panel does not estimate them. It prints, in place of the numbers:

aspect ratio: not computed in GPU mode (full-field metric) · symmetry error: not computed in GPU mode (full-field metric) (app/src/main.ts:605–606).

The same refusal appears in the depletion readout, with its reason spelled out in a code comment rather than left to be inferred: “the depletion HUD needs the full vapor field, and GPU snapshots carry compact counters/probes only — the panel says so instead of faking values” (app/src/main.ts:829–831). Three more refusals sit alongside it:

  • Speed is tagged as belonging to the machine, not the model: (instrument performance, not a model quantity) (app/src/main.ts:599, :650).
  • A missing measurement is written out loud. The number formatter renders any non-finite value as the literal string undefined (NaN) (app/src/main.ts:807) — not as a dash, not as zero, not as the last good value.
  • Even the renderer disowns itself: rendering backend: … (this page; not the evidence backend) (app/src/main.ts:566), so nobody mistakes what drew the picture for what produced the result.

None of that is decoration. Zero is a number a reader will believe. “Not computed” is not.

Why d is not sigma

Here is where the discipline stops being a writing style and becomes code that throws.

The project carries two different surface rules through the same machinery, on purpose and permanently — “GGThreshold — the working floor is never deleted” (project charter.md:336) — so that a problem in the physics can be told apart from a problem in the machinery. One of them, the Gravner–Griffeath threshold rule, tracks an invented quantity called vapor mass, written d, in units that exist only inside the model. The other, the Libbrecht kinetics rule, tracks real dimensionless supersaturation relative to ice, written sigma — the quantity Part One spent a chapter on. On screen they are indistinguishable: both are one number per cell that you can colour blue.

The comment at the top of the display module states the hazard flatly:

How we know

“The two permanent surface operators expose UNRELATED state that must never be relabeled as each other… f is NOT a reuse of G-G boundary mass b, and sigma is NOT d in different clothes.” — app/src/display.ts:3–9. The enforcement is one function down the file: “assertFieldSemanticsHonest rejects any operator/field-name combination that would show one operator’s state under the other’s label” (:11–13).

Think about what a mislabel would buy you. A phenomenological number — a made-up quantity in made-up units — would appear on screen wearing a physical name. Nothing would look wrong. The picture would be identical. That is exactly the failure mode the project exists to refuse, so it is not left to whoever is editing the file that afternoon. Try it.

Look at what the honest labels contain when you find one. Neither of them is just a name. The G–G field reads model units (computed state, unvalidated); the Libbrecht field reads dimensionless, relative to ice (computed state, unvalidated) (app/src/display.ts:33, :43). The Type and the Evidence are baked into the string, and the function checks the wording too — changing the text at all produces display labels drifted from the honest fixed wording. You cannot soften the label without failing the check.

A badge you cannot take off

One more, because it is the case where a real integrity failure was caught and the fix was not “be careful.”

The application can load a saved crystal and inspect it. Those saved files come in two kinds: real published evidence produced by a gate run, and synthetic fixtures — made-up files that exist so the tests have something to chew on. A review round found the harness cheerfully treating the second as the first: “the repository’s explicit synthetic NOT-gate-evidence fixtures passed the visual verifier, which then displayed and recorded them as published Pass A/B evidence” (docs/plans/phase-4-morphology-gauntlet.md:899–904). Everything about those fixtures was internally consistent. That was the problem.

Two words are about to do a lot of work, so here they are first. A hash is a short fingerprint computed from the exact bytes of a file — change one byte anywhere and the fingerprint changes completely, so a fingerprint written down earlier is a way of naming one specific file and no other. The ones below are 64 hexadecimal characters long and are usually shown truncated. A manifest is the list of those fingerprints for everything a run produced, so that “the manifest hash” names a whole run’s output the way a hash names a single file.

The fix made the evidence class an explicit field with its own type, alongside a required notice string:

The evidence-class fields, from app/src/inspect.ts:54–60.
FieldAllowed values
evidenceClass "published-gate-evidence" | "synthetic-fixture-not-gate-evidence"
syntheticNotice "SYNTHETIC FIXTURE - NOT GATE EVIDENCE" (optional)

The obvious attack is to delete the notice. Try it, and then try the less obvious one.

The shape of that is the lesson, and it is worth being exact about what each half buys, because they are not the same kind of safeguard. Removing the badge is closed outright. The class is a separate field, and a context that classifies itself as synthetic without carrying the exact string SYNTHETIC FIXTURE - NOT GATE EVIDENCE is rejected (app/src/inspect.ts:292–295). There is no path through by omission.

Lying about the class is closed differently, and more weakly. A context claiming published-gate-evidence must pin the frozen Pass A manifest hash and must carry no synthetic notice at all (:283–287). But that hash is a constant sitting in the source, and the field is supplied by the file being loaded, so a hand-written context can simply contain it. This check cannot make the lie impossible, and it would be exactly the wrong chapter in which to pretend otherwise. What it does is force the lie to be explicit: the forger has to write down a specific manifest hash and a specific run identifier, in named fields, which then travel with the artifact into the screenshot manifest, and which anyone can compare against the manifest hash actually recorded in the published gate report (out/phase4/gate4-report.json, field passA.manifestSha256). A vague badge cannot be contradicted by evidence. A pinned hash can.

Key idea

Every safeguard in this chapter has the same shape: the honest thing is the default, and the dishonest thing requires an explicit lie in a field somebody else checks. That is the difference between a policy and a mechanism.

Who has actually checked any of this

A chapter about honest labelling owes you its own labels, so here they are.

This project has been reviewed constantly — the evidence-class failure above was found by a review round, not by a test — and every one of those reviews has been conducted by a language model. So has the two-reviewer process that checked this page. The project’s own sharing rules say so in writing, and treat it as a limitation to declare rather than a box that has been ticked: “All reviews to date, internal and external-facing, are LLM reviews; for publication that is a disclosed limitation, not a substitute” (docs/stretch-sharing-and-investigation.md:217–219). The same passage requires that at least one human domain scientist read any manuscript before submission. No human snow-crystal scientist has reviewed any of it.

That matters more here than almost anywhere, because the failure mode of a machine reviewer is the failure mode this whole chapter is about: fluent, plausible, internally consistent output that nobody has compared against the world. The vocabulary in this chapter does not fix that. It does something narrower and still useful — it makes the gap sayable, so it can be stated in the same sentence as the result rather than discovered afterwards.

Still unsettled

Nothing in this system can force a label to be true. It can force a label to be consistent, and it can refuse an upgrade that has no artifact behind it. Whether the four Types are the right four, and whether three Evidence tiers are enough for a project that will eventually have partial agreements, are both open. The set was fixed in a single decision record on a single day, and two of the three Evidence tiers have never been used: the strings qualitatively supported and quantitatively validated appear nowhere in the application’s source.

There is one more thing the labels cannot do on their own. “Evidence: unvalidated” tells you nobody has checked a number against nature. It does not tell you whether the number was measured in a laboratory, fitted through a curve, chosen to make a picture come out right, or invented because the grid needed a spacing. Those are wildly different situations wearing one label, and the project needed a second vocabulary for them.

Which is chapter 16’s question: where did each of these numbers actually come from, and what changes when one of them turns out to have been chosen so that the answer would come out right?
