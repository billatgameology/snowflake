Chapter 18

Never Physics Ahead of the Machinery

Why can’t you just build the interesting part first?

~16 min read 2 diagrams 3 interactives

By the end you will be able to

  • Explain why isolating a variable in software means proving the floor before you put anything interesting on it.
  • Read a phase gate and say whether it could be closed by argument rather than by measurement.
  • Say why a prototype’s job can be to answer one question and then die.
  • Explain why a written record is load-bearing, not decorative, when nobody remembers yesterday.

Eight phases, nine rungs

Two bugs wearing one coat is a vivid way to lose a week. Avoiding it is, in the end, a scheduling decision — and this project made that decision structural. The work is a ladder. Its governing document, project charter.md, lists phases numbered 0 to 7 in section 3.2, and that section’s opening paragraph closes on one short sentence: “Each milestone has a done when.” A “done when” is a written sentence, fixed before the work starts, saying what would count as finishing. Not a feeling. Not “when it looks right”. A sentence.

There are eight numbered phases but nine rungs, because Phase 2 was cut in half before it was built. On 2026-07-14, numbered decision 0003 split it into Phase 2a — the machinery — and Phase 2b — the physics. Why that particular cut was made is the whole subject of this chapter.

The “done when” is not just written down; it is copied. Rule 2 of the project’s working rules says so directly:

“Any work beyond a trivial fix gets a plan file first, committed before implementation starts. A plan is: the goal, the approach, the steps, the ‘done when’, and the things deliberately not done. Charter phases already state their own done when — copy it into the plan verbatim and do not quietly soften it.”
snowflake repository, AGENTS.md — Rule 2, lines 290–293

“Committed” there is the version-control sense, and it is worth a sentence because a number later in this chapter is measured in these units. The project’s files live in git, which keeps their history as a chain of snapshots; each snapshot is a commit. Committing the plan first puts the finish line into that chain before any result exists to shape it. Chapter 27 needs a sharper version of that — how a commit gets its name, and why a place in the chain cannot be back-dated — and builds one. The chain is enough here.

The template every plan file starts from repeats the instruction and then says what to do with the temptation: “Copy the charter’s ‘done when’ for this milestone verbatim. If the charter has none, write one as a metric with a threshold, not as a feeling. If you are tempted to soften this, write an ADR instead.” (docs/plans/_TEMPLATE.md, lines 14–16). An ADR — an Architecture Decision Record — is a numbered, public file explaining why something changed. The rule does not forbid moving the finish line. It forbids moving it quietly.

Key idea

A finish line you write after you have seen the result is not a finish line. It is a description of the result.

One word needs pinning down before the table, because the rest of Part Two leans on it hard. A gate is a written pass/fail condition, fixed before the work starts, that a phase has to meet before its results are allowed to count as evidence. From Phase 2a onward every one of them is an automated metric: a threshold registered in advance, a measured value set against it, and a command anyone can re-run. That is the whole definition. Later chapters shorten it — chapter 22 needs it in half a line — but shortening is not redefining, and that sentence is what they mean.

Chapter 14 introduced a gate as a check that blocks a phase from starting until the previous one has met it. That is what a gate usually does, and it is a fair picture of the ordinary case, but it is not the rule — and two things about the table below will look like the project breaking its own rule if you hold on to it. The load-bearing word is counting, not starting. Take the two departures in turn.

First, Phases 0 and 1 have no metric underneath them at all. Their gates are still written pass/fail conditions fixed before the work started — five things you have to be able to do; one question you have to be able to answer with evidence — but no program can test either, so the maker’s word is the evidence, and the table says so on its own face instead of dressing those rows up as measurements. That is a labelled exception, not a lapse, and the section “Two rungs no computer can check” below is entirely about it — including the part where the protocol that was supposed to supply Phase 1’s evidence was not run.

Second, the dates at the end of this chapter show rungs closing out of order: Phase 4’s gate closed on 2026-07-18, before Phase 2b’s and Phase 3’s, each time under a numbered written exception. So an unmet gate did not stop the next phase from starting. What it always stops is that phase’s own results from being cited as evidence.

Below is that table’s own content: the gate for each rung, and its recorded status. The sentence introducing that table in docs/PROGRESS.md (line 594) states the standard it enforces: “A gate flips to ✓ only with a named metric, its value, and the seed/resolution/command to reproduce it.” A seed here is the single number the program’s random-number generator starts from. Same seed, same random choices, same run — it is what lets a stranger get your exact result rather than a similar one. It is not the ice seed of Part One — same word, different thing. Read the gates and ask, of each one, whether you could talk your way past it.

Never physics ahead of the machinery

Section 3.3 of the charter is a short list of standing guardrails — rules that apply to every phase rather than to one. This is the one that decides the order of the ladder:

“Never physics ahead of the machinery. Phase 2a is gated before any Libbrecht equation is written, exactly as the CPU oracle is gated before any WGSL is written. A physics bug on top of an unproven lattice is two bugs wearing one coat.”
snowflake repository, project charter.md — §3.3, standing guardrails (line 337)

Unpack the vocabulary. The machinery is everything that is not the attachment physics: the grid the crystal lives on, the arithmetic that finds a cell’s neighbours, the vapour-transport step, and the measuring tools that turn a shape into a number. The lattice is that grid. The CPU oracle is the slow, readable version of the solver, written in plain TypeScript, which exists to be understood rather than to be fast. WGSL is the shading language the fast graphics-card version is written in.

One honest wrinkle in that list. The repository does not classify vapour diffusion the same way twice. Numbered decision 0003 files “the quasi-static vapor diffusion step and its reflecting boundary” in a list introduced as “this is infrastructure, not physics” (docs/decisions/0003-libbrecht-attachment-kinetics.md, lines 40 and 44). The specification the solver is written against opens by saying the opposite: “Diffusion is physical transport; G-G’s surface knobs are phenomenological.” (docs/gg-machinery.md, line 4). The guardrail itself only ever names one boundary — Libbrecht’s equations on one side, everything the lattice needs in order to run at all on the other — so that is the boundary this chapter uses. The disagreement is flagged here rather than quietly settled, for a reason that arrives later in this chapter, in the section on which document wins.

The rule is invoked in exactly two places on the ladder. Once at the 2a→2b boundary, where the charter repeats it in Phase 2’s own text: “The governing rule is the same one that governs the GPU port: never physics ahead of the machinery. Phase 2a must stand on its own and be gated before any Libbrecht equation is written” (project charter.md, line 245). And once at the oracle→GPU boundary, where §3.1 puts it in a form that will be familiar to anyone who has debugged anything: “Debugging physics in WGSL is miserable; debugging it in inspectable TypeScript is merely hard. Never port ahead of the oracle.” (line 221).

This is not a style preference. It is the ordinary scientific instruction to isolate your variables, applied to software. If you change two things and the answer goes wrong, you have learned nothing about either. Below, you can try to break it.

What the rule actually buys

Here is the concrete pay-off. Phase 2a builds the grid and the diffusion and the measuring tools, and runs them using somebody else’s published rule for when a cell turns to ice — Gravner and Griffeath’s threshold rule, with their numbers exactly as printed. No new physics is invented at that rung. The gate is a number: a stable, sixfold-symmetric hexagonal plate, “verified by an automated symmetry check — not by eyeballing” (project charter.md, line 253).

Then — and this is the part that surprises people — that borrowed rule is never deleted. §3.3 promises permanence to the CPU oracle, and then extends the same promise sideways: “So does GGThreshold — the working floor is never deleted, for the same reason the oracle is never deleted.” (line 336). GGThreshold is just the code’s name for that borrowed Gravner–Griffeath rule, and “the working floor” is the guaranteed-decent crystal it produces — the thing that still works when the new physics does not. The charter names its purpose in Phase 2b’s text: the threshold rule is “the working floor and the differential diagnosis when the physics misbehaves” (line 262). It is a control. When the new physics produces a bad crystal, you can swap the surface rule back to the known-good one, on the same lattice, and see whether the badness follows the rule or stays with the machinery.

You cannot do that if the machinery was never proved. Try both situations.

The right-hand session is not a caricature. The charter says the failure mode out loud in Phase 2a’s own bullet list, as the reason for dumping raw field images from day one: “A malformed crystal can look plausibly organic; a malformed field is obvious immediately.” (line 254). Your eye is not a detector. It is a very good pattern matcher, and a wrong snowflake is still a pattern.

How we know

The Phase 2a gate entry in docs/PROGRESS.md (line 610) records: plate, seed 1, dims 128,128,64; a delta check — the same sixfold-symmetry test, applied every single tick to just the handful of cells that newly froze on that tick — clean across all 4800 ticks; the full symmetry metric 0 everywhere it was sampled; aspect ratio 0.168831; and total mass drifting by 2.056e-13 over the run.

Those first two are one criterion at two granularities, not two unrelated checks, and the cheap one is not decoration. core/src/metrics.ts gives the arithmetic reason it works: if the crystal is sixfold now and every tick’s set of new attachments is sixfold, then it is still sixfold next tick — and checking only the new cells is cheap enough to make “symmetry error exactly 0 across the entire run” affordable (lines 85–89). The plan file gives the reason it is load-bearing: a break can heal before the next full sample lands, so “a periodic full metric alone can miss a break, which is why the gate also runs the exact per-tick delta check” (docs/plans/phase-2-cpu-solver.md, lines 903–904).

Three numbers are tangled up in that last item, and they measure three different things. 2.056e-13 is the measurement made on the gate run. The threshold it had to beat is a separate number in the plan file — “total mass conserved to < 1e-10 relative over 10 000 ticks” (docs/plans/phase-2-cpu-solver.md, lines 403–404) — and it beats it comfortably. The “float floor” of 3.8e-16 printed beside it is a third thing again: a separate crystal-free control run, measuring how much the arithmetic drifts with no crystal in the box at all. The measured drift sits about five hundred times above that floor, and the plan records why that is expected rather than alarming — it is “consistent with per-tick freeze/melt/attach float shuffling rather than a leak” (lines 391–392).

The reproduction is a single command, and the entry says what the claim is: “Enforcing repro (exit 0 is the claim, twelve criteria)” — the command tests twelve separate conditions and reports success, by exiting with the status code 0, only if every one of them holds. And the accepted checkpoint — the saved file holding the crystal and its fields at the end of a run — carries its SHA-256: f1796b5015…a389. That is a fingerprint computed from the file’s bytes, so a changed file gets a different fingerprint, and finding two different files that share one is a problem nobody has ever solved for SHA-256.

Two rungs no computer can check

Phase 0 produces no software at all. Its charter entry reads: “Phase 0 — Ground truth (reading, no project code). Work through §2.8. Done when the exit criteria at the end of §2.8 hold. Timebox it (2–3 focused weeks); the monograph is a reference, not a gate.” (lines 239–240). The timebox matters: without it, “more reading” becomes a comfortable way of not starting.

The exit criteria are unusually concrete for a reading list. They are not “read these five things”; they are five things you must be able to do:

“Exit criteria for the reading phase. You can: sketch the Nakaya diagram from memory; explain why a cubic lattice can never work; write the Gravner–Griffeath update loop as pseudocode; explain hollowing without reference to any hollowing rule; and state cleanly which parts of the model are physics and which are phenomenology.”
snowflake repository, project charter.md — §2.8 (line 197)

No program can test that. And the project says so rather than inventing a number that looks like it did. From the phase-gate section of docs/PROGRESS.md, lines 597–604: “Phases 0 and 1 are the two exceptions, by nature. … No metric can test those; the maker is the only valid evidence source, and the maker asserted them on 2026-07-14. … Every scientific gate — Phase 2a onward — is an automated metric, no exceptions.”

Phase 1 is the other honest gate, and it is the one that teaches what a prototype is for. The charter budgets it at about a weekend and then, in the same breath, sentences it to death:

“Phase 1 — UX spike (2D, throwaway, ~a weekend). … Done when you can answer ‘does designing a cloud journey feel engaging?’ with evidence. The code is then archived, not extended — it must not quietly become the architecture.”
snowflake repository, project charter.md — §3.2, lines 242–243

The spike answers a design question — is this fun to use? — which has nothing to do with whether the physics works, and can therefore be answered years earlier and far more cheaply. Then it dies. “The 2D spike stays throwaway” is a standing guardrail (§3.3, line 336), and the reason is in the phase text: a piece of weekend code that survives contact with the real project stops being a prototype and becomes, silently, the foundation.

What makes Phase 1 worth a paragraph in a chapter about integrity is how its gate was actually closed. The plan file records it against its own standard:

“Honest labeling per this plan’s own gate standard: this is informal positive evidence (‘works well’, compare mode legible), not the protocol’s four tasks, and the gate question — does designing a cloud journey feel engaging? — has not been formally answered.”
snowflake repository, docs/plans/phase-1-ux-spike.md — lines 425–428

A four-task play-test protocol had been written in advance. It was not run. The gate was closed anyway, on the maker’s explicit assertion — and the plan file leaves the four empty task headings sitting there in the document, under a paragraph explaining that they are empty. That is a worse-looking record than a clean one, and a better one.

Careful

Several later rows in the gate table also say “maker-asserted”. That is not the same thing. On Phases 0 and 1 the maker’s word is the evidence; from Phase 2a on, the assertion sits on top of a metric, a threshold and a command anyone can re-run. The point is that the two classes are labelled differently and visibly. A project that quietly rounded “the maker says so” up to “verified” would look stronger on the page and be worth less.

A metric, not a screenshot

The standard itself was quoted at the top of this chapter: a named metric, its value, and the seed, resolution and command to reproduce it. Rule 6 of AGENTS.md is where that standard lives in the working rules, and it opens by compressing the charter to “automated metrics, not screenshots” (line 329). Then it adds two further bullets, and they are the ones that bite.

“‘Looks right’ is not a result. If you eyeballed it, write that you eyeballed it.
Every number written into PROGRESS.md or a plan is copied from a named artifact at write time, with that artifact’s path or hash beside it — never quoted from memory or an earlier prose mention.…”
snowflake repository, AGENTS.md — Rule 6, third and fourth bullets, lines 335–340

Note what the first of those does not say. It does not ban looking at things. Phase 3 — the phase whose whole purpose is a 3D viewer — kept its visual half; the gate entry records that app captures were inspected by a coordinator and a reviewer — both, like every reviewer on this project, language models; see the note below on what that is and is not worth. What the rule bans is looking at something and then calling the looking a measurement. The charter amended Phase 3’s gate specifically to make this stick: “the visualization stays, the eyeball stops being the evidence” (line 281).

The second of those two is why this page looks the way it does. Every number you have read here carries a file and a line beside it, because in this repository a number recalled from memory — or copied out of an earlier sentence of prose — does not count as copied at all. The rule was not written in the abstract. It ends by counting the damage: “at least three review rounds have been spent entirely on stale prose quotes” (line 339).

Four claimed results follow. Three of them fail the standard. Decide before you read the project’s own verdict.

The fourth claim is what a passing gate entry looks like in this repository: a named metric, its value, the threshold it was registered against, the seed, the grid, the exact command, and the hash of the checkpoint the numbers were read out of. That command is flagless — it has no options typed after it. A flag is an option you type after a command name to change what it does, so a flagless command is one whose settings are fixed in the code rather than chosen fresh at the prompt each time. The rulebook gives the reason in one clause: gate2b “is flagless because it encodes the pre-registered protocol” (AGENTS.md, line 246). Every field is there so that a stranger — including a hostile one — can re-run it and get the same answer, or fail to and say so.

Still unsettled

One limitation applies to every review in this project, and it applies to this page too. The project’s own sharing document states it flatly: “All reviews to date, internal and external-facing, are LLM reviews; for publication that is a disclosed limitation, not a substitute.” (docs/stretch-sharing-and-investigation.md, lines 217–219). Every gate you have read about was reviewed by a language model. So was this chapter, by two of them. No human domain scientist has read a word of it. That is written down here for the same reason the four empty task headings were left in the Phase 1 plan.

Written for a crew with no memory

There is a reason all of this lives in files rather than in somebody’s head. It is the first sentence of AGENTS.md, and it is not about snowflakes at all:

“This project is worked on by multiple different LLMs across sessions, with no shared memory between them. Any model may pick up work another left mid-flight. The markdown files described here are the authoritative handoff index; logs, checkpoints, and other artifacts are evidence only when the handoff points to them. Treat the handoff as part of the deliverable, not as bookkeeping.”
snowflake repository, AGENTS.md — the opening paragraph, lines 3–7

Picture a group project where every member is replaced by a competent stranger every single day. Nobody remembers yesterday’s argument, or which approach already failed, or what the half-finished file on the desk was for. In that situation a document is not paperwork about the work. It is the only channel that exists. Rule 2 makes the consequence explicit: “If the user approves a plan in chat, write it to the file anyway. The next model cannot read this conversation.” (lines 295–296).

Two rules follow directly from that constraint. Rule 4 requires every plan file to end with a Tried and rejected section — a list of dead ends — because “a model that doesn’t know the last one already tried X will try X” (lines 309–310). The plan template calls that section “the most valuable section in the file” and insists it be appended as you go, “not a retrospective written at the end”. Rule 8 requires every session to end by leaving a landing spot: the next concrete action, the file to open, the command to run, and any trap already known, “written for someone with no memory of today — because that is exactly who reads it” (lines 370–373).

And because six different kinds of document now exist, they are ranked. The table below is the project’s answer to “which one wins when two of them disagree?”

The bottom row is the interesting one. Its entry in the authority table reads: “Code, tests, logs, checkpoints | Implementation and evidence. They do not silently overrule the written contract.” (line 57). Code is what the project did; the charter is what the project agreed to do. When they disagree, the disagreement is the finding. The next sentence in the file forbids the tidy way out: “If any two disagree, state the disagreement explicitly and fix it at the proper authority level; never choose one silently.” (lines 59–60).

That is why the wrinkle about vapour diffusion earlier in this chapter was flagged and left standing rather than tidied away. A numbered decision and a solver spec sit at different levels of that table, they classify the same step differently, and picking one silently is the exact move the rule forbids. Saying so out loud costs a paragraph. Choosing quietly would have cost the reader the ability to check.

Where the ladder is allowed to bend

Go back to the gate table and read the dates. Phase 4 closed on 2026-07-18. Phase 2b closed two days later, on 2026-07-20. Phase 3 closed on 2026-07-23, after both. The rungs did not close in order.

That is not the ladder being ignored; it is the ladder being bent on the record. The opening paragraph of §3.2 sets the default in one sentence, and then spends the rest of itself on the exceptions to it:

“Phases 1 and 2 can run in parallel; everything else is sequential except where an accepted, maker-directed ADR records narrower independence.”
snowflake repository, project charter.md — §3.2, opening paragraph (line 237), first sentence of five

Three exceptions have been granted so far, and none of them is a shrug. The first let Phase 3’s development viewer finish without waiting for Phase 2b: the viewer draws whatever the solver hands it, so what it draws does not depend on which surface rule is running underneath. The second let Phase 4 start while Phase 3 was still waiting on an outside assertion — a sign-off the phase could not generate for itself — and while Phase 2b’s evidence run was still going. It came with three conditions and an end date. The other phase’s processes and artifacts are immutable; no claim may be borrowed from them; any correction upstream must be folded in and the run repeated before Phase 4’s evidence counts; and “the exception ends with Phase 4”. The third is not about order at all. Phase 4 had begun in an isolated worktree — a second working copy of the repository, kept apart from the main one — and when that copy was folded back in, the exception permitted Phase 4’s second evidence run — the v2 run the gate table’s 2026-07-18 entry cites — “only on main in the current Windows repository while preserving every isolation constraint on the separate Phase 2b process and evidence”. It moved where the work was allowed to happen, not when. After all three, the paragraph ends on the sentence this chapter opened with: “Each milestone has a done when.”

The three, in order: decisions 0007 and 0008; decision 0010; decision 0012 — all named in project charter.md §3.2, line 237, which is also where the quoted fragments come from.

Three exceptions, one shape. Each is numbered, so a stranger can go and read the argument rather than take the outcome on trust. Each states its boundaries — what may not be borrowed, what must be re-run, what stays walled off. And one of the three states its own expiry, in six words: the exception ends with Phase 4. An exception with no end date is not an exception; it is a quiet amendment.

It would be a poor advertisement for all this to pretend it is free. The rulebook closes with a set of anti-rules — things not to do — and the last of them tells you not to build fresh evidence machinery for every new piece of work (“Reuse the existing verifier seams; a new seam is justified only by a new attack surface”), then attaches a measurement of what the machinery has already cost:

“Integrity has a budget: ceremony ran ~15% of all commits and evidence-hardening ~45% of all rework through Phase 5, with visibly declining yield after WP5.”
snowflake repository, AGENTS.md — the last anti-rule, lines 426–428

Three of those words are the project’s own shorthand. Commits are the history’s snapshots, from the top of this chapter, so “~15% of all commits” says roughly one saved step in seven carried process rather than progress: a plan file, a decision record, a freeze. Rework is effort spent redoing work already done — a run re-executed, an evidence bundle rebuilt, a gate closed a second time. WP5 is work package 5: each phase’s plan is cut into numbered work packages, and in both Phase 5 and Phase 6 the one numbered 5 is the evidence package — run the registered command at one clean commit, authenticate the artifacts, and get an independent reviewer to sign them off. The WP5 in that sentence is Phase 5’s, which is closed. Chapters 28 and 29 need the same abbreviation for Phase 6’s, which has not run, and that is why the current Phase 6 numbers are not yet gate evidence.

So the measurement reads: nearly half the rework went on hardening evidence rather than on producing new results, and past the point where the verification machinery existed, building more of it visibly bought less. Whether that price is worth paying is a live question, and the project logs it as one rather than settling it.

Key idea

The ladder is a machine for making a failure meaningful. If the rungs below are closed with metrics, then a wrong answer at the top is evidence about the physics rather than about the plumbing underneath it. If they are not, a wrong answer is just a wrong answer, and nobody — including you — can say which part of it was wrong.

The bottom of the ladder is a grid, and the very first thing Phase 2a had to prove was that the grid itself was not lying. The next chapter asks why that grid gives every cell six neighbours meeting at 60 degrees, plus one directly above and one directly below — all eight the same distance away — when the obvious cube of cubes gives six meeting at right angles, which turns out to be a physics argument about a data structure.
