Chapter 22

When the Numbers Stop Changing

Chapter 21 left a run that had stopped moving and still did not balance. Long before that, this program printed converged over a field that was wrong — and the error was worse on the bigger runs. How do you catch a bug that only shows up when the job gets expensive?

~17 min read 7 figures 5 interactive, 1 animation

By the end you will be able to

  • Explain why “the numbers stopped changing” is not proof that the numbers are right.
  • Recognise the nastiest class of bug — one that gets worse as the problem gets bigger, so the cheap tests are exactly the ones that look fine.
  • Say why an independent physical check beats a tighter tolerance.
  • Explain how a model can test whether its own core assumption still holds, and why the answer gets reported rather than tuned away.
  • Describe graded validation severity, and why a rule that rejects your own source's published data is the wrong rule.

Thousands of sweeps, one growth step

Why does this program solve the same vapour field thousands of times before the crystal moves at all?

Because water vapour rearranges itself enormously faster than ice advances. So the solver does not push the vapour forward in time. Between growth steps it freezes the crystal's shape, and then iterates the vapour field until it stops changing — the steady state for that shape. Only then does the surface advance a little, and the whole field is re-solved for the new shape. That is what quasi-static means: a fast thing treated as always sitting at its equilibrium relative to a slow thing.

One pass of “replace every cell by a weighted average of itself and its neighbours” is called a sweep. It takes a lot of them. The project's own specification once got this wrong in an interesting way. An earlier version of docs/attachment-kinetics.md assigned a physical time increment to each sweep and derived an iteration count from it. Section 4.3 now opens by killing that idea and saying why:

“That mixed two different models — transient diffusion (stability timesteps, physical substeps) and quasi-static diffusion (an elliptic solve to a residual tolerance) — and produced a wrong test: relaxation counts scale like (L/Δx)², so thousands of Jacobi iterations per growth step are entirely expected and prove nothing about units. Retracted.”
docs/attachment-kinetics.md, lines 197–204 (§4.3, rewritten under decision 0005)

Three of those words are unpacked below. A residual is a measure of how much the field still moves each sweep — the next section is entirely about it. A Jacobi iteration is the sweep just described, carrying its inventor's name. And L/Δx is just the width of the box counted in cells: L is the box, Δx is one cell. So the rule says: double the number of cells across, and you need about four times the sweeps.

Elliptic is the key word. An elliptic equation has no “next” in it. It is not a statement about what happens after this moment; it is a statement about balance everywhere at once. So the sweep count is not a physical duration and never was. The same section states the consequence outright: “The iteration count is an output, not a target.” (docs/attachment-kinetics.md, lines 223–224.) The code agrees — the default budget is 200 000 sweeps per growth step, and it is one of the values a registered run must freeze (solver-cpu/src/lk-solver.ts:414; ADR 0005 as amended by ADR 0006, which adds divTol and relaxMaxSweeps to the frozen protocol, docs/decisions/0006-audited-surface-operator-numerics.md:84–87).

Key idea

A slow-looking program is not automatically a broken one. Thousands of sweeps per growth step is the correct behaviour of this model, not a symptom.

What “converged” means in the code

So what number does the loop actually watch?

It watches the biggest change any single cell made during a whole sweep, divided by the far-field supersaturation so the answer is a fraction rather than a size. The code is one line: residual = maxAbs / this.sigmaInfinity; (solver-cpu/src/lk-solver.ts:1528). The default cut-off is written into the options type as relaxTol, with the comment “per-sweep max |change| / sigmaInfinity below this = converged” and a default of 1×10−9 (solver-cpu/src/lk-solver.ts:70–71).

Read that definition again and the trap is already visible. The residual measures how much the field changed. It does not measure how wrong the field is. Those are different quantities, and a field can be uniformly, calmly, quietly wrong — wrong in a way that barely moves from one sweep to the next.

At the loosest setting the accepted field is visibly the wrong shape, and the value at the crystal surface — the one number the growth step actually uses — is off by tens of per cent. Nothing complains. The stopping rule was obeyed exactly as written.

The lie, with numbers attached

Was that ever a real problem in this project, or only a worry?

It was real, it was measured, and the measurement is written into an architecture decision record. ADR 0006 lists three things an audit found wrong with the numerics the charter had committed to. The first one is this chapter:

“Historical audit finding — residual-only convergence. Iterate-change alone reported ‘converged’ fields whose Dirichlet-shell vs Robin-sink imbalance grew with domain size (2.46e-6 at 32³ → 8.85e-6 at 48³ at tol 1e-9), on course to fail the habit gate's own < 1e-6 criterion at 96³ while printing ‘converged’ (round-3 audit).”
docs/decisions/0006-audited-surface-operator-numerics.md, lines 32–35

Unpack it. “Dirichlet-shell” is the outer wall of the box, held at a fixed supersaturation, where vapour is injected. “Robin-sink” is the crystal surface, where vapour is absorbed. A gate is a pass/fail check a phase has to clear before its results count; the habit gate is the one that decides whether the crystal grew into the right shape. Round 3 is the third pass of internal review over the same code. In a steady state those two totals must be equal. They were not. The mismatch was 2.46×10−6 on a 32³ grid and 8.85×10−6 on a 48³ grid — about 3.6 times larger — and all the while the residual test was being satisfied at a tolerance of 10−9. That number looks reassuringly small. It was measuring something else.

The ADR's phrasing and its own numbers sit slightly awkwardly together. Both measured points are already above 1e−6, so “on course to fail … at 96³” reads as a statement about the trend rather than about the first crossing. The numbers are quoted here as written. The direction is the finding.

How we know

The ADR itself limits how far these two numbers may be pushed. Under a heading “Evidence status for the numbers below” it records that they are “explicitly historical audit findings, not accepted gate results”, that “the ad-hoc round-3 probe scripts were not retained, so the quoted probe measurements are not independently reproducible commands and must not be promoted as such”, and that what is reproducible is the regression test that closes each one, in solver-cpu/test/lk-solver.test.ts (docs/decisions/0006-audited-surface-operator-numerics.md:25–30). So: the failure is documented, the fix is executable, and the original probe is not. That distinction is stated by the project rather than discovered by a reader.

Why does a bigger grid make it worse? A Jacobi sweep only smooths error locally, so error drains out of the domain the way heat does — slowly, and more slowly the further it has to travel. The specification quoted at the top of this chapter states the law: relaxation counts scale like (L/Δx)² (docs/attachment-kinetics.md:202). Widen the box and the sweeps needed to reach the same real accuracy go up roughly as the square. Give every size the same budget, then, and the largest grid buys the least real convergence.

That half of the argument is worth watching rather than taking on trust. Hold the sweep budget fixed, widen the domain, and the two meters disagree: the residual goes quiet anyway, while the conservation check climbs past 99 %. Nearly all the vapour the field claims to inject is unaccounted for at the surface.

This is the worst shape a bug can have. It hides in the small, fast, cheap test runs and only bites in the expensive ones — the ones whose results you were planning to publish.

A second gate, made of bookkeeping

What check would have caught it?

Not a tighter tolerance. Tightening relaxTol makes the same test stricter; it does not make it a different test. What was needed was a second question, asked of a different quantity, with a physical reason behind it. Here is that reason, in one sentence: in a steady state nothing accumulates in the middle, so whatever the boundary injects must equal what the surface takes.

That is the divergence identity. It is not a smaller version of the residual check — it is bookkeeping. It compares two totals that were computed independently of each other, and demands they agree.

One thing to notice before you read it, because this chapter is partly about which rule judged which evidence. As ADR 0006 wrote it the identity had two terms: injection minus exchange. The form below has three. The third term was added four days later by ADR 0013, and it applies only to the newer aggregate policies — aggregate-hv-g1h1-v5 when ADR 0013 was written, and its successor aggregate-hv-g1h1-v6 since. One function decides, so a later policy cannot be added at one branch and missed at another (core/src/libbrecht.ts:187–188). Results that had already been run keep the rule they ran under: “legacy-v3 and aggregate-hv-g1h1-v4 retain the original two-term identity and report no smoother-drift term. Phase 4's completed v4 artifacts and checkpoint meanings remain frozen” (ADR 0013, Decision 5).

divergenceResidual = | shellInjection + smootherDrift − surfaceExchange |  /  max(| surfaceExchange |, 1e−300)

where
shellInjection
the vapour pushed in across the outer wall, which is held at a fixed supersaturation
surfaceExchange
the vapour the crystal's surface actually absorbed, summed over the boundary cells
smootherDrift
a third term that is exactly zero in mathematics and not quite zero in a computer — the next section is entirely about it
1e−300
a floor on the divider, so that an exchange of almost nothing cannot turn the fraction into infinity

As written in docs/decisions/0013-float64-smoother-drift-divergence-identity.md, Decision 2 (which spells the bars as abs(…)); implemented at solver-cpu/src/lk-solver.ts:1555–1562

ADR 0006, the decision that introduced the identity, is blunt about what it means for the word “converged”. Convergence became dual: a relaxation counts as converged only when the residual is under relaxTol and the divergence identity is under its own tolerance, divTol, default 10−6. Both are run inputs, both are written into the checkpoint header, and both are pinned by the gate protocols — which may pin something stricter than the default, and gate 2b pinned divTol: 1e-7 (runner/src/main.ts:931). ADR 0006 then closes the door: “A Dirichlet solve failing the identity is not converged, whatever its residual says.”

In the loop this is three lines, two of them a comment explaining why the other boundary condition is exempt:

// Fixed-sigma Dirichlet requires BOTH criteria. Reflecting is diagnostic-only and has
// no source against which a divergence identity could be stated.
if (residual < this.relaxTol && divergenceSatisfied) break;
solver-cpu/src/lk-solver.ts, lines 1574–1576

Notice what that comment is doing. A reflecting wall bounces vapour back instead of supplying it, so there is no injection term and the identity has nothing to say. The code does not quietly skip the check in that mode; it states that the check is undefined there and why. Skipping a test and having no test to skip are different situations, and only one of them is honest to write down.

The last button in that demo is the part that matters most. Reporting “not converged” would be worth very little if the program then carried on growing the crystal anyway. It does not. The comment on step() says “growing on an unconverged field is a silent physics error”, and the public method refuses by name:

"advanceSurface requires exactly one accepted converged relaxField; an unconverged field or unmatched call cannot advance (state=" + this.cycleState + ")"
solver-cpu/src/lk-solver.ts, lines 1614–1616

And there is a test whose name is the whole claim: it("an unconverged relaxation NEVER advances the surface — including via the public interface", …). It builds a solver deliberately rigged to fail — an impossible tolerance of 10−30 and a cap of two sweeps — and then asserts that the attached-cell count did not move, that the tick did not move, that the fill ledger is still zero, and finally that calling advanceSurface() directly throws (solver-cpu/test/lk-solver.test.ts:928–941). The safeguard is tested by being triggered.

Careful

Both gates together prove one thing only: that the field the program solved is the field its own equations describe. That is a claim about arithmetic. Whether those equations describe an actual snow crystal is a completely separate claim, decided by completely separate evidence, and nothing in this chapter touches it. Keeping those two apart is the entire reason this machinery is worth building.

The check on the check

What happens when the safeguard itself turns out to be slightly wrong?

First, one fact about computer arithmetic, because the rest of this section turns on it. A computer does not store a number exactly. It stores about sixteen significant digits and rounds the rest away. The format this project uses is called float64 — sixty-four bits per number. Now look again at what a sweep does: replace every cell by a weighted average of itself and its neighbours. On paper that only moves vapour around and creates none, so the totals are untouched. In a computer, each individual average rounds its own result, and those per-cell roundings do not cancel. The smoother is conservative in real arithmetic and not conservative bit-for-bit.

Chapter 21 left protocol v4's cold job stopped while attempting growth step 12, the residual at exactly zero, the divergence ratio stuck at about 3.1×10−7 — three times its registered divTol of 1×10−7 — and the cause named as roundoff in the smoothing stencil. Here is the measurement that named it. Every value below is quoted to a few digits and recorded to full precision in the credit line under the figure that follows, so nothing here asks you to compare sixteen digits by eye.

Rather than loosening the tolerance, a separate program — scripts/diagnose-gate2b-v4.ts — decoded the saved checkpoint and rebuilt the diffusion stencil outside the solver. One reconstructed sweep measured 643,055 active cells and the two totals a steady state says must be identical: injection across the outer shell, and exchange at the crystal's surface. They agreed to six digits and then parted company — 3.679402…×10−7 going in, 3.679401…×10−7 coming out. Subtract them and the entire disagreement is about 1.1×10−13. Divide that by the exchange, which is what the identity does, and it comes to 3.1×10−7 — the exact ratio the cold run was stuck at, three times over its tolerance. That is the whole quarrel: a crumb about three parts in ten million of either total, refusing to go away after 200,000 sweeps.

Then the program measured one more thing, which is the whole point: the signed change the smoothing step itself had made, before any boundary values were substituted in. That came out as −1.1×10−13. Same size, opposite sign — and not merely the same size. The two values match digit for digit, down to the last digit either was printed with, which is why the diagnosis was an identification rather than a guess: the vapour the books could not account for is precisely the vapour the averaging step rounded away (docs/decisions/0013-float64-smoother-drift-divergence-identity.md:20–29).

So about 10−13 more vapour crossed the outer wall than the surface ever absorbed, the smoother is where it went, and the two-term identity had nowhere to put it. When the crystal is growing very slowly, as it is in the cold, that harmless absolute crumb is divided by a very small exchange and comes out as a relative error above tolerance. The identity was not detecting a physics problem. It was detecting itself.

It matters that this is a local effect and not a bookkeeping one, because it decides what the fix can be. The obvious move is to add the totals up more carefully, and the project checked: “Naïve, Neumaier-compensated, and exact binary-rational sums agree on every value. This is not a global-summation defect. It is local IEEE-754 rounding in a mathematically conservative split stencil” (docs/decisions/0013-float64-smoother-drift-divergence-identity.md:31–33). Careful summation is listed among the alternatives and rejected in one clause — “Rejected by evidence: naïve, compensated, and exact sums reproduce the same mismatch” (same file). A more careful sum returns the same number, because the number was never a summation error.

The drift therefore became a third term in the identity, with two rules attached. First, it must be metered — measured directly from the two field states in the same sweep. It may not be worked out from the other numbers, because “such an inferred correction would make the identity tautological” (ADR 0013, Decision 3); the rejected alternative spells out the damage: inferring drift as exchange minus injection “would force every reported divergence to zero by construction and destroy the guard.”

Second — and this is where the project checks its own check — the first implementation of Decision 0013 required the drift to be finite but did not bound its magnitude, and an adversarial review worked out what that permits. A report claiming a shell injection of 1, a surface exchange of 10−6, and a drift of −0.999999 would satisfy the corrected identity. Any real loss could be relabelled “roundoff” and cancelled by the new term (docs/decisions/0014-bound-float64-smoother-drift.md:11–15). ADR 0014's answer is a bound derived from the arithmetic itself — a conservative allowance of 1024 rounded operations per active cell — and a rule that the solver “must reject a non-finite drift or any abs(smootherDrift) > smootherDriftAbsLimit; such a sweep is not convergence evidence.” Try it below.

That makes three separate things a v5 or v6 sweep has to satisfy, and ADR 0014 names the two new ones exactly rather than lumping them together: “Both the three-term divergence tolerance and this absolute roundoff bound are load-bearing. Passing one does not excuse failing the other” (Decision 4). And ADR 0006 forecloses the retreat, listing residual-only convergence among the “simplifications” that may not return “without overturning measured audit findings — that requires its own ADR citing new evidence.”

Still unsettled

Every review named in this chapter — the round-3 audit that found the residual lying, the adversarial review that found the forgeable drift term — was a large language model reviewing a large language model's work. So was the two-reviewer process that checked this page. The project records that as a disclosed limitation rather than a substitute: “All reviews to date, internal and external-facing, are LLM reviews; for publication that is a disclosed limitation, not a substitute” (docs/stretch-sharing-and-investigation.md, §4 item 3). The same item requires that at least one human domain scientist read any manuscript before submission. That has not happened yet. The findings above are reproducible by anyone who runs the tests; the judgement that they were the right things to look for has not yet been checked by someone qualified to check it.

Invalid there — and saying so

The whole quasi-static idea rests on an assumption: that the vapour settles far faster than the surface moves. What if, somewhere in the parameter space, it does not?

Then the model is wrong in that place, and the project's job is to say so. Section 4.3 keeps a test for exactly this. Settling takes a time of about L²/D; growing takes a time of about L/vn; divide one by the other and you get a single number that has to be small.

vn · L / D  ≪  1

where
L
the width of the simulated box, in metres — the longest grid dimension times the cell size, which is how every caller in the repository computes it (runner/src/gate4b.ts:430, runner/src/main.ts:676)
D
the diffusion coefficient of water vapour in air at this pressure, in square metres per second: roughly, how much ground vapour covers in a second (core/src/libbrecht.ts:59–62)
vn
the speed at which the ice surface advances along its own normal, in metres per second
≪
“much less than”. The Phase 4 gate makes that concrete and demands below 10−2

docs/attachment-kinetics.md, lines 234–240 (§4.3, “Quasi-static validity check”), which states it verbatim as: “Relaxation ~L²/D against growth ~L/v_n gives the Péclet-like condition v_n·L/D ≪ 1.” Implemented as pecletUpperBound, core/src/libbrecht.ts:146–157

In plain English: the width of the box, divided by the area vapour covers in a second, times how fast the ice front moves. If that comes out large, the vapour has not finished settling before the surface moves again, and the whole quasi-static picture stops being a description of anything. What the specification does with such a failure is the point:

“where it fails, the quasi-static model is invalid there, and that is a finding to report, not a nuisance to tune away.”
docs/attachment-kinetics.md, lines 234–240

In code this is pecletUpperBound(tempC, sigmaInfinity, lengthM, pressurePa), and it is deliberately pessimistic twice over. It assumes every arriving molecule sticks (core/src/libbrecht.ts:146–157), which is the fastest the surface could possibly move; and the length it is handed is the whole box, which is wider than the crystal sitting inside it. Both choices push the reported number up, so a run that passes this check passes it with room to spare. The Phase 4 gate then evaluates it over every environment a run visits and passes only if “every registered conservative Peclet bound is finite and below 1e-2” (runner/src/gate4b.ts:3124). A run that fails does not get quietly re-tuned until it passes. It gets named in the failure list.

Errors, warnings, and a rule that would reject its own source

One last question, and it is about taste rather than arithmetic: when a check fails, how loudly should the program complain?

Before the example, a switch to flag. Everything so far — the dual gate, the drift bound, the Péclet check — belongs to LibbrechtKinetics. What follows belongs to GGThreshold, the borrowed Gravner–Griffeath machinery rule from chapter 18, validated in a different file and enforced by a different solver. The repository is explicit that the two do not share guardrails — “These constrain GGThreshold. LibbrechtKinetics does not inherit them; its separate fill-CFL and Péclet checks are specified in attachment-kinetics.md §4.3–§4.4” (docs/gg-machinery.md:355–357). So in this section, “the source paper” means Gravner and Griffeath's, and ρ, κ, μ and ggThreshBeta are not knobs on the vapour field you just watched converge.

Not every failed check deserves the same answer, and that validator — core/src/params.ts — is the clearest case of it here. Past the plain range checks it runs three more, and grades them differently. Two are hard errors. The Packard regime is runaway: the crystal expands as fast as information can travel across the grid, which is an artefact of discrete averaging rather than physics. Growth stall is the opposite: melting drains the surface faster than freezing fills it, and nothing ever attaches. Either one and the solver refuses to construct at all — throw new Error(`invalid GG parameters: …`) (solver-cpu/src/gg-solver.ts:240–243).

The third check needs two pieces of vocabulary first, and they are worth taking one at a time. The first is the slot. GGThreshold does not carry a single attachment threshold; it carries one for each way a cell can be surrounded, and a slot is the name of one of those ways, written (nT, nZ): how many neighbours the cell already has in its own plane, capped at three — so 0, 1, 2 or 3, four possibilities — and how many above or below, capped at one, so two possibilities. Four times two is eight, minus the case where the cell has no attached neighbours at all — which is not a boundary site and never gets asked — so seven: “excluding (0,0) — that's 4·2 − 1 = 7 slots” (docs/gg-machinery.md:113).

Seven meaningful slots, and yet the arrays holding them are eight long. That is not a miscount. The slot number is worked out arithmetically — return nT * 2 + nZ; (core/src/params.ts:24–25) — so the busiest corner, (3,1), lands at index 7, and an array has to run 0 to 7 to reach it. That leaves index 0, the (0,0) nobody ever asks about, as a hole in the middle of live data. A hole is the dangerous kind of empty, because an unfilled number in a computer is usually zero, and zero is a perfectly usable threshold: a cell compared against it would attach immediately, and nothing would look wrong. So the hole is deliberately filled with something unusable instead — “poisoned with NaN so accidental reads are loud” (core/src/params.ts:4–5).

That is the second piece of vocabulary. NaN — “not a number” — is what a computer stores when a calculation has no answer at all: zero divided by zero, the square root of a negative, a measurement that was never taken. It is not a word and not an error message; it is a value that lives in a number's slot and can be passed around like one. What makes it useful here is that it is deliberately contagious. Anything you do with a NaN comes back NaN, and every size comparison with it — greater than, less than, equal to — is false, including comparing it with itself. A threshold read out of slot 0 by mistake therefore cannot pass for a threshold. It poisons every sum it touches and fails every test it enters, so the mistake surfaces loudly instead of settling quietly into the results. You will meet it again in chapter 24, standing in exactly the same way for a measurement that could not be taken.

The parameters, once, before the demo uses them. ggThreshBeta is the threshold at a slot — the boundary mass a cell needs before it joins the crystal; ρ is the vapour supply, κ the fraction of vapour that stays vapour at a boundary site, and μ the melting rate that hands mass back (core/src/params.ts:10–20). ρ is one number for the whole run; ggThreshBeta, κ and μ each carry a value per slot, and the monotonicity check below is applied to all three — though in both published presets κ and μ happen to use the same value in every slot, so only ggThreshBeta varies from slot to slot.

The third check is monotonicity: the source paper assumes that a more enclosed corner should always attach at least as readily as a more exposed one, so each parameter should decrease as neighbours are added — one step at a time, either “+1 in nT at fixed nZ” or “+1 in nZ at fixed nT” (core/src/params.ts:157 and :163). That is a perfectly reasonable assumption. It is also violated by the paper's own published hollow-column preset — “twice, both into slot (3,1)”, because ggThreshBeta31 = 1 while both of its less-enclosed neighbours, ggThreshBeta30 and ggThreshBeta21, are 0.5 (core/src/params.ts:144–146; docs/gg-machinery.md:385–393). The comment in params.ts says what to do about that in one clause — “a hard error would reject published parameters” — and docs/gg-machinery.md:391–393 makes it an instruction: “Warn; do not reject.”

A validator strict enough to reject its own source material is not strict, it is useless — because the first thing anyone does with it is switch it off, and then the two checks that were right go off with it. Severity is a design decision, and this project writes down which of its rules it is prepared to be overruled on.

Key idea

A tighter tolerance makes the same test harder to pass. A second, independent test asks a question the first one could not ask at all. When a check is failing to catch things, the useful move is almost never to turn the dial — it is to find a quantity the bug cannot fake.

Deciding in advance which of your own rules you are prepared to be overruled on is also what makes the next chapter's test a fair one: a project that has not settled that question can always discover, after seeing the answer, that the rule it just broke was only ever a warning. Both gates now agree, the identity closes inside its registered tolerance, and the field is as converged as the machine can make it. It is still a field solved inside a box, and the wall of that box is a number somebody chose. The next chapter is about how you find out whether that choice mattered: vary something that should not matter, and see exactly which answers move — and which do not.
