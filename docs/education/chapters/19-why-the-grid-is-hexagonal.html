Chapter 19

Why the Grid Is Hexagonal

Before a single equation goes in, a simulation has to decide what a “place” is. Get that wrong and the shape of the container turns up inside the answer — wearing the costume of a result.

~16 min read 7 animations 1 table

By the end you will be able to

  • Explain why choosing a data structure can be a physics decision.
  • Describe a cellular automaton, and say why updating every cell simultaneously is part of the model rather than a coding style.
  • Read a conservation test as a proof-shaped assertion rather than a sanity check.
  • Say why a rectangular domain can never be relied on to score exactly zero on a sixfold-symmetry test once the depletion field reaches a wall, no matter how correct the code inside it is — and why the metric reading zero at the end of such a run is not a reprieve.

The container leaks into the answer

The last chapter left the grid sitting at the bottom of the ladder with a question hanging over it: why does every cell get eight neighbours, all exactly the same distance away? Answering that starts somewhere that looks unrelated — with a rule that has nothing sixfold in it.

Lay out a block of cells. Mark the one in the middle as ice. Then, over and over, apply a single sentence: a cell becomes ice if any one of its neighbours is already ice. That is the whole rule. It contains no hexagon, no angle, no crystal, no physics.

Run it on two different grids and watch what comes out.

The triangular grid grows a hexagon. The square grid grows a diamond. Both panels are drawn on the same 17 × 17 block of indices — 289 cells each — and the only difference between them is which cells count as neighbours. Nowhere in the rule did anyone write the word “six”. The grid supplied it. And on the square grid, the grid supplied “four” just as confidently.

That is the problem in one picture. If you built a snow-crystal simulator on a cube of little cubes and it grew something sixfold, you would have no way of telling whether the physics did that or the arithmetic did. Worse: you would probably never grow a clean hexagon at all, because a fourfold container would be fighting you. Either way the output is uninterpretable, and an uninterpretable output is not a result.

Notice one more thing about the left-hand panel: it is not hexagon-shaped. A rectangular block of indices on a triangular lattice leans when you draw it in real space. Keep that leaning shape in mind — it comes back at the end of this chapter as a measured defect.

Key idea

The symmetry of the grid is not a rendering detail. It is an assumption baked into the model before any equation is written — and it comes out in the results looking exactly like a discovery. Choosing the lattice is doing physics.

Careful

Picking a hexagonal grid does not make the model right, and it is not evidence about nature. It removes exactly one specific way of being wrong: the way where a sixfold result would only have been the container talking. Everything in this chapter buys interpretability, not correctness. Whether the physics laid on top of the grid matches reality is a separate question that only the validation sweep can ask — and that sweep, Phase 6, is still in progress.

Eight neighbours, all the same length

So what does the project use instead of a cube? The very first lines of core/src/lattice.ts answer it.

“The stacked triangular lattice T x Z. […] 8 neighbors: 6 in-plane (T) + 2 vertical (Z). The fundamental cell is a hexagonal prism with across-flats = 1 and height = 1, so all 8 bonds have unit length.”

core/src/lattice.ts, lines 1–5

Read that slowly, because it is three decisions stacked on top of each other.

A triangular plane, repeated in flat layers. Not a cube of cubes — a sheet of hexagonal tiles, then another sheet directly above it, then another. The specification calls the arrangement T × Z: the planar triangular lattice T, stacked along the vertical axis Z (docs/gg-machinery.md §1).

Eight neighbours per cell. Six around you in your own sheet, one directly above, one directly below. A cube grid would give you six neighbours meeting at right angles. This gives you six meeting at 60°, plus two vertical.

All eight bonds the same length. This is the part that is easy to skim and is doing the most work. The cell is a hexagonal prism whose across-flats width is 1 and whose height is also 1, so every one of your eight neighbours is exactly distance 1 away, and vapour hopping to one travels the same distance in every direction. If the vertical bond were 1.4 times the in-plane one, the simulation would grow crystals stretched along an axis for reasons that had nothing to do with ice.

Cells are addressed by axial coordinates (i, j, k) — a skewed pair of in-plane axes plus a layer number. Where a cell actually sits in space is then a one-line conversion: x = i + j/2, y = j·√3/2, z = k (core/src/lattice.ts line 76). Skewed coordinates look like an inconvenience. They buy something enormous: the symmetry operations become integer arithmetic.

Rotating the whole lattice by 60° is rot60(i, j) = (−j, i + j). Mirroring it is mirror(i, j) = (j, i). Reflecting it top-to-bottom about the seed plane is zmirror(k) = 2·k_c − k. The file's own comment is the point: “All are exact on the integer lattice” (core/src/lattice.ts lines 81–83). No sines, no cosines, no rounding.

Those three operations together — the sixth-turn, the mirror and the top-to-bottom flip — generate the full symmetry group of a hexagonal prism. Crystallographers call that group D6h, and the repository uses the name throughout: the comment heading those three functions is literally “D6h symmetry operators” (core/src/lattice.ts line 81). When a file in this project says “exact D6h symmetry”, it means: every one of those operations leaves the crystal looking identical, cell for cell.

That claim is checkable directly, not just quotable. Every demo so far in this chapter has exercised one generator at a time — demo-eight-bonds above turned rot60 six times and came back around. Nothing yet has composed two different generators and watched where the result lands. Try it.

When chapter 18's ladder demands a symmetry test that can return the value zero rather than small, this is where that becomes possible at all: you can ask whether cell (4, 7) and its rotated partner hold identical values, because “its rotated partner” is an exact integer address rather than a nearby float.

Three numbers, never one

How big is the grid? The obvious answer — one number, a “resolution” setting — is banned. The project's first architecture decision record says so explicitly.

“Domain size is three independent integers (nx, ny, nz) everywhere: in core, in the checkpoint header, in the CLI, in the WGSL dispatch, and in the resolution presets. There is no scalar ‘resolution’ parameter anywhere in the codebase.”

docs/decisions/0001-non-cubic-grid-dimensions.md, lines 35–38

The reason is that snow crystals are not cube-shaped and are not close. The ADR works it out from published case studies: a plate “reaches a radius of about 350 lattice units while remaining a plate — a handful of cells thick. That wants a domain around 800 × 800 × 80. Their needles and columns are the transpose: narrow in the T-plane, long in Z. A cube large enough to contain the plate is ~10× the cells actually needed, and a cube sized for a column is the same waste rotated.”

The cost of insisting on a cube, worked from the sizes in docs/decisions/0001-non-cubic-grid-dimensions.md lines 18–21. Cell counts are the product of the three dimensions.
DomainCellsFits a plate?Fits a column?
800 × 800 × 8051,200,000yes, snuglyno — too short
80 × 80 × 8005,120,000no — too narrowyes, snugly
800 × 800 × 800 (a cube)512,000,000yes, with ~10× wasteyes, with waste

That is ten times the memory and ten times the work, spent on empty air. So the domain is three numbers, and the code has to carry three numbers everywhere.

The ADR then does something worth copying. Under a heading called Live trap it writes down, in advance, the bug this decision will cause: “the triangular lattice's axial coordinates are skewed, so a domain with nx = ny is a rhombus in real space, not a hexagon, and its corners are not equidistant from the seed. […] Flagged here so it is not rediscovered as a mysterious symmetry-metric failure.”

The ADR's own verdict on that was mild: “This does not break the physics — the crystal simply must not reach the domain edge, which the 80% stopping rule already enforces — but any metric that assumes ‘distance to domain edge’ is isotropic is wrong” (lines 59–61).

That 80% is worth pinning down before it confuses you later, because chapter 23 will describe what sounds like the same rule and attach a different number to it. They are two rules, not one rule quoted carelessly. Eighty per cent is Gravner and Griffeath's own stopping rule, transcribed from their paper: halt the run when the crystal's radius passes 80% of the domain radius (docs/gg-machinery.md lines 376–377). It ends a simulation. Sixty-five per cent is a later and stricter instrument — the domain-contact guard, which the specification introduces in the very next paragraph as “distinct from, and stricter than, G-G's 80% stopping rule”: it flags a run invalid when the crystal's bounding box exceeds about 65% of any domain extent, and “flagged runs never enter validation results” (lines 379–383). One stops the clock; the other disqualifies the output as evidence. ADR 0001 could only cite the looser of the two because the tighter one did not exist yet — the ADR arrived with charter v1.1 and the guard was added in the next revision, v1.2, as review integration (project charter.md, revision history). The rule chapter 23 takes apart is the 65% guard.

Between them the wall is covered twice over: the looser rule ends a run before the crystal reaches the edge, and the stricter one refuses to count a run whose crystal came close. What the ADR did not anticipate is what happens to a symmetry gate that has to read exactly zero — which is where this chapter ends, after two more pieces of machinery have to be in place first.

One long list, and the bug that doesn't crash

The three-dimensional grid is not stored as a three-dimensional anything. It is one long flat list of numbers, and a cell's coordinates are turned into a position in that list by arithmetic.

index = k·(nx·ny) + j·nx + i

where
i, j
the two skewed in-plane coordinates of the cell
k
which flat layer the cell is in
nx, ny
how many cells wide the domain is in each in-plane direction
index
the slot number in the single flat array holding the whole grid

core/src/lattice.ts, lines 17–19

Once you have that, finding neighbours is just adding constants: +1 and −1 for east and west, then +nx, −nx, +1−nx, −1+nx for the rest of the plane, and ±(nx·ny) for straight up and straight down. Eight additions and you have visited the whole neighbourhood, which is what makes tens of millions of cells feasible at all.

And here is the trap, stated in the specification: “The flat offsets are only valid away from the domain faces — i±1 wraps across rows” (docs/gg-machinery.md lines 53–54). If a cell sits at the eastern edge of its row, +1 does not fall off the end of the world. It lands on the first cell of the next row. Nothing crashes. You have quietly added a wormhole to your universe, and the crystal that grows through it will look perfectly plausible.

The defence is best explained by what the code refuses to do. There are two neighbour lookups in lattice.ts, and the slow one is not an oversight. neighborIndices checks bounds in every direction and returns −1 for anything outside the domain — “For the domain shell; use flat offsets in the interior.” The fast one, tNeighborFlatOffsets, is labelled “valid in the interior only”. The specification even prices the split: the bounds-checked gather runs only on the boundary shell, which is “O(N^⅔), so the cost is noise” (docs/gg-machinery.md lines 53–55). A shell is a skin, and a skin grows far more slowly than the volume inside it: at the runner's default domain of 128 × 128 × 64 (runner/src/main.ts line 158) about six cells in every hundred are on a face. The border between the fast path and the careful one is written down instead of assumed.

ADR 0001 gives the reason this is treated as a physics problem rather than a tidiness problem, quoting the project's own charter: “a swapped coordinate is a silent physics bug.” Silent is the operative word. A crash is a gift; it tells you exactly where and when. An index bug hands you a beautiful, wrong snowflake and says nothing at all.

One rule, everywhere, at once

With the grid settled, what actually runs on it? A cellular automaton: a grid where every cell holds a small amount of state, and where one simple rule is applied to every cell at every tick, using only what that cell and its neighbours looked like at the start of the tick.

Each cell here holds three things (core/src/state.ts lines 44–49): a flag a that is 1 if the site is part of the crystal; a number b called boundary mass — “quasi-liquid when a = 0, frozen ice when a = 1” — and a number d for water vapour, which is “0 forever on attached sites”. That is everything the rule is allowed to see. Nobody tells the crystal to grow six arms. Six arms are what a local rule produces after a few thousand ticks on a sixfold grid.

Under GGThreshold — the code's name for Gravner and Griffeath's threshold rule, the known-good stand-in of chapters 15 and 18, and the rule Phase 2a certified — each tick runs four steps in a fixed order (solver-cpu/src/gg-solver.ts lines 6–15): diffusion, which spreads vapour by local averaging; freezing, where “boundary cells trade vapor for boundary mass”; attachment, which turns a cell into ice once its boundary mass passes a threshold; and melting, where “boundary cells that did NOT just attach leak b back to d”.

The averaging in step one is where the unit-length bonds pay off. In-plane, a cell becomes the average of itself and its six in-plane neighbours — a weight of 1/7 each. Vertically, it becomes 4/7 of its own new value plus 3/14 from each of the layers above and below. Those weights look arbitrary and are not: the specification says they “make diffusion isotropic once the lattice is scaled so all 8 bonds have unit length”, and adds the check 4/7 + 2·(3/14) = 1 (docs/gg-machinery.md lines 191–192).

Now the discipline point, and it is the reason this section exists. Because the rule is local and simultaneous, the order you visit cells in must not matter. So diffusion reads from one copy of the vapour field and writes into a second, then swaps them — two buffers, ping-ponging. Numerical people call that a Jacobi update: every cell is computed from the old field only, so no cell can ever see a value that was changed this tick. The alternative, overwriting the field as you go, is cheaper and uses half the memory. The solver header rejects it in three words.

“(i)   diffusion  — Jacobi over ping-pong buffers, NEVER in place (in-place Gauss-Seidel is a silent physics bug)”

solver-cpu/src/gg-solver.ts, lines 7–8

Gauss–Seidel — updating in place, so cells later in the sweep see values already changed this tick — is a perfectly respectable numerical method, and often converges faster. It is simply not the model this project says it is running. And the difference is not a rounding detail. Try it.

With two buffers, flipping the sweep direction changes nothing whatsoever — that is what “the order must not matter” looks like when it is true. Update in place and the sweep direction becomes an input to the physics: the rotated-partner difference leaves zero the moment you press the button, and the vapour's centre of mass — which has nowhere legitimate to go, given one source cell in a symmetric room — drifts off in whichever direction you happened to loop.

How we know

The same discipline is enforced on the physics rule, in a different file and for a different reason: solver-cpu/src/lk-solver.ts lines 1428–1432 warn against replacing values in place there too, because “an opposing pixel may itself be a boundary pixel, so in-place replacement would make the answer boundary-list-order dependent (a hidden Gauss-Seidel/D6h defect)”. Two buffers cost a full extra copy of the domain in memory. That is the price of not letting an implementation shortcut become a physics claim.

Nothing is created, nothing escapes — if the walls reflect

What stops vapour leaking out of the edges of the world, or being quietly manufactured at the crystal's surface? A rule short enough to fit in one sentence: any averaging term that would point into ice, or out of the domain, is replaced by the cell's own value.

The specification spells out the consequence: “This is what makes mass conservation exact: a cell retains (1 + n_attached)/7 of its mass and hands 1/7 to each free neighbor, and the books balance” (docs/gg-machinery.md lines 194–197). Nothing is thrown away at a wall; it is handed back to the cell that offered it. So the total of vapour plus boundary mass across the whole grid is a quantity that arithmetic says cannot change — “an exact invariant, not an approximate one” (lines 163–165) — provided the far field is reflecting, which is the condition just described, the one where a term pointing out of the domain is handed back to the cell that offered it.

That upgrades a test from a sanity check into something proof-shaped: not “does the picture look right” but “here is a number the rule guarantees, and here is the run reporting it”. A bug that leaks or manufactures mass trips it long before it produces a wrong-looking crystal.

Three things to notice. First, run it long enough and the drift stops reading exactly zero: it settles at a couple of parts in 1016, which is the floating-point noise floor of the machine rather than a physics error. The invariant is exact in arithmetic; a computer reports it plus rounding dust. The project therefore writes its tests against measured floors rather than against hope. One asserts “conserves total mass to < 1e-10 relative over 10 000 ticks GROWN, noise OFF, reflecting”; a companion “crystal-free control run characterizes the float floor” and demands drift below 1e-13 (solver-cpu/test/gg-solver.test.ts lines 37 and 52). The maker-asserted Phase 2a gate run records drift of 2.056e-13 against a measured float floor of 3.8e-16 (docs/PROGRESS.md, Phase 2a gate row) — asserted by the project about itself, on the strength of a run that exits zero or fails.

The same row records the other number this chapter has been circling. On a 128 × 128 × 64 hexagonal-prism domain, plate preset, seed 1, that run reports “delta check clean all 4800 ticks, full metric 0 everywhere sampled” (docs/PROGRESS.md, Phase 2a gate row). Not small. Zero — checked every tick, for the whole run. That is the claim the rest of this chapter is protecting, and it is a stranger claim than it looks.

Second — and this generalises far beyond snowflakes — the measuring instrument has to be finer than the thing being measured. Adding a million floating-point numbers the obvious way accumulates its own error, and core/src/metrics.ts does that arithmetic out loud: “Naive summation over ~1e6 f64 cells has worst-case relative error of order n*eps ≈ 1e-10 — at the mass-gate tolerance itself.” A ruler whose own error is the size of the tolerance cannot decide anything. So the total is accumulated with compensated summation, which keeps track of the crumbs ordinary addition throws away — the lower panel of the demo runs the exact case the test suite uses.

Third, and this is a condition rather than a decoration: read the last word of that test name again. “Noise OFF, reflecting.” The closed ledger belongs to that far field and no other. Reflecting is the Phase 2a condition and the one faithful to the Gravner–Griffeath paper: vapour is never replenished, so the crystal eats a finite reservoir and the supersaturation falls over the run (docs/gg-machinery.md lines 199–201).

Phase 2b added a second: fixed-σ Dirichlet, which holds the domain faces at the set supersaturation, so vapour is replenished at the far field. The motive is that “Nakaya coordinates and Libbrecht's measurements assume a maintained far-field σ”. The cost is the theorem. Under Dirichlet the boundary is “a source/sink by design”, so those runs do not come with a closed ledger; they come with a metered one, a check that “starts depleted and verifies that Dirichlet returns to the set value with injected field change metered and balancing” (lines 203–210). Same discipline, different theorem.

And Phase 6 registered a third. Its condition is monopole-matched: “Every Phase 6 validation run uses the monopole-matched shell” (docs/plans/phase-6-nakaya-validation.md line 158, citing ADR 0024). Fixed-σ Dirichlet was measured and found wanting — a fixed-value wall at a finite radius “over-supplies vapor, by a factor the spherical solution gives in closed form, and at the domain sizes this project can afford that factor is large rather than negligible” (core/src/state.ts lines 13–17). Chapter 23 takes that apart.

Three conditions, then, and three different ledgers, and the specification refuses to let them blur: which condition a run used is recorded in its checkpoint metadata, and results are “never compared across conditions silently — the two record different experiments” (docs/gg-machinery.md lines 211–212). One more thing has to be said about those Phase 6 runs, because it is easy to picture them as this chapter's tick with a different wall bolted on. They are not. They run the other surface rule, LibbrechtKinetics, and it rewrites three of the four steps you just read. In plain English:

  • Diffusion stops being one averaging pass. Instead of smoothing the vapour field once per tick and moving on, the field is relaxed over and over — the same kind of neighbour averaging applied repeatedly until the answer stops moving — with the crystal's surface written into the boundary of that solve. Deciding when it has stopped moving is a harder question than it sounds, and chapter 22 is about that.
  • The freezing step disappears. The crystal's surface becomes the one and only place vapour leaves the field, absorbed there at a rate the surface physics sets. That absorption is the “sink” the quotation below mentions, and it does the job freezing used to do: “its Robin sink replaces κ freezing” (docs/gg-machinery.md lines 125–126).
  • Attachment stops being a threshold. Rather than tipping over a fixed line, a surface cell accumulates a fill fraction — it fills up, face by face, and becomes ice when it is full. Which rule governs that filling is recorded in the run as a version number, so a result can always name the policy that produced it. That is what “policy-versioned boundary-pixel fill” means.
  • Melting is switched off entirely. The fourth step simply does not run.

That third change is the hard one, and chapter 21 is about nothing else: turning a continuous surface speed into a discrete cell that either is or is not ice. Here is the specification's own one-sentence version, now that you can read it.

“Under LibbrechtKinetics, diffusion becomes an iterated surface-boundary relaxation, freezing is replaced by that sole sink, threshold attachment is replaced by policy-versioned boundary-pixel fill, and melting is disabled.”

docs/gg-machinery.md, lines 173–175

What carries through unchanged into Phase 6 is everything underneath — the eight unit-length bonds, the integer symmetry operators, the inscribed hexagonal prism. That is the point of this chapter, and the point of the ladder in the last one: the rung below does not get rebuilt when the rung above changes.

The box that isn't a hexagon

Now the trap ADR 0001 flagged — arriving on schedule, with a number attached, and worse than the ADR expected.

The array of cells is a rectangle of indices. It is not a rectangle in space. Because the axes are skewed by 60°, a block of indices running −R to +R in both i and j is a rhombus when you draw it — long in one diagonal, short in the other. Its walls therefore sit at unequal distances from the seed in the middle. The comment in core/src/state.ts states the consequence as geometry, not as a bug.

“a rectangular axial box is a RHOMBUS in cartesian space — its walls sit at unequal hex distances from the center (C2 symmetry, not C6), and an even nz puts unequal z-reservoirs above and below the seed plane. Under the reflecting condition the walls therefore feed the crystal anisotropically, and exact D6h symmetry is geometrically impossible once the depletion field reaches a wall (measured: a systematic Δb ≈ 0.03 between zmirror partners by tick 269 on nz=16).”

core/src/state.ts, lines 22–30

Two shorthands in there. C6 means a shape that comes back to itself every 60° — six positions, all identical. C2 means it only comes back after a half turn: two positions, not six. A rhombus is a C2 shape wearing a C6 grid, and that mismatch is the whole defect. (D6h, from earlier, is C6 plus the mirrors and the top-to-bottom flip — the full symmetry of a hexagonal prism.)

Note which axis breaks. A box is asymmetric in two independent ways — sideways, because the skewed index box is a rhombus, and vertically, because an even number of layers leaves no exact centre plane (at nz=16 the seed plane sits 8 layers from one z-wall and 7 from the other, solver-cpu/test/gg-solver.test.ts lines 154–155). The measured break came through the vertical one: the Δb of about 0.03 above is between zmirror partners, cells reflected top-to-bottom about the seed plane.

Now read the mechanism as a sequence. The crystal eats vapour, so a shadow of depleted air spreads outward from it. While the shadow is small, the walls are irrelevant and everything is perfectly symmetric. The moment the shadow touches a wall, the wall starts handing vapour back — and an unequal wall hands back unequally. From that tick onward, exact sixfold symmetry is not difficult. It is impossible. No amount of correct code can pass a test the room forbids.

The fix is a mask, and it has to cut in both directions at once, because the box was asymmetric in both. Sideways, the active region is cut down to a hexagonal prism inscribed in the index box, and everything outside it becomes an inert wall cell: “wall cells are inert and reflect exactly like attached cells” (solver-cpu/src/gg-solver.ts lines 24–25). Vertically, the same mask trims the layer stack: hexPrism “masks the active region to an inscribed hexagonal prism with a zmirror-symmetric z-range” (core/src/state.ts lines 29–30), so the reservoir above the seed plane holds exactly as many layers as the one below — which is the axis that actually broke. The half-extent it keeps is the smaller of the two gaps, Math.min(kc, nz − 1 − kc) (solver-cpu/src/gg-solver.ts line 368), so at nz=16 a layer is simply given up. It costs you the corners of the array you allocated, and it buys the only thing that matters here: every wall is now the same lattice distance from the seed. The project also notes it was not first. The machinery is transcribed from J. Gravner and D. Griffeath, “Modeling snow crystal growth III: three-dimensional snowfakes”, Phys. Rev. E 79, 011601 (2009) — the repository calls them “G-G” and transcribes the model in docs/gg-machinery.md (lines 11–12). And “G-G themselves ran ‘a finite lattice in the shape of hexagonal prism’ (paper §III)” (core/src/state.ts line 28).

ADR 0001 predicted that the rhombus would confuse a distance metric. It did not predict that exact sixfold symmetry would become geometrically impossible, and nobody reasoned that out in advance either — core/src/state.ts dates it as a finding, 2026-07-14. It was measured, and the failure is pinned in a test that exists purely to keep failing.

How we know

solver-cpu/test/gg-solver.test.ts line 152 runs a negative control — a test built to fail on purpose, so you know your instrument can still catch the thing it is watching for. (The name is borrowed from laboratory science, and chapter 25 makes it the backbone of the whole test suite. It does not mean a run that happened to come out negative.) The control here is named “the box domain breaks symmetry once the field feels the walls”. At 32×32×16 it records that “the first asymmetric attachment lands at tick 270 via zmirror, with a boundary-mass split of ~0.03 between mirror partners: mesoscopic wall physics, three orders above ulp scale, NOT index arithmetic”, and asserts that tick number exactly (line 181). Its stated job is that “if this test ever fails, the box has silently become symmetric and the domain machinery changed underneath the gate.”

Two things in that quotation. Tick 270 is one tick later than the 269 in the state.ts comment above, and that is not a transcription slip: the two files record different events. state.ts notes the boundary-mass split as present by tick 269 — an observation, not an onset — and the test pins the first asymmetric attachment at 270. The mass has to go unequal before an attachment can, so the two numbers are consistent rather than in conflict.

And a ulp is the gap between one number a computer can store and the next one up — the subject of the next chapter. Calling the split “above ulp scale” is ruling out a suspect: 0.03 is enormously larger than anything floating-point rounding on this lattice can produce, so whatever caused it, it is not the arithmetic slipping in the last bit and it is not index arithmetic. The comment names what is left: “mesoscopic wall physics”. It is the walls.

And a sting in the tail, also asserted (line 189): by tick 400 the overall symmetry number is back to exactly 0, because the lagging mirror partners catch up. So the full metric at the end of a run that demonstrably broke at 270 reads clean. That is why the gate does not rely on sampling it — the runner's default is one full symmetry metric every 1000 ticks (runner/src/main.ts line 167), and a run like this one could slip between two of them. The comment says so: “the per-tick delta check is load-bearing, not belt-and-braces.”

Two lessons, and neither is about snowflakes. First, “the test failed” does not mean “the code is wrong”; sometimes the experiment is impossible, and the obvious diagnosis — index arithmetic, where everyone's suspicion goes first — was the wrong one. Second, an automated metric caught something an eyeball would have waved straight through: a boundary-mass difference of 0.03 between two cells does not look like anything at all. There is nowhere to hide inside the number either: the symmetry metric moves in whole cells, so its smallest possible nonzero value is 2 divided by the number of cells in the crystal — because a mismatch costs you a whole cell and its partner, never a fraction of one — and “there is no meaningful ‘small but nonzero’” (core/src/metrics.ts lines 47–48). It is zero, or it is a failure.

The rule that fell out of it is now written where the next person will trip over it: “Exact D6h symmetry gates require hexPrism. A box footprint and its walls are not a sixfold-symmetric environment” (AGENTS.md lines 263–265). The runner defaults to hexPrism; the solver class itself still defaults to box, “so tests must choose intentionally”.

Nineteen, not twenty

One last thing has to be sixfold before any of the machinery can be trusted: what you start with. A run begins from a seed — a small patch of cells declared to be ice before tick zero. If the seed is lopsided, the symmetry test is measuring your typing rather than your physics.

The canonical seed is a flat hexagonal plate of radius 2 and thickness 1. Count its cells and you get 19, following 3r² + 3r + 1 — 1, 7, 19, 37 for radii 0 to 3. The G-G paper says 20. The project's notes record that as an erratum, in one line in the house rules: “The canonical radius-2, thickness-1 seed has 19 sites. The paper's ‘20’ is an erratum” (AGENTS.md line 262).

What makes that an erratum rather than a disagreement is that it can be settled without running anything. A 60° rotation moves every cell except the one at the very centre. So the cells of any sixfold-symmetric set fall into groups of six, plus possibly the lone centre — which means the number of sites is always a multiple of 6, or one more than a multiple of 6. The code comment states it exactly: “any C6-symmetric set has |S| = 0 or 1 mod 6”. Nineteen is 18 + 1. Twenty is neither, so no arrangement of 20 cells anywhere on this lattice can be sixfold symmetric.

The response was not to hard-code 19 and move on. The same comment continues: “Seed size stays a parameter so the 20-site variant can be run deliberately; the symmetry metric rejects it.” The unusable configuration stays reachable, and the instrument that catches it stays pointed at it.

Still unsettled

“Sources are checked, not trusted” has to include this page and the project it describes. Every review in this project to date has been an LLM review — including the two-reviewer process that checked this chapter. The project treats that as a disclosed limitation, not as a substitute for review by a human domain scientist, and no human domain scientist has yet read any of it. Phase 6, the validation sweep, is in progress; Phase 7, the product, has not started. Nothing in this chapter is evidence about nature. It is evidence about whether the apparatus can be blamed.

All of this rests on a word used repeatedly here and never examined: that the symmetry error is exactly zero. A grid can be perfectly hexagonal, a room perfectly symmetric and a seed perfectly balanced — and two mirror-image cells can still disagree, because adding the same six numbers in a different order does not always give the same answer. The next chapter is about the last bit of a floating-point number.
