The Flaw in the Last Bit

Six arms should be identical. Why did one of them end up a cell longer than its siblings — and what does the sixteenth digit of a number have to do with it?

~18 min read 6 original graphics all of them interactive

By the end you will be able to

  • Explain why a symmetry that holds in exact arithmetic still has to be made to survive evaluation.
  • Say why “negligible rounding error” is never negligible in a system that contains a threshold.
  • Describe reproducibility as a design constraint chosen for a comparison that had not happened yet, rather than as tidiness.
  • Choose test conditions that amplify a defect instead of conditions that flatter the code.

A word you should not have let past

The last chapter finished on a claim: on the hexagonal-prism domain, the simulated crystal’s symmetry error is exactly zero. Not small. Zero.

You should be suspicious of that. Computers are famously bad at “exactly”. Ask one for 0.1 + 0.2 and it will hand back 0.30000000000000004. So what is being measured, and how can the answer be a flat zero?

Here is the measurement, written down in core/src/metrics.ts just above the function that computes it:

symmetry error = maxg |A Δ g(A)| / |A| = maxg 2(|A| − |A ∩ g(A)|) / |A|

where
A
the set of lattice cells that are currently ice
g
one of the three symmetry moves the crystal is supposed to survive: a 60° turn (rot60), a reflection (mirror), and a top-to-bottom flip (zmirror)
g(A)
the ice set after that move is applied
Δ
symmetric difference — the cells that are in one set but not the other
| |
how many cells

core/src/metrics.ts, lines 43–48 (the D6h symmetry error block)

Those three moves are the D6h group from the last chapter, turned into a measurement. Now read the shape of it. The numerator counts cells. You cannot be out by half a cell. So the metric’s own comment can say something that most error measures cannot:

“Exactly 0 iff A is invariant under the full group; the smallest nonzero value is 2/|A|, so there is no meaningful ‘small but nonzero’.”
— core/src/metrics.ts:47–48

For a crystal of five thousand cells the smallest non-zero reading is 0.0004. Between that and zero there is nothing. The metric either says perfect or it says one cell of your crystal is in the wrong place. That removes the option of shrugging at a small number.

Key idea

A measurement that can only return zero or “at least one whole cell wrong” is a measurement you cannot negotiate with. Everything in this chapter is what it took to keep it at zero honestly.

Adding is not adding

A float64 — the number format this solver runs on — stores about sixteen decimal digits. When you add two of them, the true answer usually needs more digits than that, so the machine rounds to the nearest storable value. The gap between two neighbouring storable values has a name: one ulp, for “unit in the last place”. It is the smallest difference a number of that size can have.

Now the consequence that matters. Because every addition rounds, (a + b) + c and a + (b + c) can land on different values. Addition in floating point is not associative. The order you add in is part of the answer.

That sounds like a curiosity. Here is what it looked like in this project. A calibration run at −5 °C, with the random noise switched off, reported a symmetry error of 0.020915 — where every neighbouring grid point reported exactly 0. Instrumenting the solver stage by stage produced this, captured at growth step 14 of a 32³ run — a cell, and the cell you get by rotating it 60°:

The decision record states it in one line: “Same operands bitwise; (a + b) + a against (a + a) + b; the results differ by one ulp.” Nothing about the two cells was different. Not the physics, not the inputs, not the code. Only the order in which three numbers were added.

And the way that was confirmed is worth copying: “Re-summing the image’s operands in the source cell’s direction order reproduces the source value bit-for-bit, which is the decisive check — nothing else about the two cells differs.” That is what closing an investigation looks like: not “this seems to be about rounding”, but a manipulation that makes the difference vanish and come back on demand.

Why a rotation reorders a sum

Why would two cells ever add the same numbers in different orders? Because the code walks the neighbours in a fixed order — and a rotation moves the numbers between slots.

The routine at fault gathers its inputs in this fixed sequence of lattice directions: +i, −i, +j, −j, +i−j, −i+j, +k, −k. A 60° rotation about the centre sends +i → +j → −i+j → −i → −j → +i−j → +i. In terms of positions in the list, that is the cycle (1 3 6 2 4 5) — and, as the decision record puts it, “that cycle is not order-preserving”. Slot 1’s number moves to slot 3. The multiset of values is identical; the sequence is not.

So the fix cannot be “use more digits”. More digits still gives you an order. The fix has to make the answer a function of which numbers are being added, never of their order. There are two cheap ways to do that, and this codebase uses both.

The first way is pairing. In the plane, the six neighbours come in three opposite-facing pairs, and every symmetry move of a hexagon sends a pair to a pair — it can swap the two members, and it can send a pair somewhere else, but it can never split one. Adding two numbers is commutative: a + b and b + a are bit-for-bit identical, because there is only one rounding and it does not know which number came first. That leaves three pair-sums, and the second way handles those: sort them, because a sorted list depends only on the set of values, not on where they came from. The whole thing is about twenty lines of the diffusion step — three pair sums, a hand-written three-way sort, and one divide:

d′(x) = ( ( ( own + lo ) + mid ) + hi ) / 7

where
own
the cell’s own vapour value
lo, mid, hi
the three opposite-pair sums east+west, ne+sw, se+nw, sorted smallest to largest
/ 7
the cell plus its six in-plane neighbours

solver-cpu/src/gg-solver.ts:837, verbatim: out1[x] = (((own + lo) + mid) + hi) / 7;

That file’s header states the reasoning before the code, and its last sentence is the whole point of this chapter:

“Step (1a) therefore sums opposite-direction PAIRS (e+w, ne+sw, se+nw — pairs map to pairs under every D6h generator, and within-pair order is commutative hence exact), then adds the three pair-sums in sorted order. Symmetric cells round identically, so the gate’s ‘exactly 0’ is structural, not luck.”
— solver-cpu/src/gg-solver.ts:28–34, determinism decision 2

Here is the sting. That comment was written in Phase 2. The routine that broke was added two phases later, by a different piece of work, and it never inherited the rule. The decision record says so in one flat sentence: “So the rule was already written down; the boundary operator simply never inherited it.” Knowing about a hazard, and having defended against it once, is not the same as being protected from it.

The repair could not reuse the pairing trick: that second routine sums a variable subset of eight directions with no pairing structure to exploit. So it uses the other guarantee, sorting its operands into ascending order — by insertion sort, over at most eight values — before adding them. Same principle, different mechanism. Then the record adds the sentence that is the reason it exists: “Any future neighborhood reduction inherits this rule. A reduction over a set that a D6h generator permutes must be a function of the multiset — by pairing, by sorting, or by an equivariant construction — and stating that here is the point of the ADR, because the same omission has now happened once.”

Careful

The obvious fix is to add more carefully — compensated summation, which tracks the rounding you threw away and adds it back. The project uses exactly that elsewhere, for measuring total mass. It was rejected here, by name: “A compensated sum is more accurate but still order-dependent, so it would shrink the asymmetry without eliminating it, and ‘small but nonzero’ is precisely the state the symmetry metric was designed to refuse” (ADR 0023, Alternatives considered). More accuracy was not the goal. Order-independence was.

Break it yourself

Arguments about rounding are easy to nod along to and hard to believe. So: break it.

Below is a small grower running in your browser. It is not the project’s solver — it is a two-dimensional toy on the same hexagonal lattice, with a relaxation step and a threshold. The first dropdown changes one thing: the order in which each cell adds up its six neighbours. Geometry, seed, threshold and step count are identical across all four settings.

Two things should have happened. First, on canonical pairs the disagreement count sits at zero for all fifty steps — not a small number, no number. Second, on any of the other three orders it leaves zero at step 2 and climbs into the hundreds within a dozen steps, while the crystal’s symmetry error still reads 0. All four settings finish with the same number of cells attached.

That second observation is the thing worth taking away. The field underneath the crystal was already asymmetric; the crystal had not noticed yet. The project measured the same gap on the real solver:

“The field asymmetry is chronic: at 32³ the field loses exact D6h invariance at growth step 14, while the attached set stays invariant through step 40. […] Of three v5 grid points examined, one broke and two did not.”
— ADR 0023, “How often the field defect reaches the attached set was measured, not assumed”

Eventually the rounding does surface, and the record traces the whole route in the solver’s own variable names — read sigma_b as how hungry the surface is, alphaHK as how readily a molecule sticks, f as how full a cell is, and raw >= room as “this cell now has more ice arriving than it has space for”: “That ulp enters sigma_b, then alphaHK, then the fill rate, then the accumulating fill fraction f. Growth amplifies it. Eventually one member of a symmetry orbit crosses raw >= room a step before its images, the attached set loses D6h invariance”. One arm attaches a cell ahead of its five siblings. The sixteenth digit has become a whole cell of ice.

How we know

Now switch the demo’s second control from “every step” to “only the final crystal”. The broken run reports clean — because what is being reported then is the end-of-run crystal metric, and in this toy the crystal never does break. What broke, at step 2, was the field underneath it.

Do not read the demo’s counter as the project’s per-step check, though: they ask different questions. The counter above compares the entire vapour field bit-for-bit against its own rotated and mirrored copies, which is stricter than anything a real run prints. What the solver prints beside symErr= is deltaSymClean, and that asks something narrower — is the set of cells that attached on this tick itself D6h-invariant? The reasoning is written above the function: if the crystal is invariant and every increment to it is invariant, the crystal stays invariant, and checking the increment costs work proportional to the increment rather than to the whole crystal, “which makes ‘symmetry error exactly 0 across the entire run’ affordable”. The full metric of this chapter’s opening equation is still run too, “periodically and at the end as belt and braces” (core/src/metrics.ts:84–90).

That distinction is what lets the decision record say two things that sound contradictory. The field asymmetry is “chronic” — and yet the two re-run v5 grid points “returned deltaSymClean=true for both. They were genuinely clean runs, not lucky stops.” A field check would have called those runs broken. The attachment-delta check called them clean, and it was right to. The rule that comes out of it is stated flatly: a v4/v5 symErr = 0 “is a snapshot at the stop instant and does not establish that the run stayed symmetric, whereas deltaSymClean does”. So both checks are kept, and the per-tick one is reported on every line the run prints.

One more detail, and it is the most transferable thing in the investigation. The bad run was not silent. The solver printed deltaSymClean=false on the same line, and a heartbeat had been printing deltaSym=false from step 78. What went wrong was downstream: the calibration harness parsed only symErr= out of that line and threw the rest away. In the record’s own words, “The defect is in the solver; the silence was in a coordinator-only probe.” An alarm nobody reads is not an alarm.

The same mistake in a different disguise

Here is the part that makes this a chapter and not an anecdote. The same mistake was made again, the same day, by the decision record that cites the first one.

A different piece of work needed the distance from the crystal’s centre to each cell on the outer boundary. Distance is obviously the same for every cell in a symmetric ring. So it was computed the obvious way: turn the cell into x, y, z coordinates and take the square root of x² + y² + z². Exactly right in exact arithmetic. Not right once evaluated.

On the cell it opens with, four of the six rotated copies come out holding a different number in the left-hand column. Run the scan and the page sweeps 84,035 rotated pairs and reports the worst gap it finds: about 7 × 10−15 — one ulp, at those distances — between two values that are supposed to be the same value. The repository records the identical magnitude: “symmetry-equivalent shell cells came out differing by up to ~7e-15”. The right-hand column never disagrees at all, because the squared distance can be written as a whole number, di² + di·dj + dj² + dk², and the rotation and the reflection turn whole numbers into whole numbers with nothing to round.

Two instances, two different disguises, and so the rule got promoted out of both and written in general form at the top of the contributor guide:

“Anything a D6h generator maps onto itself must be computed so that the invariance survives evaluation, not merely so that it holds in exact arithmetic (gg-solver determinism decision 2; ADRs 0023 and 0024). This has now been got wrong twice, in two different ways, so it is stated in the general form and both instances are named below. The cheapest guarantee is to key the value to something the group preserves exactly — a multiset, or an integer.”
— AGENTS.md:130–134

Choosing the test that fails

How was the second one caught? Not by the test suite as it stood. It was caught because somebody ran the code at an uncomfortable setting.

The fill-CFL is how big a bite of time each growth step takes. The working value is 0.1. Nothing in the code caps it at any particular number — the solver only insists that it be “finite and in (0, 1)” (solver-cpu/src/lk-solver.ts:452) — but 0.2 is the top rung of the registered timestep ladder, the largest step the project tests at (research/phase6-convergence.md §2, which runs 0.2, 0.1, 0.05 and 0.025). The erratum gives the mechanism in a sentence: “A larger step lets many cells cross the attachment threshold together, which is what turns a ulp into a split orbit.” More cells at the threshold at once, more chances one of them lands on the wrong side of it by a single bit. AGENTS.md draws the moral: “a symmetry regression test that does not run at the largest admissible step is not testing much.”

The other axis is the far-field condition — how the model decides what the vapour is doing out at the edge of the box, far from the crystal. dirichlet pins every edge cell to one fixed value. monopole-matched gives each edge cell its own value based on how far it sits from the centre — and it is that distance, computed the obvious way, that carried the bug. Chapter 23 comes back to why the choice matters at all; here it only matters that one of the two settings runs the defective line and the other does not.

Three of the four choices are green, and the sensible-looking one — the setting the solver actually runs at — is among them. So the regression test was deliberately written at the wrong setting. Its name says so:

it("holds symmetry at the LARGEST fill-CFL, which is what amplifies a ulp shell error", …)
“Testing only at the working cfl of 0.1 missed it for exactly that reason, so the regression test runs at the amplifying setting deliberately.”
— solver-cpu/test/monopole-far-field.test.ts:130–134

And then a second test was added that does not grow a crystal at all. It builds the outer shell, walks every shell cell’s rotated and mirrored partners, and asserts that they hold bit-identical distances — “which catches the regression with no growth at all, where the end-to-end symmetry test only catches it once a timestep amplifies it”. It even checks that it did some work: the final assertion is that more than 100 pairs were compared, so the test cannot pass by having examined nothing.

Two nets over the same falling bug, with different mesh. The project keeps both.

Randomness that does not care who goes first

There is one more place order could sneak into the answer, and it was closed before it was ever a problem.

The model has an optional noise term — a tiny random nudge per cell per step. The obvious way to build that is a random-number generator you call over and over, each call advancing a hidden internal state. That is what almost every language ships. This project refuses it, and the file says why in its first ten lines:

“The output is a PURE FUNCTION of the tuple (seed, cellIndex, tick, streamId) — a murmur3-style integer hash, never a sequential stream. A stream PRNG makes a noise realization depend on iteration order, which GPU threads do not have; a sequential choice here would quietly foreclose Phase 5’s oracle-vs-GPU comparison on every noise-on run.”
— core/src/prng.ts:1–10

Read the timing of that. Phase 5 is where the fast graphics-card engine gets checked against the slow readable one, and thousands of card threads run in no particular order. A generator that depended on call order would hand the two machines different noise, so the two crystals would differ and no one could tell a real disagreement from an artefact of scheduling. The choice was made in the scaffolding, several phases before the comparison it protects.

The three integers in that panel are not decoration. They sit in the test suite with a blunt comment above them: “These pin the algorithm. If they change, every recorded noise-on run is invalidated.” A run’s randomness is completely described by two numbers — the seed and the noise amplitude — both of which are written into every saved checkpoint. Same seed, same noise, in any order, on any engine: the hash uses only integer operations, and those “are exactly specified by ECMA-262, so this is bit-identical across engines” (core/src/prng.ts:8–10).

Note the size of that claim. It is about the noise, not about the crystal — the crystal is decided by a great deal of arithmetic that is not integer-only. The prng file makes the distinction itself, calling its own guarantee “stronger than the pinned-oracle determinism scope the charter requires”, which only makes sense if the charter’s scope is narrower. The next section says how much narrower.

Still unsettled

Where does a real snow crystal’s asymmetry come from? Nobody in this project claims to know, and the model does not settle it. What is settled is how the model is allowed to be asked. Noise deliberately destroys sixfold symmetry — it is drawn independently per site, so of course it does — and that is not a bug to be reconciled with the symmetry gate, because the rule was written down in advance: the Phase 2a symmetry gate runs noise off, and studies specifically targeting natural asymmetric branching may run it on. The machinery documentation ends that part in three words — “Two different experiments” (docs/gg-machinery.md:341–343). Which experiment the real world is running is the part still open.

What “exactly zero” buys, and what it does not

Be precise about the size of the claim, because this is exactly the kind of engineering that invites overstatement.

Bitwise reproducibility is not claimed everywhere. The charter scopes it narrowly: “Bitwise reproducibility is claimed only for the oracle pinned to one engine (Node/V8): the JS spec does not guarantee bit-identical Math.exp/Math.pow across engines, and LibbrechtKinetics leans on exp().” Comparisons against the graphics card, or across engines, use stated tolerances instead. The fix in this chapter did not extend that scope by one inch. It made the symmetry claim inside that scope true.

The fix changed arithmetic, not physics. That was checked rather than asserted: the new summation order and the old one reach the same state at the same scale, and the test that says so is in the suite — “v6 is an ordering change only: it reaches the same state v5 does at this scale” (solver-cpu/test/lk-solver.test.ts:1182). That is one scale, not a guarantee. On the configuration that opened the investigation the attached count moved 765 to 749, and the record refuses to let that pass as noise: “v6 will differ from v5 wherever the split orbits fall differently, and any v5 calibration number carried forward has to be re-measured rather than assumed.” What was changed was the order of an addition. What that does to any particular crystal still has to be measured.

It also cost about 5% in runtime, measured properly, with the honest note that the run-to-run spread on that machine was about 14% — larger than the effect — so “~5% is the right order and the third digit is not available from this machine”.

And it was fixed in one lane only. The same defect sits in the graphics-card version of that routine, and it was deliberately left there: “The WGSL lane is not ported. […] So the shader defect described above is registered, not repaired” (ADR 0023, Decision). In the 32-bit arithmetic the card uses, one ulp there is about 1.2×10−7 relative rather than 2.2×10−16 — a much bigger last bit, and this chapter has just spent four sections on how a single ulp gets amplified into a whole cell of ice, so nobody should read that size as a bound on the damage. The record does not offer one. It states a consequence instead: the card is Phase 6’s labelled diagnostic rather than its sweep engine, and the untouched operator is “a second declared difference beside f32 arithmetic and the relaxed divergence tolerance: the GPU lane can corroborate a trend, and cannot be compared value-for-value against a v6 sweep.”

And none of this says the physics is right. A symmetry error of exactly zero says that the arithmetic did not decide the answer. It says nothing whatever about whether the equations being evaluated are nature’s equations. Those are two different claims and they are supported by two different kinds of evidence. When the validation sweep later reports that every one of its 204 runs held symErr = 0 with noise off, that is a statement about the instrument, not about the world. Keep the two apart; the rest of this section depends on it.

For orientation: that sweep is Phase 6, the validation phase, and it is in flight. Phase 7, the product layer, has not started — the progress ledger records it as one unticked box. Nothing on this page describes a finished thing.

How we know — and who checked

Every finding in this chapter was produced and reviewed inside the project’s own process, which requires every review round to record the reviewing agent’s model, what it independently re-executed, and “what it did not check, stated as a limit of the evidence rather than left implicit”, and which prefers a different model from the one that wrote the code on any review that carries a gate (AGENTS.md:389–394, Rule 10). That process has a limit the project states plainly and this page will not soften: every review this project has had, internal or external-facing, is an LLM review, including the two-reviewer pass over this page. The project’s own words: “At least one human domain scientist reads any manuscript before submission. All reviews to date, internal and external-facing, are LLM reviews; for publication that is a disclosed limitation, not a substitute” (docs/stretch-sharing-and-investigation.md:217–219). No human domain scientist has read this work. That is a disclosed limitation, not a defence.

That last row is not housekeeping. The old policies were left bit-unchanged on purpose: accepted results from earlier phases ran under them, and quietly “fixing” the code underneath an old result would make a stored file claim a policy it never ran. Fixing a bug and preserving the record of the buggy runs are separate obligations.

Everything so far has been about the machine’s arithmetic — the grid it counts on, the order it adds in, the randomness it refuses to let drift. None of that decides what a physical growth rate is supposed to mean once you have chopped space into cells and time into steps. The next chapter is about that seam, and about the move that happens there: temperature stops being a label written on the outside of a run and becomes an input to the rate of every boundary cell, recomputed every step. That is the move that makes the whole project capable of being wrong.
