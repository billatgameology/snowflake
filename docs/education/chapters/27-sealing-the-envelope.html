Chapter 27

Sealing the Envelope

When the result comes back disappointing, what makes a later rule change auditable and prevents old evidence from silently following it?

~19 min read 7 figures 6 interactives

By the end you will be able to

  • Explain why the timing of a decision changes its meaning, even when the decision itself is word-for-word identical.
  • Recognise a partial safeguard that is worse than no safeguard, because it looks like protection.
  • Tell “wrong about the world” apart from “wrong about the evidence”, and find the two wired to different exit codes.
  • Say why making cheating expensive and visible is a stronger design than making it forbidden.
  • Follow a saved checkpoint through framing, schema, state, and experiment-context checks, and explain why a file can pass one layer and fail the next.

The same decision, twice

Here is a rule. A model point that lands within 1 °C of a reference boundary does not count, in either direction.

Read it once as a rule written before any run happened. It is careful: the reference diagram’s own boundaries are known only to about half a degree, so demanding that the model locate a habit flip — a temperature where the crystal stops growing plates and starts growing columns, or the reverse — more precisely than the reference does would be unfair.

Now read the same sentence as something written after 204 runs came back, with the disagreements sitting near the boundaries. It is an excuse. Not a different sentence — the same sentence. Only the order of events changed.

The Phase 6 plan says this out loud, before the sweep it governs:

“The band must be registered before any sweep runs, because applied afterwards the same rule becomes ‘the points that disagreed happened to be near a boundary’ — exactly the post-hoc rationalisation the §3.2 freeze exists to make impossible.”

docs/plans/phase-6-nakaya-validation.md, “Reporting rules that hold for every protocol”

That historical wording overstates what a freeze can do. Registration cannot make post-hoc reinterpretation or misconduct impossible. A versioned freeze instead makes authorized changes auditable and undisclosed byte drift detectable; whether the registered list was complete remains a separate scientific question.

This is the whole chapter in one idea. A scientific claim is not just a number; it is a number plus the order in which the choices were made. So before the validation sweep ran, the project wrote down every choice it could identify that could move the answer, turned the list into a single 64-character string, and pointed a program at that string with instructions to refuse to produce evidence if one byte of it moved. Whether the list was complete is a different question, and the last third of this chapter is the day the answer was no.

Two words first, because the rest of the chapter leans on them. The project’s files live in git, which stores the history as a chain of snapshots. Each snapshot is a commit, named by a fingerprint of everything in it plus the fingerprint of the one before — so a commit’s name depends on its entire past. HEAD is git’s name for the snapshot you are standing on now.

Key idea

Deciding how you will mark the exam is not cheating. Deciding it after you have seen the answers is. Since nobody can prove from the outside which order it happened in, the project made the order checkable: the marking scheme is hashed, and the hash is recorded in a commit that must sit upstream of the commit that ran the exam.

Deliberately, there is no result in this chapter. You will finish it knowing exactly how the exam is marked and not knowing the mark. That wait is the point: when the number arrives in chapter 28, you will have watched the rules being picked, so “they probably picked the ones that suited them” is not available to anybody.

The list

The charter names what has to be frozen. It is not a vague instruction to “be careful”; it is a shopping list, and it ends with a price tag:

“Before the first validation sweep runs, freeze docs/libbrecht-parameters.md and a written validation protocol: the T/σ grid; the far-field boundary condition … how a model habit class is scored against the reference regimes … the crystal size at which habit is measured — habit is size-dependent, so measuring at a stated maximum dimension is what keeps comparisons apples-to-apples; metric thresholds; domain budgets; and pressure, physical seed size, Δx, the named surface policy, the fill-CFL bound, the diffusion residual tolerance and its norm, the divergence-identity tolerance, the relaxation-sweep cap, float precision, the parameter interpolation scheme, noise amplitude, seed-ensemble size, the model/code version (commit hash), and the uncertainty-reporting scheme. Any post-freeze edit to parameters or protocol requires a logged ADR and invalidates prior sweep results — the full sweep re-runs. This is what makes ‘a negative result is a result’ survive contact with a disappointing plot.”

project charter.md, §3.2, Phase 6 item 1

Most of those are the numerical settings from chapters 20 to 26. You are not expected to follow each one. What matters is that there are twenty-five of them, that each has a written-down value, and that the price of changing one afterwards is the whole sweep again. (ADR is the project’s name for a numbered decision record — an architecture decision record. Decision 0025, below, is one.)

In the repository the list is not prose. It is an array called PHASE6_FREEZE_LIST in runner/src/phase6-protocol.ts, each entry carrying an id, a group, a status of registered or pending, the requirement in the words of whichever document demands it, the value chosen, and the source that produced it. Twenty-five registered rows today; the revision log records the first seal as twenty-one.

Read a few. The interesting column is the last one.

One property matters more than any single row. The function that assembles the list into a hashable document throws an error if any row is still pending. It “refuses to exist while any required item is pending, so a sweep cannot quote a protocol hash the freeze has not actually earned.”

The seal

A list anybody can edit is a promise. To turn it into a fact, the list is written out as one long piece of text, always in exactly the same way — programmers call that serialising — and run through SHA-256: a function that turns any text into a fixed 64-character fingerprint, where changing anything at all scrambles the output unpredictably.

“One fixed way” is doing real work there. The list is written as JSON, a plain-text format where every value sits under a named label called a key — "noiseAmplitude": 0. Two people can write the same JSON in a different order, with different spacing, and mean exactly the same thing, so a fingerprint taken naively would differ for no reason. The repository’s serialiser removes that freedom: “Canonical UTF-8 JSON: recursively sorted keys and no insignificant whitespace” (runner/src/gate4-evidence.ts).

Its reader is stricter. Turning text back into values is called parsing; this one parses the file, writes the result out again in canonical form, and demands the two be identical character for character. That one comparison “rejects duplicate keys, alternate number spellings, reordered keys, trailing data, and whitespace changes.” Two files that mean the same thing hash the same; two that mean different things cannot be made to match by tidying the formatting.

Type into the list below and watch the seal break.

The real seal covers the manifest built by phase6ProtocolManifest(), and its fingerprint is stored as a constant. When this chapter was first written that constant read 8aeb2b80… (updated below — it has since moved), with a comment explaining what it is for:

“Pinned in runner/test/phase6-protocol.test.ts, so changing any registered value — a temperature, a fraction, a tolerance, a justification string — fails there rather than silently producing sweep evidence under a protocol nobody agreed to.”

runner/src/phase6-protocol.ts, above PHASE6_PROTOCOL_SHA256

Updated

8aeb2b80… was the live pin when this chapter was written. It no longer is, and the reason is worth having, because it is this chapter’s own mechanism being exercised for real. Decision record 0033 (2026-07-29) split the manifest in two: a values hash over the twenty-five rows’ registered numbers, thresholds and schemes — the one a re-sweep is priced against — and a justification hash over their prose, correctable by a logged decision record without invalidating anything, “provided the values hash is unchanged by it.” Decision record 0034 then used exactly that door: one freeze row had justified part of the sigma-axis upper bound with figures computed under a different, superseded parameter set, and under the registered one the argument actually reverses. The corrected sentence sits in the row now. Because the combined manifest still embeds prose by construction, fixing it necessarily moved the combined fingerprint — 8aeb2b80… → 2b94aa5f… — while the values hash, the one that actually gates a re-sweep, did not move at all. 8aeb2b80… is not gone: it is kept as a named historical constant, reproducible by checking out the commit Arm 1’s evidence names and recomputing the manifest there, and it is still the correct answer to “what fingerprint did Arm 1 run under” everywhere the rest of this chapter and chapters 28 and 29 use it that way. It stopped being the correct answer to “what is the live pin today.” One footnote on the footnote: the decision record that made this split first claimed the combined hash would be “preserved, not retired” — an over-strong claim its own successor record corrected less than an hour later, once a real prose fix proved it false. Even the correction mechanism got corrected in the open, which is this chapter’s whole argument working on itself.

The pin is enforced by a test that recomputes the fingerprint from the live code every time the suite runs. Three details in that test matter more than the rest of the machinery, because each is a way the seal could have looked convincing while being useless.

First: the grid goes in by value, not by size. The manifest embeds the actual temperatures and humidity fractions, not the count of them, because “a manifest hash that moved only when a count changed would not notice a temperature or a fraction being swapped for another.” A seal that counts the pages does not notice a rewritten page.

Second: the hash must not be inside the thing it hashes. That is a literal line in the test file, and it is not pedantry: writing the fingerprint in changes the document, which changes the fingerprint, which makes the one you just wrote wrong. The freeze commit is named by the commit that follows it for the same reason — “a commit cannot contain its own hash.”

Third, and this is the one to remember: a partial seal is worse than none. While the freeze was being amended, someone noticed that the newly written scoring rule had been registered as text but never included in the hashed manifest. The grid was sealed. The rule that turned runs into a verdict was not.

Careful

“A hash that pins the grid while leaving the rule that turns runs into a verdict editable is worse than no hash, because it looks like protection.” (runner/test/phase6-protocol.test.ts.) An unsealed protocol is honestly unsealed — a reader knows to be sceptical. A protocol with an impressive fingerprint on the front and an editable marking scheme in the back invites trust it has not earned. When you audit a safeguard, the question is never “is there one?” It is “what exactly is inside it?”

One last piece of engineering that sounds trivial and is not. The parameter table is hashed with its line endings normalised to LF, because Windows and Linux store the invisible end-of-line character differently. Without that step the fingerprint would depend on which machine checked the file out — and would fail on exactly the second computer the project needs to reproduce itself on. Normalising “makes the hash a statement about the physics, which is what it is for.”

The four refusals

A seal is only useful if something checks it before the work starts. In this project that something is a function called phase6SweepPreflight, and the file it lives in introduces itself like this:

“It fails closed. … A sweep that cannot prove which protocol produced it is not evidence, and the charter’s whole pre-registration argument rests on that being checkable rather than asserted.”

runner/src/phase6-sweep.ts, file header

The sentence the ellipsis swallows lists four checks, each designed to reject a different mismatch when the correct preflight actually runs. Freeze complete rejects a protocol with blanks in it. Hash matches the pin detects an edited registered value. Freeze commit is an ancestor of HEAD rejects writing the protocol after the runs and backdating it — git’s history is a chain, and a commit cannot be an ancestor of one that already existed without changing history. Tracked tree is clean rejects running with uncommitted edits: source you have not committed is source nobody else can inspect, and without this check it would defeat the other three.

How we know

The sweep report records the four checks as facts about the run that produced it: “The preflight refused to produce any of it until the freeze was complete, the manifest hashed to the registered pin, the freeze commit was an ancestor of HEAD, and the tracked tree was clean” (research/phase6-sweep-report.md). Its provenance table names the protocol fingerprint 8aeb2b80… — “25 freeze rows”, the same pin you saw in the last section — the execution commit 390fe35…, and the freeze commit e2f1bfca…, “verified an ancestor of the execution commit”.

There is a second sweep, though, and keeping the two apart is the one piece of bookkeeping the next two chapters ask of you. An earlier 204-point sweep exists, and its report named a different fingerprint: the twenty-four-row 9aa2e7c1…. That is the sweep that was thrown away. Decision record 0031 records the move as “9aa2e7c1… → 8aeb2b80… (24 freeze rows → 25)”, and § Try to cheat is the story of why the list gained that twenty-fifth row. Hold on to which hash belongs to which: 9aa2e7c1 is the withdrawn one; 8aeb2b80 identifies the corrected historical Arm 1 run. Neither is the future R15 replacement-gate pin.

The marking scheme

The hardest thing to freeze is not a number. It is the rule that turns runs into a verdict. On 2026-07-27, an independent review — recorded as an LLM review; the last section says what that is worth — found that the freeze had registered the grid, the band, the thresholds and the uncertainty scheme, and had never registered how a model habit class is scored at all. Decision record 0025 filled the hole, written while the answer was still unknown: no sweep had run at the time of writing. Its freeze row covers four items — “the accepted-class matrix, the treatment of neutral and invalid, the flip predicate, and the headline scope” (the agreement-scoring row). Take them in turn.

1. Each reference regime accepts a named class. The reference diagram divides temperature into four bands at −3.3, −9.9 and −21.5 °C: plates, then columns, then plates again, then a mixed cold band that the source labels “Columns and Plates”. The first three accept exactly one model class. The fourth accepts both.

2. neutral counts as disagreement. The model has a third outcome: the aspect ratio defined in the table above landing strictly between 0.6667 and 1.5, meaning neither a plate nor a column. It would be very convenient to call that an abstention and leave it out of the score. The record refuses, and gives the reason:

“The reference names a habit in every regime. The neutral band is ours, not the reference’s, and a model producing neither habit has failed to reproduce the reference. Scoring it as abstention would let a model that never commits report perfect agreement on whatever few points it did commit on.”

docs/decisions/0025-phase6-agreement-scoring-rule.md

The neutral count is nevertheless published separately, so a reader can always tell “wrong habit” from “no habit” — which, as the record puts it, “is the distinction that carries the science.”

3. invalid is excluded — by name. A run that tripped the 65% domain-contact guard — the chapter-23 rule that throws out a run whose crystal has grown too close to the wall of its box — or broke the six-fold symmetry check, or failed to converge, is thrown out: “it is not a statement about the model; it is a run that did not happen.” But 0025 is explicit that such runs are “excluded by name rather than dropped silently”, and that difference is the whole difference between a safeguard and a laundry chute.

4. Flips are bracketed, and how many there are is itself a result. This matters most in the next chapter. A flip is reported not as a temperature but as an interval: the span between the last temperature at which the model produced one pure habit and the first at which it produced the other, its width carried as the location uncertainty. Neutral and invalid points do not end the search — they widen the bracket, “which is the honest representation: a wide neutral span means the flip location is poorly located, and collapsing it to a midpoint would manufacture precision the data does not have” (phase6DetectFlips, runner/src/phase6-protocol.ts). Then the sentence that pre-registers chapter 28’s whole counting argument:

“The number of flips is itself a first-class result: the reference has three, and a single monotone σ0 crossing can produce at most one.”

docs/decisions/0025-phase6-agreement-scoring-rule.md

That sentence is preserved because it is what the historical freeze said, but its second clause has since been retracted. It counted crossings of σ0, while the surface law uses the full attachment coefficient alphaHK = A exp(−σ0/σsurf) on different evolving facets. An input-curve crossing therefore does not bound the number of habit flips in a coupled three-dimensional run. Flip count remains a legitimate measured output; the quoted structural explanation is not admissible to the replacement gate.

Those four are 0025’s. Two older rows do the remaining work, and the first of them registers something the four do not: what “agrees” means.

5. The registered replacement headline counts a point only if it agrees twice. Decision 0026 says a replacement-gate point is measured at the registered crystal size and also grid-extrapolated — an estimate of the aspect ratio at infinitely fine spacing from the two finest spacings in a three-spacing ladder. It admits that estimate only where the fitted convergence order lands from 0.7 to 1.5; outside that window the point is reported not-extrapolatable and carries its measured class alone. The registered rule then takes the harsh reading of the two, in capitals: “THE HEADLINE IS THE CONSERVATIVE INTERSECTION — points whose measured class agrees AND whose admitted extrapolation does not contradict it”, with the two component counts and the not-extrapolatable tally “reported BENEATH it, never as the top line” (uncertainty-reporting row of PHASE6_FREEZE_LIST). The reason is one sentence in the same row, and it is this chapter’s subject exactly: “counting agreement twice and quoting the friendlier number is the failure mode a dual report invites.” This paragraph describes the registered contract, not an executed result. Neither historical 204-row sweep called the ADR 0026 extrapolation operator or wrote its outputs, so 3/90 and 54/90 are measured-only counts, not the registered headline.

The last row is the oldest. The ambiguity band was already in the first twenty-one-row seal, and 0025 published its budget “alongside the existing 28/6 split” rather than inventing it. Its half-width was fixed by formula:

w = uref + ΔT/2 = 0.5 °C + 1.0 °C / 2 = 1.0 °C

where
w
the half-width of the band around each reference boundary inside which neither agreement nor disagreement is counted
uref
the measured uncertainty on the reference boundary temperatures, ±0.5 °C as digitized from the published figure
ΔT
the frozen spacing of the model’s temperature grid, 1 °C

docs/plans/phase-6-nakaya-validation.md, “ambiguity half-width = 0.5 °C (WP1’s measured boundary uncertainty) + half the frozen T-grid spacing” — WP1 is the work package that digitized the reference figure, so that 0.5 °C is the project’s own measurement of how well it can read the published boundaries. Evaluated at the frozen grid in the boundary-ambiguity-band row of PHASE6_FREEZE_LIST.

The freeze row spells out the part that makes it a rule rather than a shield: “It cuts BOTH ways: agreement inside the band earns nothing either, because a model agreeing with the diagram only near boundaries has demonstrated nothing.”

Put those together and you can count, in advance and without seeing a single result, exactly which points the headline number is computed over. Do that now, and remember to multiply at the end: the strip below is the temperature axis alone, and each temperature is swept at all six supersaturation levels, so 15 counting temperatures × 6 = 90 headline points — chapter 28’s denominator.

What the harsh rule cost, stated in advance

Every one of those choices makes the model’s job harder, which is suspicious in its own way: it is easy to look rigorous by being gratuitously strict. So the record prices its own strictness, in the same document, before the result. Dropping the mixed cold regime removes 13 of the 28 counting temperatures, and it does not pretend this is free:

“The headline denominator drops from 28 to 15. That is a real loss of apparent statistical power and it is the correct trade: the 13 discarded points were never going to discriminate.”

docs/decisions/0025-phase6-agreement-scoring-rule.md, Consequences

The reason those 13 could never discriminate generalises far beyond snowflakes. The cold band accepts both plates and columns, so almost any non-neutral answer scores a point there, and a test you pass whatever you do is not a test. There is a deeper mismatch too: that band describes a population of natural falling crystals, while one grid point here is one deterministic crystal. Matching a mixed population with a single run is, in the record’s word, ill-posed. Then comes the sentence hardest to write before a result.

Still unsettled

“A stated limitation rather than a discovered one: the warmest Plates regime has exactly ONE counting temperature (−2 °C). It can therefore only ever score 0% or 100% and carries essentially no statistical weight… Any conclusion about the warm plate regime is a one-point conclusion and must say so.” The obvious fix — extend the grid to −1 °C for one more point — is rejected by name in the same paragraph, because −1 °C sits where the latent-heating correction — which this protocol registers as “carried as a stated systematic; not applied” — is at its largest. Buying one point with the worst systematic in the phase is called “a bad trade”.

Notice what that warning label does to the future. Whatever the warm regime scores, nobody — including the project — can present it as evidence in either direction. It was disarmed before it was fired. The record closes by listing what else it forecloses: “Deciding after results whether neutral counts. Reporting a single agreement percentage across all four regimes. Quoting a flip temperature to a precision the grid spacing does not support. Dropping an invalid run without naming it.” Four escape routes, welded shut in advance.

Try to cheat

Reading about a safeguard is not the same as pushing on one. Below is a scoring panel with four buttons. Each makes a change a real researcher would be tempted by, each edits a row genuinely on the frozen list — printed under the button — and each makes the score jump.

The fourth needs a word of explanation, because it uses a term the freeze list invented. A point is extent-fragile when its shape is close enough to a class boundary that measuring it at a larger crystal might tip it over. The historical freeze registered a one-sided rule: flag a measured aspect ratio within 0.135 below a class threshold. Its justification claimed that the extent-21→31 ladders moved only upward, but the tracked P1 ladder instead falls from 1.52632 to 1.52174. The three sampled extents do not establish convergence. A closed, symmetric audit therefore finds 59/204 historical CAK rows and 85/204 M1 rows within 0.135 of a threshold; the historical one-sided labels remain preserved. A later bounded numerical ladder returned criterion-no-pass, with its excluded ceiling strata still explicitly unverified. Flagging costs nothing. Deleting the flagged points would quietly remove the ones most likely to misbehave, which is what the fourth button does. Press them, then read the banner.

The lesson is not that those four edits are forbidden; several are things a careful person could argue for in good faith. The lesson is about when. The protocol’s revision log carries six entries registered before any sweep had run, alongside the rule that “every amendment before the first sweep is free — after it, the same change costs a full re-sweep.”

Now the fifth-button question, because the revision log answers it and the answer is not comfortable. There is a seventh entry, labelled in capitals: THE FIRST AMENDMENT THAT IS NOT FREE. Somebody found a knob that was not on the list at all — a default buried in the command-line handling that silently chose a different set of physics parameters from the one the protocol had registered. Nobody pressed that button on purpose. A default pressed it. In decision record 0031’s words, “an unregistered CLI default silently overrode a registered freeze row, through a path the freeze did not cover because paramSet was not itself a registered row” — and the bill was “the 204-point sweep of 6995868 is invalidated and re-runs.” It is a registered row now. It is the third field you typed into in the seal demo, the twenty-fifth of twenty-five, and it is in the envelope only because it was left out of it. Chapter 29 is that bill in full.

So the accurate claim is narrower than “every knob is on the list”. Nobody can prove a list of this kind complete; completeness is exactly what gets discovered the hard way. Anything on the versioned list is covered by a recomputable fingerprint, and an authorized change is required to leave a decision record and new history. Those controls make drift detectable to a reviewer who actually checks the artifacts; they do not make misconduct or omission impossible. The replacement-gate consequence is a new freeze and full rerun. Historical executed bytes remain records of what the superseded protocol produced; they are not silently rewritten or promoted to the replacement gate.

A cheat nobody had to invent

The panel above is honest about what it is: an invented model row, stamped FICTIONAL, built that way on purpose so this chapter could show the marking scheme being pushed on without printing Phase 6’s actual result early. But the paramSet story that just closed — the unregistered CLI default that silently overrode a registered freeze row — was not invented. A real audit found it, and it kept looking. What it found next is worse in kind, not just in degree: not a number nobody registered, but a condition nobody had ever checked at all — whether a run had actually reached the finish line before its shape was scored.

docs/phase6-evidence-pin-register.md is that audit: a systematic pass, committed as 49a3a81, enumerating “every surface that touches a Phase 6 evidence artifact and states what pins it.” Its method was not just reading code — “roughly seventy of the mutations were executed against a working tree or a scratch copy of the artifacts, and where execution contradicted the reading, the executed result is what is recorded.” Its first row, marked critical, is steps — the growth loop’s step cap. Decision record 0035, the fix, states the finding plainly:

“steps was registered nowhere. It reached every run from GROW_LK_DEFAULTS.steps, and mutating that default moved no manifest hash and failed none of the 100 tests then covering the sweep.”

docs/decisions/0035-phase6-run-outcome-and-input-pins.md, “The step cap — a whole fabricated diagram in about a minute of compute”

The register found no test standing in the way either — “grep GROW_LK_DEFAULTS runner/test/ returns zero hits (verified this pass)”. So the decision record reproduced the run for real, at the exact registered configuration, changing one flag: --steps 1. Here is that run’s own header, quoted character for character.

Read the header slowly, because the whole point is that there is nothing to catch by reading it harder. paramSet=CAK is the registered parameter set; dx=0.35um, targetExtent=21, seedSites=19 — every configuration token is the one the freeze list demands. symErr=0 and deltaSymClean=true: the shape is exactly D6h-symmetric. allConverged=true: the field relaxed. The only thing wrong is stop reason=step-cap step=1 … extent=5: the run was told to stop after one step, so what got measured is not a crystal at all. It is the seed itself, one layer thick, five cells across, aspect ratio exactly 0.2 by construction, carrying no temperature dependence whatsoever. Score that shape at every one of the 204 grid points and the harness, before this decision record, would have called it plate everywhere — agreeing in both plate regimes and disagreeing only in the columns regime, which is arithmetic on a fabricated shape, not a measurement of anything.

Notice what did not fail. Decision 0025’s scoring rule — the one this chapter spent two sections earning your trust in — did exactly what it was built to do with the input it was handed: agree with a plate, because the shape in front of it really was flatter than a column. The rule was never the problem. Nobody had wired anything to ask the question that has to come before scoring at all: did this run reach the size it claims to have measured?

The fix needed no new instrumentation. Every token it reads — largestExtent, stopReason — was already printed on every run and read by nothing. Decision 0035 adds two conditions to phase6ScorePoint’s invalid list, both excluding the point by name, the same discipline decision 0025 already committed this chapter to:

“largestExtent < 21 → ‘stopped at extent N, short of the registered measurement size 21 — habit is size-dependent, so this is not a smaller measurement of the same crystal’… <, not !==. Extent can rise by two in a step, so a legitimate run can end at 22, and a rule that invalidates that would be a different defect from the one being closed.”

docs/decisions/0035-phase6-run-outcome-and-input-pins.md

Three negative controls were executed against the real source, not described: the step cap (caught, as above); the solver’s hard-coded domain swapped from hexPrism to box (caught on the active-cell count, 110 592 against a registered 77 879); and the seed thickness doubled behind the same kind of silent default (caught twice — once by the new preflight check on the default itself, once again by the run-time site count). The register’s own closure log records the first in one line: “--steps 1 (was plate/AGREE/headline → now invalid/excluded)”, closed at commit b701285, “a step-capped run is EXCLUDED, and every run input is pinned.” That final historical phrase was too broad: the repair pins the registered and per-row self-reported run-configuration fields, not the complete execution environment or an immutable source snapshot.

How we know

This is not a hypothetical the audit reasoned its way to. It is a real process, spawned with one extra flag against the registered configuration, whose real stdout is what you just read — and, per decision record 0035’s own accounting, both mutated files were restored and reverified by sha256 against pre-mutation copies afterwards, so the demonstration left the working tree exactly as it found it.

This is the sequel to this chapter’s whole argument, not a footnote to it. “Try to cheat” showed four edits to rows already on the frozen list, each one caught because the list has a fingerprint to break. This one was never on any list, had no fingerprint to break, passed every hash, every preflight refusal, and the full test suite then covering the sweep — and it did all of that while fabricating a headline dramatically better than honest measurement. A safeguard that only watches the rows someone thought to write down is watching the wrong thing. The seal was never the whole safeguard; reading, by hand, what the program had been printing the entire time and had never been asked about is what closed this one.

Three exit codes

Everything so far protects the marking scheme. One thing still needs protecting: the difference between two very different sentences that both start “it failed”. A program that finishes hands the operating system a small number, its exit code; by convention 0 means success and anything else means failure. The historical Phase 6 gate contract assigned three meanings:

“A morphology miss does not change exit 0. Invalid numerics, provenance, artifacts, incomplete runs, or protocol violations exit 1. Any flag exits 2.”

docs/plans/phase-6-nakaya-validation.md, Gate contract

Under that historical contract, the model could disagree with the reference diagram at every point and still return 0, because 0 meant that the command’s execution checks passed, not that the model was right or that later replacement-gate requirements had been met. Exit 2 is subtler: the registered gate command takes no flags at all, so any flag means the thing that ran was not the thing that was registered — not a science failure and not an evidence failure, but its own category of wrong. Almost every project says “a negative result is a result”. This one has to mean it, because a program must return a number and there is nothing between 0 and 1. Try the scenarios.

The last row of that gate contract is the one most projects skip. It is not enough for the gate to pass on good evidence; it has to be shown failing on bad evidence, on demand, for each specific kind of bad. The original plan named six. WP5 later executed a seventh, aimed at the timing hazard the sweep itself disclosed:

  • a forged published verdict
  • a post-freeze parameter edit
  • rows merged from two different parameter sets
  • a domain-contacted run entering results
  • a mismatched far-field condition
  • a habit classification taken at the wrong measurement size
  • a tracked solver file edited after preflight

Each must “fail by name”, not merely make the gate refuse. A refusal saying only “something is wrong” is nearly useless: you cannot tell a caught sabotage from an unrelated bug, or whether the control you thought you were testing is the one that fired. It is the difference between a lock that resists a key and a lock that tells you which key was tried.

All seven mutations really executed. The first pass caught five and exposed two gaps: per-row output could not prove which parameter set produced it, and a row measured at the wrong size still scored normally. Commit b701285, implementing decision record 0035, pins every registered and per-row self-reported child run-configuration field and requires a size-target stop with largestExtent ≥ 21. The inequality matters: a legitimate growth step can jump from 20 to 22. Re-checking the historical Arm 1 rows found all 204 at extent exactly 21, so its measured 3 of 90 did not move. That repair governs checking and future runs; it cannot insert the per-row configuration and stop-reason fields that Arm 1 never recorded.

The timing control needed a different repair. Commit 154359d dynamically fingerprints every TypeScript source file under core/src, solver-cpu/src, and runner/src before a future sweep launches and again when it finishes, and refuses publication if the sets or bytes differ. There were 39 such files at that commit; later additions are included rather than hidden behind a hard-coded count. It detects a different named source graph at the two endpoints, such as a commit that remains landed at completion. It does not exclude a transient edit that was reverted before the final fingerprint, inherited NODE_OPTIONS, or a shadow module. R15 still owes an immutable snapshot, environment allowlist, and verified child identity. This is a forward safeguard, not a retroactive upgrade of Arm 1’s provenance.

The same instinct governs how results reach disk. The Phase 4 and Phase 5 gates each publish through their own staging function (publishEvidenceBundle in runner/src/gate4-evidence.ts; publishPhase5Lane in runner/src/gate5-evidence.ts): the bundle is built in a hidden folder, every artifact is written and immediately re-read and re-hashed, and only then is it made real by a single renameSync onto its published name. Evidence either appears complete or does not appear.

A saved run is a contract too

The same fail-closed idea reaches inside a checkpoint. Its first eight bytes must spell VCCCKPT1; the next four declare, in little-endian order, exactly how long the JSON header is; and the header’s field table says where the raw arrays begin and end. The decoder does not merely ask whether the file is readable. It requires the exact wire version, the exact fields for that solver, an exact payload length, recognized controls, and state that can exist: attachment flags are 0 or 1, fill lies from 0 to 1, supersaturation is never below −1, and attached cells and masked walls carry their required values.

Then a gate asks a question the codec cannot answer: is this the checkpoint from the registered run in front of me? A reflecting-boundary LK file is perfectly valid diagnostic data, for example, but it cannot support a physical habit gate that registered a fixed-supersaturation far field. A recognized v5 policy is valid syntax but still the wrong experiment when the run registered v6. Gate validators therefore compare the decoded metadata and field bits with the named run, require a byte-stable re-encode, and reconstruct a solver from the recorded controls. The SHA-256 that authenticates an evidence artifact belongs to the surrounding evidence bundle; the checkpoint codec does not smuggle a self-certifying hash into its own payload.

What the seal cannot do

It would be easy to finish this chapter feeling that the machinery settles everything. It settles exactly one thing: that the rules were chosen before the answers were known. Four it does not settle are worth naming.

It does not make the physics right. Freezing a parameter table only makes the parameters fixed. A sealed protocol built on a wrong number produces a beautifully provenanced wrong answer.

It does not improve the reference. The comparison target is Libbrecht’s Figure 1 in arXiv:1211.5555v1, which research/nakaya-morphology-diagram.md describes as “a redrawn schematic of natural, free-falling crystals” rather than a controlled measurement; the project’s own digitisation found its supersaturation axis failing an independent check, which is why only its three boundary temperatures are used and its printed humidity values never are.

A correction does not rewrite the old experiment. If a frozen protocol turns out to have a flaw, its executed bytes remain a historical record, while a logged decision, a new freeze and a full rerun are required before replacement-gate evidence is admissible. The project has already paid a full-rerun bill once and now owes R15 for the corrected science contract.

No human domain-expert review is recorded. Every recorded non-maker reviewer-agent round — including the two-reviewer process that checked this page — is an LLM review. Maker audits are recorded separately, and the maker is not identified as a domain scientist. The project’s own sharing rules require that “at least one human domain scientist reads any manuscript before submission” and call the absence of a recorded human domain-expert review a disclosed limitation, not a substitute. That limitation is disclosed here for the same reason the freeze list is published: a weakness you have named is one a reader can price.

Key idea

A safeguard is not a promise not to cheat. It is an arrangement in which cheating costs something specific, leaves a mark, and has to be signed for. Twenty-five rows, one fingerprint, four preflight refusals, three exit codes, seven executed sabotages — and a price of about twenty hours of compute for changing your mind after the fact, which this project has now paid once.

Phase 6 later closed on an accepted negative finding; Phase 7, the product layer, has not started. What this chapter shows is a historical values-manifest mechanism whose verifier can detect registered value drift. Rules can be revised, confused or bypassed, so the evidence depends on executing and auditing the right checks. The historical executor ran once under the twenty-four-row value protocol, was withdrawn, and ran again under the twenty-five-row value protocol. Neither run executed the ADR 0026 conservative-intersection output rule, even though its freeze row existed. Both value-manifest openings are on the public record: every result must say which registered values it used, while separately stating which outcome operators actually ran.

The grid is 204 points and the headline is computed over 90 of them. One piece of bookkeeping to carry across, because chapter 28 opens with it: the envelope you just watched being sealed — the twenty-five-row 8aeb2b80… — identifies the protocol values in force for chapter 28’s measured CAK run. It does not mean that run executed ADR 0026; its 3/90 is measured-only, not the registered conservative-intersection headline. The earlier twenty-four-row 9aa2e7c1… identifies the values used by the withdrawn sweep. It was withdrawn not because that hash was wrong but because a knob outside the list had overridden a row inside it — and adding the missing row moved the pin. A reviewer who runs the correct verifier can therefore distinguish the two results. A protocol is identified by its hash, so reporting a 9aa2e7c1 number under 8aeb2b80 is detectable from the preserved evidence; hashing does not make misreporting impossible. Chapter 29 itemises what going from twenty-four rows to twenty-five cost. Now the number gets read.
