Chapter 27

Sealing the Envelope

When the result comes back disappointing, what stops you from quietly adjusting the rules until it looks better?

~14 min read 5 figures 4 interactives

By the end you will be able to

  • Explain why the timing of a decision changes its meaning, even when the decision itself is word-for-word identical.
  • Recognise a partial safeguard that is worse than no safeguard, because it looks like protection.
  • Tell “wrong about the world” apart from “wrong about the evidence”, and find the two wired to different exit codes.
  • Say why making cheating expensive and visible is a stronger design than making it forbidden.

The same decision, twice

Here is a rule. A model point that lands within 1 °C of a reference boundary does not count, in either direction.

Read it once as a rule written before any run happened. It is careful. The reference diagram’s own boundaries are only known to about half a degree, so demanding the model place a habit flip — a temperature where the crystal stops growing plates and starts growing columns, or the reverse — more precisely than the reference locates it would be unfair, and the rule says so in advance.

Now read the same sentence as something written after 204 runs came back, with the disagreements sitting near the boundaries. It is an excuse. Not a different sentence — the same sentence. The words did not change. Only the order of events did.

The Phase 6 plan says this out loud, before the sweep it governs:

“The band must be registered before any sweep runs, because applied afterwards the same rule becomes ‘the points that disagreed happened to be near a boundary’ — exactly the post-hoc rationalisation the §3.2 freeze exists to make impossible.”

docs/plans/phase-6-nakaya-validation.md, “Reporting rules that hold for every protocol”

This is the whole chapter in one idea. A scientific claim is not just a number; it is a number plus the order in which the choices were made. So before the validation sweep ran, the project wrote down every choice that could move the answer, turned the whole list into a single 64-character string, and pointed a program at that string with instructions to refuse to produce evidence if one byte of it moved.

Two words first, because the rest of the chapter leans on them. The project’s files live in git, which stores the whole history as a chain of snapshots. Each snapshot is a commit, named by a fingerprint of everything in it plus the fingerprint of the snapshot before it — so a commit’s name depends on its entire past. HEAD is git’s name for the snapshot you are standing on right now.

Key idea

Deciding how you will mark the exam is not cheating. Deciding it after you have seen the answers is. Since nobody can prove from the outside which order it happened in, the project made the order checkable: the marking scheme is hashed, and the hash is recorded in a commit that must sit upstream of the commit that ran the exam.

Deliberately, there is no result in this chapter. You will finish it knowing exactly how the exam is marked, and not knowing the mark. That wait is the point. When the number arrives in chapter 28, you will already be unable to say “well, they probably picked the rules that suited them” — because you will have watched the rules being picked.

The list

The charter names what has to be frozen. It is not a vague instruction to “be careful”; it is a shopping list, and it ends with a price tag:

“Before the first validation sweep runs, freeze docs/libbrecht-parameters.md and a written validation protocol: the T/σ grid; the far-field boundary condition … how a model habit class is scored against the reference regimes … the crystal size at which habit is measured — habit is size-dependent, so measuring at a stated maximum dimension is what keeps comparisons apples-to-apples; metric thresholds; domain budgets; and pressure, physical seed size, Δx, the named surface policy, the fill-CFL bound, the diffusion residual tolerance and its norm, the divergence-identity tolerance, the relaxation-sweep cap, float precision, the parameter interpolation scheme, noise amplitude, seed-ensemble size, the model/code version (commit hash), and the uncertainty-reporting scheme. Any post-freeze edit to parameters or protocol requires a logged ADR and invalidates prior sweep results — the full sweep re-runs. This is what makes ‘a negative result is a result’ survive contact with a disappointing plot.”

project charter.md, §3.2, Phase 6 item 1

(ADR is the project’s name for one of those numbered decision records — an architecture decision record. Decision 0025, below, is one of them.)

In the repository that list is not prose. It is an array called PHASE6_FREEZE_LIST in runner/src/phase6-protocol.ts. Each entry carries six fields: an id, a group, a status of registered or pending, the requirement — in the words of whichever document demands it, which the source file calls “what the charter/ADR requires, in its own terms” — the value chosen, and the source, which study or decision record produced that value. The list runs to twenty-five registered rows today; the code’s own revision log records the first seal as twenty-one.

Read a few. The interesting column is the last one.

Seven of the twenty-five rows of PHASE6_FREEZE_LIST in runner/src/phase6-protocol.ts. The registered values are the file’s own, glossed into plain English where it uses the repository’s shorthand. The right-hand column is not in the file; it is what each row takes away from you afterwards.

One more property matters more than any single row. The function that assembles the list into a hashable document throws an error if any row is still pending. You cannot hash a half-finished protocol and call yourself pre-registered. In the source’s own words, it “refuses to exist while any required item is pending, so a sweep cannot quote a protocol hash the freeze has not actually earned.”

The seal

A list that anybody can edit is a promise. To turn it into a fact, the whole list is written out as one long piece of text, always in exactly the same way — programmers call that serialising — and run through SHA-256: a function that takes any text and produces a fixed 64-character fingerprint, where changing anything at all in the input scrambles the output completely and unpredictably.

“One fixed way” is doing real work there. The repository’s serialiser is described in one line: “Canonical UTF-8 JSON: recursively sorted keys and no insignificant whitespace” (runner/src/gate4-evidence.ts). Its reader is stricter still — it re-serialises whatever it parsed and compares the bytes, so that byte equality “rejects duplicate keys, alternate number spellings, reordered keys, trailing data, and whitespace changes.” Two files that mean the same thing hash the same; two files that mean different things cannot be made to hash the same by tidying the formatting.

Type into the list below and watch the seal break.

The real seal covers the manifest built by phase6ProtocolManifest(), and its fingerprint is stored as a constant with a comment explaining what it is for:

“Pinned in runner/test/phase6-protocol.test.ts, so changing any registered value — a temperature, a fraction, a tolerance, a justification string — fails there rather than silently producing sweep evidence under a protocol nobody agreed to.”

runner/src/phase6-protocol.ts, above PHASE6_PROTOCOL_SHA256

A freeze nothing checks is a comment. The pin is enforced by a test that recomputes the fingerprint from the live code every time the suite runs. Three details in that test are worth more than the rest of the machinery put together, because each one is a way the seal could have looked convincing while being useless.

First: the grid goes in by value, not by size. The manifest embeds the actual list of temperatures and humidity fractions, not the count of them. The comment explains why: “A manifest hash that moved only when a count changed would not notice a temperature or a fraction being swapped for another.” A seal that only counts the pages does not notice a rewritten page.

Second: the hash must not be inside the thing it hashes. That is a literal line in the test file. It sounds pedantic and it is not: a document that contains its own fingerprint cannot be built at all. Writing the fingerprint in changes the document, which changes the fingerprint, which means the one you just wrote in is now wrong. The same problem shows up one level up, with commits. The freeze commit is named by the commit that follows it, because — again in the source’s own words — “a commit cannot contain its own hash.”

Third, and this is the one to remember: a partial seal is worse than none. While the freeze was being amended, someone noticed that the newly written scoring rule had been registered as text but never actually included in the hashed manifest. The grid was sealed. The rule that turned runs into a verdict was not. The test that now prevents this carries the reason as a comment:

Careful

“A hash that pins the grid while leaving the rule that turns runs into a verdict editable is worse than no hash, because it looks like protection.” (runner/test/phase6-protocol.test.ts.) An unsealed protocol is honestly unsealed — a reader knows to be sceptical. A protocol with an impressive fingerprint on the front and an editable marking scheme in the back invites trust it has not earned. When you audit a safeguard, the question is never “is there one?” It is “what exactly is inside it?”

One more piece of engineering that sounds trivial and is not. The parameter table is hashed with its line endings normalised to LF, because Windows and Linux store the invisible end-of-line character differently. Without that step the fingerprint would depend on which machine checked the file out rather than on what the file says — and it would fail on exactly the second computer the project needs to reproduce itself on. The comment states the goal plainly: normalising “makes the hash a statement about the physics, which is what it is for.”

The four refusals

A seal is only useful if something checks it before the work starts. In this project that something is a function called phase6SweepPreflight, and the file it lives in introduces itself like this:

“It fails closed. … A sweep that cannot prove which protocol produced it is not evidence, and the charter’s whole pre-registration argument rests on that being checkable rather than asserted.”

runner/src/phase6-sweep.ts, file header

The sentence the ellipsis swallows is the list of what it requires: four checks, and each closes a different door. Freeze complete stops you pre-registering a protocol with blanks in it. Hash matches the pin stops you editing a registered value. Freeze commit is an ancestor of HEAD stops you writing the protocol after the runs and backdating it — git’s history is a chain, and a commit cannot be an ancestor of one that already existed. Tracked tree is clean stops you running with uncommitted edits, which is the loophole that would otherwise defeat the other three: source you have not committed is source nobody else can inspect.

How we know

The sweep report records the four checks as facts about the run that produced it: “The preflight refused to produce any of it until the freeze was complete, the manifest hashed to the registered pin, the freeze commit was an ancestor of HEAD, and the tracked tree was clean” (research/phase6-sweep-report.md). Its provenance table names the protocol fingerprint 9aa2e7c1… — the protocol that sweep ran under — the execution commit 3e3f75ce…, and the freeze commit e2f1bfca…, “verified an ancestor of the execution commit”. That is not the fingerprint at the top of this chapter. The list has since gained a row and the pin has moved to 8aeb2b80…; decision record 0031 records the move as “9aa2e7c1… → 8aeb2b80… (24 freeze rows → 25)”. Hold on to that difference — chapter 29 is entirely about what it cost.

The marking scheme

The hardest thing to freeze is not a number. It is the rule that turns runs into a verdict. On 2026-07-27, an independent review found that the freeze had registered the grid, the band, the thresholds and the uncertainty scheme — and had never registered how a model habit class is scored against the reference at all. Decision record 0025 filled the hole, and it was written while the answer was still unknown: no sweep had run at the time of writing.

The freeze row it wrote says what it covers, in four items: “the accepted-class matrix, the treatment of neutral and invalid, the flip predicate, and the headline scope” (the agreement-scoring row of PHASE6_FREEZE_LIST). Take them in turn.

1. Each reference regime accepts a named class. The reference diagram divides temperature into four bands at −3.3, −9.9 and −21.5 °C: plates, then columns, then plates again, then a mixed cold band that the source labels “Columns and Plates”. The first three accept exactly one model class. The fourth accepts both.

2. neutral counts as disagreement. The model has a third outcome: the aspect ratio defined in the table above landing strictly between 0.6667 and 1.5, meaning neither a plate nor a column. It would be very convenient to call that an abstention and leave it out of the score. The decision record refuses, and gives the reason:

“The reference names a habit in every regime. The neutral band is ours, not the reference’s, and a model producing neither habit has failed to reproduce the reference. Scoring it as abstention would let a model that never commits report perfect agreement on whatever few points it did commit on.”

docs/decisions/0025-phase6-agreement-scoring-rule.md

The neutral count is nevertheless published separately, so a reader can always tell “wrong habit” from “no habit” — which, as the record puts it, “is the distinction that carries the science.”

3. invalid is excluded — by name. A run that tripped the 65% domain-contact guard — the rule from chapter 23 that invalidates a run whose crystal grows too close to the wall of its box — or broke the six-fold symmetry check, or failed to converge, is thrown out, because “it is not a statement about the model; it is a run that did not happen.” But decision 0025 is explicit that the plan “already requires such runs be excluded by name rather than dropped silently.” The difference between those two is the entire difference between a safeguard and a laundry chute.

4. Flips are bracketed, and how many there are is itself a result. This is the part that will matter most in the next chapter, so read it twice. A flip is not reported as a temperature. It is reported as an interval: the span between the last temperature at which the model produced one pure habit and the first at which it produced the other, with the width of that span carried as the location uncertainty. Neutral and invalid points do not end the search — they widen the bracket, “which is the honest representation: a wide neutral span means the flip location is poorly located, and collapsing it to a midpoint would manufacture precision the data does not have” (phase6DetectFlips, runner/src/phase6-protocol.ts). And then the sentence that pre-registers the whole of chapter 28’s counting argument:

“The number of flips is itself a first-class result: the reference has three, and a single monotone σ0 crossing can produce at most one.”

docs/decisions/0025-phase6-agreement-scoring-rule.md

That is a claim about what the model can do, written down before anybody looked at what it did. If the count comes back at one, nobody gets to call that a surprise, an artefact, or a matter of tuning — the number that would have to appear was named in advance, and so was the reason. Whether it did come back at one is chapter 28’s business, not this chapter’s.

Those four are decision 0025’s. One older row does the remaining work, and it is worth being exact about which is which: the ambiguity band was already in the first twenty-one-row seal, and 0025 published its own budget “alongside the existing 28/6 split” rather than inventing it. The band cuts both ways. Its half-width was fixed by formula before the grid spacing was even chosen:

w = uref + ΔT/2 = 0.5 °C + 1.0 °C / 2 = 1.0 °C

where
w
the half-width of the band around each reference boundary inside which neither agreement nor disagreement is counted
uref
the measured uncertainty on the reference boundary temperatures, ±0.5 °C as digitized from the published figure
ΔT
the frozen spacing of the model’s temperature grid, 1 °C

docs/plans/phase-6-nakaya-validation.md, “ambiguity half-width = 0.5 °C (WP1’s measured boundary uncertainty) + half the frozen T-grid spacing”; evaluated at the frozen grid in the boundary-ambiguity-band row of PHASE6_FREEZE_LIST.

The freeze row spells out the part that makes it a rule rather than a shield: “It cuts BOTH ways: agreement inside the band earns nothing either, because a model agreeing with the diagram only near boundaries has demonstrated nothing.”

Put those together and you can count, in advance and without seeing a single result, exactly which points the headline number will be computed over. Do that now — and remember to multiply at the end. The strip below is the temperature axis alone; every temperature on it is swept at all six supersaturation levels, so 15 counting temperatures × 6 supersaturation levels = 90 headline points. That 90 is the denominator chapter 28 reports against.

What the harsh rule cost, stated in advance

Every one of those four choices makes the model’s job harder. That is suspicious in its own way — it is easy to look rigorous by being gratuitously strict. So the decision record does something unusual: it prices its own strictness, in the same document, before the result.

Dropping the mixed cold regime removes 13 of the 28 counting temperatures. The record does not pretend this is free:

“The headline denominator drops from 28 to 15. That is a real loss of apparent statistical power and it is the correct trade: the 13 discarded points were never going to discriminate.”

docs/decisions/0025-phase6-agreement-scoring-rule.md, Consequences

The reason those 13 could never discriminate is worth holding on to, because it generalises far beyond snowflakes. The cold band accepts both plates and columns, so almost any non-neutral answer scores a point there. A test you pass whatever you do is not a test. And there is a second, deeper mismatch: that band of the reference describes a population of natural falling crystals, while one grid point here is one deterministic crystal. Matching a mixed population with a single run is, in the record’s word, ill-posed.

Then comes the sentence that is hardest to write before a result and worth the most afterwards.

Still unsettled

“A stated limitation rather than a discovered one: the warmest Plates regime has exactly ONE counting temperature (−2 °C). It can therefore only ever score 0% or 100% and carries essentially no statistical weight… Any conclusion about the warm plate regime is a one-point conclusion and must say so.” The obvious fix — extend the grid to −1 °C for one more point — is rejected by name in the same paragraph, because −1 °C sits where the latent-heating correction — which this protocol registers as “carried as a stated systematic; not applied” — is at its largest. Buying one point with the worst systematic in the phase is called “a bad trade”.

Notice what that warning label does to the future. Whatever the warm regime scores, nobody — including the project — can present it as evidence, in either direction. It was disarmed before it was fired.

The record closes by listing what it forecloses: “Deciding after results whether neutral counts. Reporting a single agreement percentage across all four regimes. Quoting a flip temperature to a precision the grid spacing does not support. Dropping an invalid run without naming it.” Four escape routes, named and welded shut while they were still tempting in the abstract rather than in the specific.

Try to cheat

Reading about a safeguard is not the same as pushing on one. Below is a scoring panel with four buttons. Each button makes a change a real researcher would be tempted by, each one edits a row that is genuinely on the frozen list — the row is printed under the button — and each one makes the score jump.

The fourth button needs a word of explanation, because it uses a term the freeze list invented. A point is extent-fragile when its shape is close enough to a class boundary that measuring it at a larger crystal might tip it over. The project measured how much drift there is: between the registered measurement size of 21 lattice cells and the size at which the value has actually converged, 31, the aspect ratio drifts upward by 0.135, and the drift only ever goes one way. So the registered rule flags “any point whose measured AR sits within 0.135 below a class threshold” (uncertainty-reporting row of PHASE6_FREEZE_LIST). Flagging costs you nothing. Deleting the flagged points would quietly remove the ones most likely to misbehave, which is what the fourth button does.

Then read the banner.

The lesson is not that the four edits are forbidden. Several of them are things a careful person could argue for in good faith. The lesson is about when. Before the sweep, each would have been a free amendment: the protocol’s revision log carries six entries registered before any sweep had run, alongside the rule that “every amendment before the first sweep is free — after it, the same change costs a full re-sweep.” After the sweep, the identical edit costs seventeen hours of compute and a numbered public decision record explaining why.

Now the honest version of the fifth-button question, because the revision log answers it and the answer is not comfortable. There is a seventh entry, and the source labels it in capitals: THE FIRST AMENDMENT THAT IS NOT FREE. It is there because somebody found a knob that was not on the list at all — a default buried in the command-line handling that silently chose a different set of physics parameters from the one the protocol had registered. Nobody pressed that button on purpose. A default pressed it. In decision record 0031’s words, “an unregistered CLI default silently overrode a registered freeze row, through a path the freeze did not cover because paramSet was not itself a registered row” — and the bill was the one the panel above prints: “the 204-point sweep of 6995868 is invalidated and re-runs.” Chapter 29 is that bill in full.

So the accurate claim is narrower than “every knob is on the list”, and stronger than it sounds. Nobody can prove a list of this kind complete; the completeness of a freeze list is exactly the thing that gets discovered the hard way. What the machinery does guarantee is two things. Anything on the list cannot move without the fingerprint moving. And anything found to be off the list gets added at a published price: a numbered record, a new entry in the revision log, and the whole sweep again. That is a different kind of rule from “do not do this”. It does not rely on anybody’s honesty holding under pressure. It makes the move expensive, slow, and — because the fingerprint and the git history both move — permanently visible to anyone who looks. The charter states the goal in one line: “Quiet tuning is not a discipline failure that review catches — it is structurally impossible to hide.”

Three exit codes

Everything so far protects the marking scheme. One thing still needs protecting: the difference between two completely different sentences that both start “it failed”.

A program that finishes hands the operating system a small number, its exit code. By convention 0 means success and anything else means failure. The Phase 6 gate uses three, and the assignment is the moral argument of the whole project compiled into a return value:

“A morphology miss does not change exit 0. Invalid numerics, provenance, artifacts, incomplete runs, or protocol violations exit 1. Any flag exits 2.”

docs/plans/phase-6-nakaya-validation.md, Gate contract

Exit 0 — a valid run, whatever nature says. The model can disagree with the reference diagram at every single point and the gate still succeeds, because the gate is not asking “was the model right?” It is asking “is this evidence?” Exit 1 — the evidence is broken. Bad numerics, unverified provenance, a missing artifact, an incomplete run, a violated protocol. Exit 2 — somebody deviated from the frozen command. The registered gate command takes no flags at all, so any flag means the thing that ran was not the thing that was registered, and that is its own category of wrong.

Almost every scientific project says “a negative result is a result”. This one has to mean it, because a program has to return a number and there is no third option between 0 and 1. Try the scenarios.

The last row of that gate contract is the one most projects skip. It is not enough for the gate to pass on good evidence; it has to be shown failing on bad evidence, on demand, for each specific kind of bad. Six sabotages are registered by name:

  • forged provenance
  • a post-freeze parameter edit
  • a merged no-SDAK / SDAK report
  • a domain-contacted run entering results
  • a mismatched far-field condition
  • a habit classification taken at the wrong measurement size

And the requirement is that each “fails by name” — not merely that the gate refuses. A refusal that says only “something is wrong” is almost useless: you cannot tell a caught sabotage from an unrelated bug, and you certainly cannot tell whether the control you thought you were testing is the one that fired. It is the difference between a lock that resists a key and a lock that tells you which key was tried.

The same instinct governs how results get written to disk, though the two gates do it differently and the difference is worth knowing. The Phase 4 and Phase 5 gates publish through publishEvidenceBundle (runner/src/gate4-evidence.ts, imported by gate4a.ts and gate4b.ts): the bundle is built inside a hidden staging folder, every artifact is written and immediately re-read and re-hashed, the whole bundle is verified twice, and only then is it made real by a single renameSync onto its published name. Evidence either appears complete or does not appear. There is no state in which a half-written results folder is sitting there looking finished.

The Phase 6 sweep does not use that function. It writes points.json, report.json and diagram.svg straight into out/phase6-sweep/ as it goes, and its integrity story is a different one: that folder is not tracked by git at all, and “their hashes are the tracked record” (research/phase6-sweep-report.md). The guarantee there is not atomic publication but a committed fingerprint of each artifact, against which anyone can re-hash the file they were handed. Both designs answer the same question — can you tell whether what you are looking at is what was produced? — and it is worth noticing that they answer it with different machinery.

What the seal cannot do

It would be easy to finish this chapter feeling that the machinery settles everything. It settles one thing, exactly: that the rules were chosen before the answers were known. Four things it does not settle are worth naming.

It does not make the physics right. Freezing a parameter table does not make the parameters correct; it only makes them fixed. A sealed protocol built on a wrong number produces a beautifully provenanced wrong answer.

It does not improve the reference. The comparison target is a redrawn schematic — Libbrecht’s Figure 1 in arXiv:1211.5555v1, which research/nakaya-morphology-diagram.md describes as “a redrawn schematic of natural, free-falling crystals” rather than a controlled measurement — and the project’s own digitisation found its supersaturation axis failing an independent check — which is exactly why only its three boundary temperatures are used and its printed humidity values never are.

It cannot be undone, and that is the intended discomfort. A frozen protocol that turns out to have a flaw in it costs a full re-sweep to fix. The mechanism has no setting for “this time we were right to change it”. You will see the project pay that bill, on its own initiative, in chapter 29.

And no human expert has checked any of it. Every review this project has had — internal and external-facing, including the two-reviewer process that checked this page — has been an LLM review. The project’s own sharing rules require that “at least one human domain scientist reads any manuscript before submission” and state the current position without softening it: “All reviews to date, internal and external-facing, are LLM reviews; for publication that is a disclosed limitation, not a substitute.” That limitation is disclosed here for the same reason the freeze list is published: a weakness you have named is one a reader can price.

Key idea

A safeguard is not a promise not to cheat. It is an arrangement in which cheating costs something specific, leaves a mark, and has to be signed for. Twenty-five rows, one fingerprint, four preflight refusals, three exit codes, six named sabotages — and a price of roughly seventeen hours of compute for changing your mind after the fact.

Phase 6 is still in flight as this is written; Phase 7, the product layer, has not started. What exists is a sealed envelope and a machine that will open it exactly once, in public, under rules nobody can now revise without saying so.

The envelope is sealed, the marking scheme is fixed, the grid is 204 points, and the headline will be computed over 15 counting temperatures at 6 supersaturation levels each — 90 points. All that is left is to run it for seventeen hours and read the number, which is the next chapter and the reason every chapter before it exists. One caution to carry across, and it is the chapter’s own thesis turned on itself: the envelope you have just watched being sealed is the twenty-five-row one, 8aeb2b80…. The exam whose result chapter 28 reports was sat under the earlier version of it, 9aa2e7c1…. A protocol is identified by its hash and those are two different hashes — and chapter 29 is about why that distinction turned out to matter enough to throw the run away.
